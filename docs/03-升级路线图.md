# 03 · 升级路线图

> 状态标记：`规划中` / `进行中` / `已完成` / `已放弃`
> 每个已完成项必须写清**验收证据**（哪条命令/测试证明它可用）。

## 总目标

把 CineFlow 从「能自动追剧的工具」升级为**日常真正可用的家庭影视中枢**：

1. 网盘资源不再需要人工去网盘点转存 → **自己会转存、能浏览网盘**
2. 不用打开电脑开网页 → **在飞书/钉钉/TG 里发一句话就能搜和下**
3. 配置不用翻代码 → **界面上看得见、该改的地方有入口**
4. 项目可被他人接手 → **文档齐全、每步可 review**

5. 网盘里的片子不必占 NAS 空间 → **STRM 直连播放**
6. 媒体服务器不再猜片名 → **自动刮削 NFO**

**v1.3.0 结论：M1~M4 全部交付并实测通过。**
**v1.4.0 结论：M5~M10 全部交付并实测通过**（对标调研见
[09-竞品对标与差距分析.md](09-竞品对标与差距分析.md)）。

## 里程碑 M40 · 下载器限速时段（v1.12.0）· 已完成

**动机**：白天限速夜间放开是 NAS 用户最常见的诉求（`docs/09` 竞品矩阵里
qBittorrent / Transmission 原生都有，CineFlow 之前只能去下载器自己的 WebUI 里配）。

| # | 交付项 | 验收证据 |
|---|---|---|
| M40-1 | 服务与接口 | `app/services/speed_limit.py` + 3 个端点（读配置 / 写配置 / 立即应用） |
| M40-2 | 第 14 个定时任务 | `speed_limit`，默认 10 分钟；**幂等**——同一 phase 重复下发不产生副作用 |
| M40-3 | 跨午夜正确 | `23:00-07:00` 这种区间用朴素 `start <= now <= end` 比较**恒为假**，是经典 bug；已显式拆成两段判断。`start == end` 视为全天 |
| M40-4 | qBittorrent 单位 | qB API 收 **B/s**，配置里填 KB/s，**必须 ×1024**，否则实际限速差 1024 倍（等于没限） |
| M40-5 | Transmission 单位与开关 | TR 收 **KB/s 不乘**，但**必须同时下发 `*-enabled`**，否则值存进去了下载照样满速跑；传 0 要**关开关**而不是限速到 0（那会彻底断流） |

| M40-7 | 不假装支持 | 基类 `supports_speed_limit = False`，`xunlei` / `ytdlp` 继承该默认值；不支持的下载器如实标 `skipped` 而不是伪造成功 |
| M40-8 | 刻意不做 per-torrent | 单任务限速需要维护 hash 级状态且各下载器语义不同，收益远低于复杂度；全局限速已覆盖「夜间放开」这个主场景 |
| M40-9 | 设置页卡片 | 「下载器限速时段」卡片，请求失败降级为 `{data:null}`，老后端没这接口时其余设置照常显示 |
| M40-10 | 测试钉住 | `tests/test_speed_limit.py` **62 条**：`parse_hhmm` 脏值、同日 / **跨午夜** / `start==end` 全边界、三种 phase、四种非法归一化、**qB ×1024 / TR 不乘 + enabled / TR 0 关开关 / aria2 字符串**、不支持标 skipped、API 端点 |

## 里程碑 M51 · 多站点 RSS 追新 + 更新检测（v1.18.0）· 已完成

**动机**：用户两条 —— 「参考 Auto_Bangumi，支持多种 RSS 站点与聚合 RSS 解析」
「增加更新检测，可以直接操作更新」。前者补的是本项目最大的一块追新盲区：
番剧站的 RSS **不支持关键词查询**，既有的「订阅巡检（去各站搜）」与
「追新雷达（拉站点最新流）」两条路都用不上它，而它恰恰是时效性最好的源。

**① RSS 方言层**：`feedparser` 只抹平骨架，各站有用字段都在自己命名空间里。
最要紧的是抓到一个**静默真缺陷**：Nyaa 的 `<enclosure>` 是**空的**（种子地址就是
`<link>`，体积与做种数在 `nyaa:size` / `nyaa:seeders`），而旧 `RssIndexer` 只从
enclosure 取 → 所有 Nyaa 结果 `size=0 seeders=0`，用户设了最小做种数就**整站被滤光**，
界面只显示「0 条」且不报任何错。方言判定刻意**看 feed 自述优先于 URL**：
Mikan/Nyaa 镜像域名极多，只看 URL 会让镜像站全退化成 generic 然后继续静默丢字段。

**② 聚合流分流**：一条聚合 RSS 混着几十部作品，必须"先识别每条是什么，
再看是否命中订阅"。`aggregate` 做成**用户可配开关而非自动推断** ——
推断错的代价是**把整站新番下回来**，这种错误用户往往在磁盘满了才发现。
增量判据用 **guid 而不是 pubDate**：RSS 的 pubDate 不可靠（重发/修种会刷新时间，
有站点整条流共用一个时间），按时间会重复下载或漏下。

**③ 更新检测**：实测发现本仓库**至今没有任何 Release/Tag**，
只按 Release 实现会永远回答"已是最新版本" —— 一个不报错的假功能。
故做双路判定并把 `source`（`release`/`branch`）返回出去，让结论本身可核对。
更新动作只做 `git pull --ff-only`：不 merge、不 `reset --hard`，
本地有改动就如实中止；容器部署直接说"我换不了自己的镜像"并给出 compose 命令，
**刻意不挂 docker.sock**（详见 ADR-81）。

**产出**：新增 `app/core/rss_dialects.py`、`app/services/rss_feeds.py`、
`app/services/update_check.py`、`app/api/routers/rss_feeds.py`、`rss_feeds` 表、
第 16 个内置任务、前端第 23 个页面，10 个新端点；
`tests/test_rss_feeds.py` 22 用例，**24 个注入缺陷全部转红**；
pytest 1357 passed / 54 文件，smoke 314/314，ui_check 0 报错。
本轮 4 个初判假绿**全是测试真漏检**（不是注入无效），与上一轮相反 ——
说明"先怀疑注入"这条方法论要两头都查。

## 里程碑 M48 · 站点清单实测瘦身 + 百度网盘存储补链（v1.16.0）· 已完成

**动机**：用户的四条 —— 删无效站点 / 按上游清单补可用站点 / 再查下载器 / 网盘加 115+百度登录。
四条都做了，但**每条的真实结论都和「以为的问题」不一样**。

**① 删站：判据不是首页状态码，是详情页能否取到真链接**

对 20 个 indexer+pan 站点逐站真实搜索，零结果的 11 个**逐个跟到详情页取证**：

内置示例站 **27 → 20 条**。⚠️ 关键：**必须改 seed 而非只删 DB** ——
`create_default_sites()` 按 name 补齐，光删库重启就复活（已验证「全新库 20 条、无复活」）。

**② 补站：上游 12 个「可达」站，只有 1 个真能用**

- 磁力熊用 `GET /?s=` 会**静默返回首页**：真词和乱码词都返回 **20 条、字节数完全一致**。

- 另一个候选 POMO 被排除：`?keyword=` **根本不参与过滤**，任何关键词都返回同一批详情页。

顺带修掉二段抓取的一个静默缺陷：详情页磁力多不带 `dn=`，旧逻辑用**搜索词**兜底标题，

写了 mock qB（qB WebUI API v2 最小子集）把「CineFlow 实现对不对」与「用户机器有没有装 qB」分开。
**投递链路本身是通的**：投磁力 → 任务 `downloading` → sync 后进度 `0.0 → 0.35`。

## 里程碑 M47 · 搜索慢站熔断 + 下载结局如实回报（v1.15.0）· 已完成

**动机**：用户反馈「搜索和下载依然有问题」。先实测再动手，结论与直觉不同 ——

- 搜索**不是搜不到**：8 个启用站点稳定返回 200 条、5 个站有结果。
  真问题是**慢**：YouTube 连不上时吃满 25s 预算且返回 0 条，
  而 `asyncio.gather` 要等最慢的那个，于是**每次搜索都要为它付 25 秒**。
- 下载**最严重的不是投不出去**，而是**假成功**：投递失败仍回 `success: true`，
  界面弹绿色「已加入下载队列」，任务列表里其实是红色 failed ——
  真因（qBittorrent 连不上）从未出现在用户眼前。

**做了什么**：

- `app/services/search_breaker.py`：站点级熔断，连续 3 次「吃满预算且零结果」
  冷却 10 分钟。只在内存里记、到期自动半开、命中即清零、跳过写进诊断
  （`status="skipped"`）。实测 2.0s → 2.0s → **0.0s**。
- `POST /downloads` 的 `success` 改为反映**投递真实结局**；`pending` 带下一步提示。
- `GET /downloads/routing` 从「配没配」升级为「连不连得上」，
  直接复用站点健康巡检的结论，把连通性判断**提前到点击之前**。
- `docker-compose.yml` / `.fnos.yml` 补 `pull_policy: always` ——
  这才是「Docker 版本和 GitHub 不一致」的根因（`:latest` 是可变 tag，
  compose 默认复用本地同名镜像，不比对远端 digest）。

**关键结论（写进 ADR-71 / ADR-72）**：

1. 「建出了一行任务记录」和「投递成功」是两件事，接口必须回报后者，
   否则用户看到的绿色提示会把他引向错误的排查方向。
2. 熔断只能对「吃满预算 + 零结果」计数。慢但有结果的站（PanSou 19s / 2529 条）
   是最有价值的站之一，只按「慢」熔断会把它剔掉；快速返回空也不能计数，
   否则搜冷门片会误伤健康站。

**本轮还查出并修掉 5 个「静默/误导性」缺陷**（用户描述成「界面卡死 / 换页很慢 /
封面裂图」，全都不在最初的两条反馈里）：

| # | 缺陷 | 为什么难发现 | 实测证据 |
|---|---|---|---|
| ⑤ | 4 项配置在白名单里却没挂任何设置页分组 | 后端能改、界面没入口，用户只能猜环境变量名 | 门禁列出 `SEARCH_MAX_PER_SITE` + 熔断三项 |
| ⑥ | 后端 v1.6.0 就返回每站诊断，前端**从没渲染** | 用户看不到「谁超时/谁被跳过」，只能怀疑「只有一个站有结果」 | `app.js` 里搜不到 `data.sites` 的任何渲染 |
| ⑦ | `bgm.tv` 在后端白名单里，前端 `PROXY_HOSTS` 没列 | 浏览器直连拿 `ERR_HTTP2_PROTOCOL_ERROR`，新番日历整片裂图 | 走代理实测 `200 image/jpeg` |
| ⑧ | 切页不关弹窗 → 遮罩留在 `#modal-root` | 新页面**看得见点不动**，刷新就好 → 像「卡死」 | 订阅页开弹窗 → 切设置页 → 任何按钮点不到 |
| ⑨ | 同源封面图把浏览器 ~6 连接池占死 | 换页要等约 **10s**，而后端只用 **8ms** → 像「后端慢」 | 正文长度 `+2s..+8s`=169、`+10s`=2031；切页仍在飞 29 个请求**全是**图片代理 |

⑨ 的取舍写进 **ADR-73**：回收判据用 `isConnected`（是否还挂在文档里）
而非「切页全清」—— 后者会把当前屏正在加载的封面一起掐掉，实测新屏封面全变占位块。
挂载点选 `shell()` 收尾而非 `render()`，因为 `shell()` 是唯一渲染出口
（含 `pageTrending` 换分类时不经过路由的自调用）。

**顺着 ⑨ 又挖出封面裂图的两个真因**（`ui_check` 的 502 一直没人追）：

| # | 缺陷 | 实测 |
|---|---|---|
| ⑩ | 日历封面用 Bangumi **原图** `images.large` | 300 KB ~ 3 MB、单张最慢 **21s**；同一张 `common` 只 **11 KB / 230ms**。卡片宽仅 ~120px，原图像素纯浪费，还打爆代理 15s 超时 → 502 |
| ⑪ | 图片代理对**连接层抖动零重试** | `lain.bgm.tv` 的 TLS 被间歇掐断：同一 URL 三连 = `EXC / EXC / 200`（`SSL: UNEXPECTED_EOF_WHILE_READING`）。镜像轮换只救豆瓣，其它图床一次抖动就 502 |

⑩+⑪ 修完后，一屏封面传输量从约 **20 MB 降到约 0.3 MB**，
`ui_check` 的失败请求数 **24 → 0**、JS 报错 **2 → 0**，**首次 exit 0**。

**门禁侧同时补强**（否则这些修复没有任何东西守着）：
`_is_noise()` 为「我们主动中止的图片请求」与「外站图 404/403」开白名单并写明理由，
但**严格排除本机地址** —— 本机图片代理报错正是抓出 ⑩⑪ 的那根线，不能一起放行；
控制台报错改为带出 `msg.location`，否则 `Failed to load resource` 不带 URL，
根本无法定位是谁挂了。

**产出**：新增 25 个熔断用例 + 9 个图片代理/封面尺寸用例 + 2 条设置页覆盖断言
