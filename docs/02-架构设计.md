# 02 · 架构设计

## 1. 分层总览

```
┌──────────────────────────────────────────────────────────────┐
│  web/        零依赖 Web 控制台（原生 JS，无 CDN，14 页）          │
└────────────────────────────┬─────────────────────────────────┘
                             │ REST /api/v1
┌────────────────────────────▼─────────────────────────────────┐
│  app/api/       router 汇总 + routers/（14 个，按领域拆分）       │
│                 deps：JWT / X-API-Token 双认证                 │
│                 例外：chatops webhook 走平台验签（ADR-03）        │
├──────────────────────────────────────────────────────────────┤
│  app/services/  业务编排层（有 IO，可 async）                    │
│    search / subscribe / radar / trending / download           │
│    library / notify / scheduler / sites / discovery           │
│    presets / settings_store / pan_storage / chatops/           │
├──────────────────────────────────────────────────────────────┤
│  app/core/      纯函数内核（无 IO，易测）                        │
│    meta 解析 · filters 过滤打分 · organizer 命名转移            │
│    config 三级配置 · security PBKDF2+JWT · logger 环形缓冲      │
├──────────────────────────────────────────────────────────────┤
│  app/providers/ 外部能力适配层，装饰器自动注册                    │
│    indexer / pan(盘搜) / panstorage(网盘存储) / downloader      │
│    mediaserver / notify / metadata          共 21 个            │
├──────────────────────────────────────────────────────────────┤
│  app/plugins/   插件基类 + 管理器（发现/热启停/配置/动作）        │
├──────────────────────────────────────────────────────────────┤
│  app/db/        SQLAlchemy 2.0 ORM · SQLite(WAL)              │
└──────────────────────────────────────────────────────────────┘
```

### 分层铁律

1. **`core/` 不许有 IO**。解析、打分、命名都是纯函数，因此可以脱离数据库和网络做单测。
2. **`providers/` 只做协议适配**，不含业务判断。它把外部世界（站点 API、下载器 RPC、
   网盘 SDK）统一成 `Resource` / `BaseDownloader` / `BaseNotifier` 等内部契约。
3. **`services/` 才能编排**。跨 Provider、跨表的流程都写在这里。
4. **`api/` 只做参数校验与响应组装**，不写业务逻辑。

## 2. 核心数据流

### 订阅追新主链路
```
订阅（subscribes）
  → 缺集计算（DB downloaded_episodes ∪ library_files 实际扫描）
  → search.search_for_subscribe（多级关键词并发查所有站点）
  → filters.filter_and_rank（硬过滤 + 加权打分）
  → download.add_download（BT 投下载器 / 网盘登记 pending）
  → download.sync_tasks（进度同步，完成触发）
  → library.transfer（硬链 + 规范命名）
  → mediaserver 刷新 + notify 推送
  → 回写 downloaded_episodes（缺集收敛，永不重复下载）
```

### 扩展点一览

| 想加什么 | 在哪加 | 是否需要改核心 |
|---|---|---|
| 新 BT 站点（标准协议） | 站点管理里加 Torznab/RSS 配置 | 否，零代码 |
| 新 BT 站点（私有 API/网页） | 站点管理里用 `api_generic` / `html_generic` 配字段映射 | 否，零代码 |
| 全新协议的索引器 | `app/providers/indexer/` 加一个 `@register` 类 | 否 |
| 新下载器 | `app/providers/downloader/` 实现 `BaseDownloader` | 否 |
| 新通知渠道 | `app/providers/notify/` 实现 `BaseNotifier` | 否 |
| 新网盘（存储/转存） | `app/providers/panstorage/` 实现 `BasePanStorage` | 否 |
| 新聊天机器人 | `app/services/chatops/` 加一个 `ChatAdapter` | 否 |
| 定时/事件副作用 | `plugins/<id>/` 放插件，界面热启停 | 否 |

## 3. Provider 契约

```python
BaseProvider              # 配置读取 + health_check
├── SearchProvider        # search() / fetch_latest()   ← indexer + pan 搜索
├── BaseDownloader        # add() / list() / control() / remove()
├── BaseNotifier          # send()
└── BasePanStorage        # 网盘存储：list_dir / save_share / storage_info …
```

`Resource` 是统一资源模型，`unique_key` 对磁力链取 infohash 归一，实现跨站去重。

## 4. 认证模型

| 方式 | 用途 | 位置 |
|---|---|---|
| JWT（`Authorization: Bearer`） | Web 前端登录态 | `core/security.py` PBKDF2 + JWT |
| `X-API-Token` | 外部脚本/自动化 | 配 `CF_API_TOKEN` 后免登录 |
| Webhook 签名 | 入站机器人回调 | 见 [05-ChatOps](05-ChatOps-机器人.md)，各平台算法不同 |

## 5. 配置三级优先级

```
代码默认值  <  config/config.yaml  <  环境变量 / .env（CF_ 前缀）
                                          ↑ 部署期
运行期用户改动 → settings 表（settings_store）→ 覆盖上面全部
                                          ↑ 界面可改，重启仍生效
```

`settings_store` 是运行期配置的唯一入口。定时任务改期、站点配置、
ChatOps 平台配置均用此机制，**改完立即生效、重启仍保留**。

⚠️ 但**不是所有配置都走 settings 表**。第 4 级只覆盖那些有专用界面的项；
其余 47 个 `CF_` 配置项仍是「进程启动时快照」，界面「设置」页
只做**只读展示 + 指路**，不假装能改。理由见 [`04-决策记录.md`](04-决策记录.md) ADR-05。

## 6. 关键设计取舍

| 取舍 | 原因 |
|---|---|
| 前端零依赖手写，不用框架 | NAS 常在离线内网；避免构建链与 CDN 依赖，单文件可直接改 |
| SQLite 而非 PostgreSQL | 单机 NAS 场景，WAL 足够；免去用户额外部署数据库 |
| Provider 装饰器注册而非配置文件 | 新增 Provider 只需放文件，不改注册清单（`load_builtin_providers` 显式导入以便打包） |
| 热度归并只作用于榜单展示 | 不污染 `meta` 解析结果，避免影响下载命名与缺集计算 |
| 网盘资源默认不进 BT 下载器 | 网盘是"转存"语义而非"下载"，强行塞给 qB 会失败 |
| 事件总线用进程内 list 而非消息队列 | 单机单进程，无需引入 Redis/MQ 复杂度 |

## 7. 目录约定

```
app/core/       纯函数，禁止 import services / providers
app/providers/  可 import core，禁止 import services
app/services/   可 import core / providers / db
app/api/        可 import 全部，但只做校验与组装
```

> 依赖方向单向向下，避免循环 import。`services` 之间若需互相调用，
> 在函数内部延迟 import（现有代码多处如此，例如 `scheduler._job_target`）。


## 8. v1.3.0 新增子系统

### 8.1 网盘：两类 Provider 的分工

```
                盘搜（SearchProvider，只读）
    用户/订阅 ──► pansou / pan_generic ──► 得到「别人的分享链接」
                                              │
                                              ▼
                                    download.add_download(kind=pan)
                                              │  CF_PAN_AUTO_SAVE
                                              ▼
                网盘存储（BasePanStorage，可写）
                alist / quark / local_dir ──► 转存进「自己的盘」
                                              │
                          失败 ──► 留在 pending 队列
                                              ▼
                          cineflow.pan_transfer 定时重试（ADR-09）
```

两者 `kind` 不同（`pan` vs `panstorage`），在站点表里是两条独立记录。
拆开的理由见 ADR-01；为何主推 AList 见 ADR-02。

### 8.2 ChatOps：入站请求的处理管道

```
平台 POST /api/chatops/webhook/{platform}
   │
   ├─ 1. get_adapter(platform)          按平台取适配器
   ├─ 2. adapter.verify()               验签（失败 → 401，未配密钥默认拒绝 ADR-04）
   ├─ 3. adapter.parse()                归一化成 InboundMessage
   │      └─ challenge？→ 原样回包，不当指令
   ├─ 4. dedupe_key() 去重              10 分钟内重复投递只执行一次
   ├─ 5. 白名单校验                      CF_CHATOPS_ALLOW_USERS（service 层统一做）
   ├─ 6. commands.parse()               42 别名 → 8 规范指令 + 季/集/序号
   ├─ 7. 执行                            延迟 import 调 search/download/subscribe/pan
   │      └─ 会话上下文：搜索结果暂存，供「下载 2」回溯
   ├─ 8. _audit()                       写 audit_logs
   └─ 9. adapter.reply()                回复原会话（钉钉可直接写响应体）
```

设计要点：

- **验签在最外层**，未通过的请求不会碰到任何业务代码。
- **幂等在业务之前**，因为飞书/钉钉都会超时重推，重推不能重复下载。
- **执行层不感知平台**：`_do_search` / `_do_download` 只吃 `Command`，
  所以加新平台只需写一个 `ChatAdapter`，不动任何业务逻辑。
- **适配器自带 `config_fields`**，前端表单据此自动渲染，避免前后端两份字段声明漂移。
