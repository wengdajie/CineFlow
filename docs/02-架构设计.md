# 02 · 架构设计

## 1. 分层总览

```
┌──────────────────────────────────────────────────────────────┐
│  web/        零依赖 Web 控制台（原生 JS，无 CDN，20 页）          │
└────────────────────────────┬─────────────────────────────────┘
                             │ REST /api/v1
┌────────────────────────────▼─────────────────────────────────┐
│  app/api/       router 汇总 + routers/（20 个，按领域拆分）       │
│                 deps：JWT / X-API-Token 双认证 + 三档角色鉴权     │
│                 例外：chatops webhook 走平台验签（ADR-03）        │
├──────────────────────────────────────────────────────────────┤
│  app/services/  业务编排层（有 IO，可 async）                    │
│    search / subscribe / radar / trending / download           │
│    library / notify / scheduler / sites / discovery           │
│    presets / settings_store / pan_storage / chatops/          │
│    scraper / strm_sync / pan_subscribe / upgrade              │
│    config_store / site_health / ranking / rule_groups         │
├──────────────────────────────────────────────────────────────┤
│  app/core/      纯函数内核（无 IO，易测）                        │
│    meta 解析 · filters 过滤打分 · organizer 命名转移            │
│    nfo NFO 渲染 · categories 分类判定 · rules 规则组分层        │
│    config 三级配置 · security PBKDF2+JWT · logger 环形缓冲      │
├──────────────────────────────────────────────────────────────┤
│  app/providers/ 外部能力适配层，装饰器自动注册                    │
│    indexer / pan(盘搜) / panstorage(网盘存储) / downloader      │
│    mediaserver / notify / metadata          共 23 个            │
├──────────────────────────────────────────────────────────────┤
│  app/plugins/   插件基类 + 管理器（发现/热启停/配置/动作）        │
├──────────────────────────────────────────────────────────────┤
│  app/db/        SQLAlchemy 2.0 ORM · SQLite(WAL)              │
└──────────────────────────────────────────────────────────────┘
```

### 分层铁律

1. **`core/` 不许有 IO**。解析、打分、命名都是纯函数，因此可以脱离数据库和网络做单测。
2. **`providers/` 只做协议适配**，不含业务判断。它把外部世界（站点 API、下载器 RPC、
   网盘 SDK）统一成 `Resource` / `BaseDownloader` / `BaseNotifier` 等内部契约。
3. **`services/` 才能编排**。跨 Provider、跨表的流程都写在这里。
4. **`api/` 只做参数校验与响应组装**，不写业务逻辑。

## 2. 核心数据流

### 订阅追新主链路
```
订阅（subscribes）
  → 缺集计算（DB downloaded_episodes ∪ library_files 实际扫描）
  → search.search_for_subscribe（多级关键词并发查所有站点）
  → filters.filter_and_rank（硬过滤 + 加权打分）
  → download.add_download（BT 投下载器 / 网盘登记 pending）
  → download.sync_tasks（进度同步，完成触发）
  → library.transfer（硬链 + 规范命名）
  → mediaserver 刷新 + notify 推送
  → 回写 downloaded_episodes（缺集收敛，永不重复下载）
```

### 扩展点一览

| 想加什么 | 在哪加 | 是否需要改核心 |
|---|---|---|
| 新 BT 站点（标准协议） | 站点管理里加 Torznab/RSS 配置 | 否，零代码 |
| 新 BT 站点（私有 API/网页） | 站点管理里用 `api_generic` / `html_generic` 配字段映射 | 否，零代码 |
| 全新协议的索引器 | `app/providers/indexer/` 加一个 `@register` 类 | 否 |
| 新下载器 | `app/providers/downloader/` 实现 `BaseDownloader` | 否 |
| 新通知渠道 | `app/providers/notify/` 实现 `BaseNotifier` | 否 |
| 新网盘（存储/转存） | `app/providers/panstorage/` 实现 `BasePanStorage` | 否 |
| 支持 WebDAV 的网盘 | 站点管理里加一条 `webdav` 站点（填 URL + 账号密码） | 否，零代码 |
| 新 NFO 字段 | `app/core/nfo.py`（纯函数，改完直接单测） | 否 |
| 新媒体分类 | `app/core/categories.py` 的 `_GENRE_MAP` / 关键词表 | 否 |
| 新聊天机器人 | `app/services/chatops/` 加一个 `ChatAdapter` | 否 |
| 定时/事件副作用 | `plugins/<id>/` 放插件，界面热启停 | 否 |

## 3. Provider 契约

```python
BaseProvider              # 配置读取 + health_check
├── SearchProvider        # search() / fetch_latest()   ← indexer + pan 搜索
├── BaseDownloader        # add() / list() / control() / remove()
├── BaseNotifier          # send()
└── BasePanStorage        # 网盘存储：list_dir / save_share / storage_info
                          #   + list_share / save_share_files（分享追更用，
                          #     不支持的网盘由基类给降级默认值）
```

`Resource` 是统一资源模型，`unique_key` 对磁力链取 infohash 归一，实现跨站去重。

## 4. 认证模型

| 方式 | 用途 | 位置 |
|---|---|---|
| JWT（`Authorization: Bearer`） | Web 前端登录态 | `core/security.py` PBKDF2 + JWT |
| `X-API-Token` | 外部脚本/自动化 | 配 `CF_API_TOKEN` 后免登录 |
| Webhook 签名 | 入站机器人回调 | 见 [05-ChatOps](05-ChatOps-机器人.md)，各平台算法不同 |
| **匿名** | `GET /api/v1/strm/play/{id}`：播放器带不了 JWT | 只回 302 跳转、不代理流量、不列举内容（同 ADR-03 的思路，见 ADR-14） |

### 4.1 角色鉴权（v1.5.0）

认证解决「你是谁」，授权解决「你能干什么」。三档角色按 `rank` 比较：

```
viewer(1)  只读        ← CurrentUser
operator(2) 运营写操作  ← OperatorUser：搜索/订阅/下载/入库/手动巡检/网盘转存
admin(3)   配置写操作   ← AdminUser：系统配置/站点/用户/规则组/榜单规则/调度改期
```

```
请求 ──▶ current_user()          解析 JWT 或 X-API-Token → User
          │                       （用户不存在或被停用 → 401）
          ▼
        require_role(minimum)     role_of(user).rank >= minimum.rank ?
          │                       否 → 403，提示缺哪一档权限
          ▼
        端点业务逻辑
```

三条关键约定：

1. **角色以数据库为准，不信 JWT 里的 role 副本**。JWT 是签发时的快照，
   信它就意味着「降权要等旧令牌过期才生效」。令牌里仍带 role，
   但**只供前端决定隐藏哪些按钮**。
2. **前端隐藏入口不是安全边界**。`visiblePages()` / `canDo()` 只改善体验，
   每个写端点都必须显式挂 `OperatorUser` 或 `AdminUser`。
3. `is_superuser` 布尔位保留，**由 role 推导**（`admin ⇔ true`），
   老代码、旧令牌与 `X-API-Token` 取管理员的逻辑因此零改动。

详见 [ADR-19](04-决策记录.md)。

## 5. 配置三级优先级

```
代码默认值  <  config/config.yaml  <  环境变量 / .env（CF_ 前缀）
                                          ↑ 部署期
运行期用户改动 → settings 表（settings_store）→ 覆盖上面全部
                                          ↑ 界面可改，重启仍生效
```

`settings_store` 是运行期配置的唯一入口。定时任务改期、站点配置、
ChatOps 平台配置均用此机制，**改完立即生效、重启仍保留**。

v1.5.0 起第 4 级由 `config_store` 统一承担，覆盖范围从「有专用界面的少数项」
扩展到 **`EDITABLE` 白名单里的 51 项**：

```
启动：init_db() → config_store.apply_overrides() → load_builtin_providers() → scheduler.start()
                        │
                        └─ 读 settings 表的 runtime_config，用 object.__setattr__
                           写回 settings 单例 → 所有既有 settings.X 读取点零改动生效
```

⚠️ 但**仍不是所有配置都能改**。判定标准很清楚：
**代码是在请求/任务里读 `settings.X`，还是在启动时读一次？**
前者可编辑（进白名单），后者不可——`DATA_DIR` / `PORT` / `SECRET_KEY` / `DB_URL`
等启动期配置保留只读并在界面标「需重启」。
让它们「看起来能改」就是造一个假功能。理由见 ADR-18
（它**部分推翻了 ADR-05**：不是全部只读，而是只放开真能生效的）。

## 6. 关键设计取舍

| 取舍 | 原因 |
|---|---|
| 前端零依赖手写，不用框架 | NAS 常在离线内网；避免构建链与 CDN 依赖，单文件可直接改 |
| SQLite 而非 PostgreSQL | 单机 NAS 场景，WAL 足够；免去用户额外部署数据库 |
| Provider 装饰器注册而非配置文件 | 新增 Provider 只需放文件，不改注册清单（`load_builtin_providers` 显式导入以便打包） |
| 热度归并只作用于榜单展示 | 不污染 `meta` 解析结果，避免影响下载命名与缺集计算 |
| 网盘资源默认不进 BT 下载器 | 网盘是"转存"语义而非"下载"，强行塞给 qB 会失败 |
| 事件总线用进程内 list 而非消息队列 | 单机单进程，无需引入 Redis/MQ 复杂度 |
| 可编辑配置用白名单而非全放开 | 「改了不生效」比「不能改」更糟；只放开运行期读取的键（ADR-18） |
| 只三档角色，不做细粒度 ACL | 家用场景真实需求就三种人；ACL 的排查成本远大于收益（ADR-19） |
| 规则组用有序分层而非调权重 | 一维评分无法编码多维交叉偏好，权重会互相打架（ADR-22） |
| 不健康的下载器排后而不剔除 | 健康数据天生过期，剔除会导致「明明能用却不投递」（ADR-21） |

## 7. 目录约定

```
app/core/       纯函数，禁止 import services / providers
app/providers/  可 import core，禁止 import services
app/services/   可 import core / providers / db
app/api/        可 import 全部，但只做校验与组装
```

> 依赖方向单向向下，避免循环 import。`services` 之间若需互相调用，
> 在函数内部延迟 import（现有代码多处如此，例如 `scheduler._job_target`）。


## 8. v1.3.0 新增子系统

### 8.1 网盘：两类 Provider 的分工

```
                盘搜（SearchProvider，只读）
    用户/订阅 ──► pansou / pan_generic ──► 得到「别人的分享链接」
                                              │
                                              ▼
                                    download.add_download(kind=pan)
                                              │  CF_PAN_AUTO_SAVE
                                              ▼
                网盘存储（BasePanStorage，可写）
                alist / quark / local_dir ──► 转存进「自己的盘」
                                              │
                          失败 ──► 留在 pending 队列
                                              ▼
                          cineflow.pan_transfer 定时重试（ADR-09）
```

两者 `kind` 不同（`pan` vs `panstorage`），在站点表里是两条独立记录。
拆开的理由见 ADR-01；为何主推 AList 见 ADR-02。

### 8.2 ChatOps：入站请求的处理管道

```
平台 POST /api/chatops/webhook/{platform}
   │
   ├─ 1. get_adapter(platform)          按平台取适配器
   ├─ 2. adapter.verify()               验签（失败 → 401，未配密钥默认拒绝 ADR-04）
   ├─ 3. adapter.parse()                归一化成 InboundMessage
   │      └─ challenge？→ 原样回包，不当指令
   ├─ 4. dedupe_key() 去重              10 分钟内重复投递只执行一次
   ├─ 5. 白名单校验                      CF_CHATOPS_ALLOW_USERS（service 层统一做）
   ├─ 6. commands.parse()               42 别名 → 8 规范指令 + 季/集/序号
   ├─ 7. 执行                            延迟 import 调 search/download/subscribe/pan
   │      └─ 会话上下文：搜索结果暂存，供「下载 2」回溯
   ├─ 8. _audit()                       写 audit_logs
   └─ 9. adapter.reply()                回复原会话（钉钉可直接写响应体）
```

设计要点：

- **验签在最外层**，未通过的请求不会碰到任何业务代码。
- **幂等在业务之前**，因为飞书/钉钉都会超时重推，重推不能重复下载。
- **执行层不感知平台**：`_do_search` / `_do_download` 只吃 `Command`，
  所以加新平台只需写一个 `ChatAdapter`，不动任何业务逻辑。
- **适配器自带 `config_fields`**，前端表单据此自动渲染，避免前后端两份字段声明漂移。


## 9. v1.4.0 新增子系统

### 9.1 刮削：为什么拆成 core + service 两层

```
library.transfer 成功
   │
   ├─ core/nfo.py            纯渲染：dict → XML 字符串（无 IO，可离线单测）
   │    build_movie_nfo / build_tvshow_nfo / build_season_nfo / build_episode_nfo
   │
   └─ services/scraper.py    才做 IO：
        1. 取元数据：TMDB（含 credits 演职员）→ 失败则用本地 meta 解析结果
        2. 写盘：movie.nfo / tvshow.nfo / season.nfo / <同名>.nfo
        3. 下图：poster.jpg / fanart.jpg / seasonN-poster.jpg（CF_SCRAPE_IMAGES）
        4. 已有 NFO 且 CF_SCRAPE_OVERWRITE=false → 跳过（不冲用户手改）
```

`cineflow.scrape` 定时任务（默认 `30 4 * * *`）扫 `library_files` 里缺 NFO 的行做批量补刮，
单次上限 `CF_SCRAPE_BATCH` 防止打满 TMDB 限速。TMDB 不可用时写**最小 NFO** 并标 `degraded`：
"有一份不完整但正确的元数据"胜过"让媒体服务器乱猜"（ADR-12）。

### 9.2 STRM：同步与播放两条独立路径

```
【同步路径】cineflow.strm_sync（CF_STRM_SYNC_INTERVAL_MINUTES）
  panstorage.list_dir 递归
     ├─ 视频文件 → 写 <name>.strm，内容按 CF_STRM_LINK_MODE：
     │     proxy  → {CF_STRM_BASE_URL}/api/v1/strm/play/{record_id}
     │     direct → 网盘当次返回的临时直链
     ├─ 字幕/NFO/图片 → 直接下载（CF_STRM_SYNC_METADATA，文件很小但媒体库需要）
     └─ 落 strm_records（记 storage/远端路径/本地路径/大小）

【播放路径】播放器 → GET /api/v1/strm/play/{id}（匿名）
     → 查 strm_records → panstorage.resolve_download_url 现取直链
     → RedirectResponse(302)   ← 只跳转，流量不过 CineFlow

【清理】CF_STRM_CLEAN_INVALID：远端已消失的记录 → 删本地 .strm + 删记录
        （不清理会在媒体库里留下点开就报错的"幽灵剧集"）
```

选 `proxy` 作默认值的理由见 ADR-14：直链会过期，而 `.strm` 一旦被媒体库扫进去
就可能几个月不再重扫，写过期链接等于埋雷。

### 9.3 网盘分享追更：增量判定与停手条件

```
pan_subscribes 一行 = 一个分享链接的追更任务
   │  cineflow.pan_subscribe（CF_PAN_SUBSCRIBE_INTERVAL_MINUTES，默认 60 分钟）
   ├─ _should_run()      星期几 / expire_at 到期 → 直接跳过（日更剧不必整天轮询）
   ├─ list_share()       列举分享内文件
   │     └─ 网盘不支持列举 → 哨兵 `__whole_share__` 记「已整体转存过」防重复搬
   ├─ match_files()      包含/排除关键词 + 正则；saved_files 去重 → 只留新增
   │     └─ 用户正则写错：_compile 捕获 re.error 当没填，绝不让巡检崩
   ├─ apply_rename()     第08集.mp4 → 剧名 - S01E08.mp4（方便后续识别入库）
   ├─ save_share_files() 逐文件转存
   └─ 失败累计到 CF_PAN_SUBSCRIBE_MAX_FAILURES → status=invalid 停手（死链不无限重试）
```

### 9.4 洗版：三重防横跳 + 先入库后删旧

```
cineflow.upgrade（默认关闭 CF_UPGRADE_ENABLED=false，因为它会删文件）
   │
   ├─ 只看 best_version=True 的订阅          ← 第一重
   ├─ evaluate()：新资源分 - 已入库 quality_score ≥ CF_UPGRADE_SCORE_DELTA(15)  ← 第二重
   ├─ library_files.upgrade_count < CF_UPGRADE_MAX_TIMES(2)                     ← 第三重
   ├─ 下载新版本（走既有 download 链路，带 upgrade_for 标记）
   └─ 入库时才 library.replace_library_file()：
        新文件确实入库成功 → 删旧文件 + quality_score/upgrade_count 更新
        （反过来先删后下，中途失败就在媒体库留一个空洞）
```

### 9.5 分类归档：判不出就不猜

```
organizer.build_target_path(..., genres=?, original_language=?)
   └─ CF_CATEGORY_ENABLED=true 时：
        categories.detect(media_type, genres, original_language, title)
           ├─ 优先 TMDB genre 映射（_GENRE_MAP：Animation→动漫、Documentary→纪录片…）
           ├─ 再看语言与标题关键词兜底
           └─ 判不出 → return None → 不加分类目录（原样入库）
        categories.directory_for() → 电影 / 电视剧 / 动漫 / 纪录片 / 综艺 / 儿童
```

默认关闭：给已有媒体库中途加一级目录会让用户手工搬文件，必须由用户主动选择（ADR-13）。

### 9.6 老库升级：为什么不上 Alembic

`Base.metadata.create_all()` 只会**建新表**，不会给已有表**加列**。
v1.4.0 给 `library_files` 加了 `quality_score` / `upgrade_count`，
老库直接启动会在 `/system/dashboard`、`/library/files` 等处 500（已实测复现）。

所以 `init_db.migrate_columns()` 用一张表驱动清单 `_ADDED_COLUMNS` 做
幂等 `ALTER TABLE ... ADD COLUMN`，失败只 `warning` 不阻塞启动。
不引入 Alembic 是为了保持"零迁移文件、一个 SQLite 文件即全部状态"的轻量部署（ADR-17）。

## 10. v1.5.0 新增子系统

### 10.1 可编辑配置：白名单 + 先校验后落库

```
PUT /system/settings {values:{...}}
      │
      ▼
config_store.update(values)
      │
      ├─ 1. 逐键查 EDITABLE 白名单        ← 不在白名单 → ValueError（400）
      ├─ 2. coerce() 逐项校验             ← 类型/范围/枚举/cron
      │      cron 复用 scheduler.validate_cron()  ← 同一份规则，避免两处漂移
      ├─ 3. **全部通过后**才写 settings 表  ← 关键：不留半吊子状态
      ├─ 4. object.__setattr__ 回填 settings 单例  ← 热生效
      └─ 5. 涉及周期的键 → scheduler.refresh_builtin_jobs()  ← 自动改期
```

**为什么第 3 步要先全校验**：如果边校验边落库，「改 5 项、第 3 项非法」会留下
前 2 项已生效、后 2 项没生效的中间状态——用户完全无法推断系统当前到底是什么配置。

**为什么用 `object.__setattr__`**：替代方案是把每个读取点改成「先查表、没有则退默认」，
那要改上百处调用，漏一处就是隐蔽的不一致。值在 `coerce()` 里已经校验过，
绕过 pydantic 直接赋值是安全的，且让全部既有代码零改动受益。

### 10.2 站点健康：探测「静默失效」

```
check_site(site_id)
      │
      ├─ 搜索类站点 → provider.search(PROBE_KEYWORD="的")   ← 真搜一次
      │                    │
      │                    ├─ 有结果 + 耗时 < SLOW_MS  → ok
      │                    ├─ 0 结果 或 耗时 ≥ SLOW_MS → degraded  ← Cookie 过期的典型表现
      │                    └─ 异常/超时                → down
      ├─ 其它类型站点 → health_check()（探首页足够）
      │
      ├─ 写 site_health 记录 → flush() → 裁剪到每站 KEEP_PER_SITE=50 条
      │                        ↑ 必须先 flush，否则本次记录不参与计数，永远多留一条
      │
      └─ 告警判定：连续失败 ≥ FAIL_THRESHOLD 且**状态发生翻转** → 通知
                   手动探测（notify=False）→ 不通知（用户正看着屏幕）
```

**为什么要真搜一次**：探首页对 Cookie 过期完全无感——首页照样 200，
只有搜索结果会变成 0 条。用户的体感是「最近怎么没更新」，查不到原因。
代价是每次探测产生真实请求，所以默认周期是 180 分钟而不是几分钟（ADR-20）。

### 10.3 下载器调度：策略排序 + 健康降权 + 失败换源

```
downloader_candidates(prefer)
      │
      ├─ healthy_downloaders()
      │     ├─ 只有 1 个 → 直接返回（不查健康、不排序）
      │     ├─ 按策略排序：priority | least_tasks | round_robin
      │     └─ 健康降权：down/degraded 的**移到末尾**（不剔除，ADR-21）
      │           健康数据取不到（异常）→ 退回策略排序，不抛异常
      ├─ prefer 命中的提到最前
      └─ FAILOVER=false → 只返回首选 1 个（行为与 v1.4.0 完全一致）

download.add_download() 遍历候选：第 1 个失败 → 自动换第 2 个 → …
```

### 10.4 榜单自动订阅：节流 + 已处理去重

```
run_rule(rule, dry_run=False)
      │
      ├─ fetch_candidates(rule)      ← TMDB 榜单 或 本地资源热度榜
      ├─ filter_candidates(...)      ← 纯函数：评分/票数/年份/包含/排除
      ├─ 剔除 handled_ids 里已处理过的  ← 用户手动删掉的订阅不会被加回来
      ├─ 截断到 RANKING_MAX_PER_RUN（默认 5）  ← 否则一次刷进上百个订阅
      ├─ dry_run？→ 只返回将要创建的清单，不落库
      └─ 创建订阅 → handled_ids 追加（截断 500 条）→ 更新统计
```

**为什么按 `handled_ids` 而不是「订阅表里还在不在」判重**：后者会让用户手动删掉的
订阅在下次巡检时又被加回来，用户会觉得这东西有毒（ADR-23）。

### 10.5 过滤规则组：在既有过滤链上加一层分层

```
search() ──▶ filter_and_rank(resources, rule, group)
                  │
                  ├─ 既有硬过滤（枪版/无关剧/做种不足）
                  ├─ 既有 score_resource() 加权打分
                  └─ group 非空？→ rules.annotate(group, resources, resource_meta)
                                        │
                                        ├─ 逐资源 match_level() → (层号, 层名)
                                        ├─ 未命中 → UNMATCHED_LEVEL(9999)
                                        │    accept_unmatched=False → 剔除
                                        └─ 排序键 (rule_level, -score)
                                              ↑ 层间定优先，层内仍按既有评分
```

`group` 从哪来：`rule_groups.load_group(subscribe.rule_group_id)`
——指定的组不存在或被停用时**退回默认组**，把 fallback 决策收在一处，
避免每个调用点各写一遍。`group=None` 时 `annotate` 原样返回，即完全不改变既有行为。

**为什么 `core/rules.py` 不直接 import `filters`**：它需要资源的 `MetaInfo`，
但为了保持 core 层「纯函数、无 IO、可离线单测」，`meta_of` 由调用方注入
（同 ADR-10 / ADR-11 的思路）。

### 10.6 三档角色如何铺到 120 个端点

不是逐个端点想权限，而是**按写操作的性质二分**：

| 性质 | 依赖 | 例子 |
|---|---|---|
| 只读 | `CurrentUser` | 列表、详情、概览、日志、试算/预览 |
| **运营类**写 | `OperatorUser` | 搜索、订阅 CRUD、下载、入库、手动巡检、网盘转存、STRM 同步、立即执行任务 |
| **配置类**写 | `AdminUser` | 站点、系统设置、调度改期、插件启停、规则组、榜单规则、用户、ChatOps 配置 |

判据是一句话：**「这个操作会不会改变系统对所有人的行为？」**
会 → admin；只是干一次活 → operator。
这样新增端点时不需要重新讨论，照判据挂依赖即可。

## 11. v1.6.0 新增子系统

### 11.1 搜索聚合：轮转交错 + 每站诊断

原先的聚合是「全部收集 → 去重 → 截断」，缺陷是**截断发生在混合之后**：
返回 214 条的站会把返回 90 条的站挤到窗口之外，用户看到的就是"只有一个站有结果"。

```
搜索关键词
   │
   ├─ 并发 _search_one(站点A) ──► (资源[], SiteOutcome{status,raw,kept,ms,message})
   ├─ 并发 _search_one(站点B) ──► (资源[], SiteOutcome{...})
   └─ 并发 _search_one(站点C) ──► ([],    SiteOutcome{status:"error", message:"502"})
   │
   ▼
apply_site_quota(grouped, SEARCH_MAX_PER_SITE)
   │   轮转交错：A1,B1,C1,A2,B2,C2…（不是 A 全部 + B 全部）
   ▼
dedupe → 全局上限
   │
   ▼
(results, outcomes)  ← search_detailed()
                        search() 只返回 results，老调用点零改动
```

**为什么交错而不是砍配额**：公平性问题的本质是"谁能进入结果窗口"，
答案在**合并次序**，不在丢弃数据。首版实现按每站 40 条截断，
总数反而从 145 掉到 80（ADR-25 记录了这次返工）。
`SEARCH_MAX_PER_SITE` 保留为安全阀，默认 300 —— 正常情况碰不到，
只防单站返回几万条打爆内存。

`SiteOutcome` 四态的意义在于**把"没有结果"拆成可行动的原因**：
`empty`（连通但无匹配，如 Nyaa 只收日番）与 `error`（如 Jackett 未部署报 502）
对用户来说要做的事完全不同。

### 11.2 榜单元数据：站点自带 → 资源 extra → meta 列 → 榜单字段

```
站点搜索 API 返回的列表项
  {image, doub_score, years, class, episodes, performer, ...}
        │
        ▼  generic_api._media_meta()（DEFAULT_MEDIA_MAP，可用 options.media_map 覆盖）
  {poster, rating, year, genres, total_episodes, actors, ...}
        │
        ▼  合并进每条 Resource.extra
        │
        ▼  search._save_results() 白名单过滤 → ResourceRecord.meta（已有 JSON 列，无需迁移）
        │      ⚠️ 已存在的记录要**回填空字段**，否则老库永远拿不到封面
        ▼
  trending._Bucket.absorb_media()（逐字段先到先得，空值不覆盖）
        │
        ▼  榜单 to_dict() → 前端 rankingBoard()
                              ├─ 有图 → <img referrerpolicy=no-referrer>，onerror 退占位
                              └─ 无图 → 按标题哈希取稳定色相的占位块
```

三个刻意的取舍：
- **不强依赖 TMDB**：站点结果里本来就带封面和评分，多打一次 TMDB 还会因译名差异匹配错（ADR-26）。
- **映射表而非硬编码**：不同站点字段名不同，接新站改配置即可。
- **空值不输出**：评分 `0`/空/"暂无" 不产出 `rating` 字段——把"无数据"渲染成"0 分"是制造错误信息。

### 11.3 yt-dlp：合规边界在入口，风控在缓存

```
POST /downloads/webvideo/probe?url=...
   │
   ├─ is_blocked(url)?  ── 正片播放页/流媒体平台 → 400 + 可读中文原因（不发任何请求）
   │
   ├─ _cache_get(url)?  ── 命中（TTL 5 min）→ 直接返回（反复点「解析」瞬间响应）
   │
   ▼  asyncio.to_thread(yt_dlp.extract_info)   ← 同步阻塞库必须离开事件循环
   │
   ├─ 成功 → _cache_put()（**只缓存成功**：失败多是临时风控，缓存会让用户以为永久坏了）
   └─ 失败 → is_rate_limited()?
               ├─ 是（412/429）→ 退避重试 sleep(1.5×(n+1))，耗尽后给"稍等几秒再试"
               └─ 否（404/私有）→ 立即返回原因，不浪费重试
```

B 站实测会对连续解析回 `HTTP 412`（第 1 次成功、紧接的第 2 次就被拒），
带不带请求头都一样——这是**频率风控**而非鉴权问题，所以解法是缓存 + 退避，
而不是继续伪装请求头。

`_tasks` / `_futures` 必须是 `ClassVar`：每次 API 请求都会 new 一个 Provider 实例，
挂在实例上的任务表下一次查询就找不到了。

### 11.4 前端：唯一 DOM 写入口负责丢弃过期渲染

20 个页面函数的模式都是「先画 `loading()` → `await` 拉数据 → 画真内容」。
只要用户在 `await` 期间切页，旧请求返回后就会覆盖新页面。

```
go("settings") ──► store.page = "settings"
                        ▲
站点健康的慢请求(12s)返回 ──► shell(内容, "站点健康", …)
                        │
                        └─ PAGE_BY_TITLE["站点健康"] = "sitehealth" ≠ store.page → return（丢弃）
```

**为什么把守卫放在 `shell()`**：它是唯一的 DOM 写入口，41 处调用一处修复全部覆盖；
若在每个页面函数里手工判断，需要改 41 个地方，且以后每加一页都可能漏——
这类约束必须由基础设施保证（ADR-27）。

判据用**页面标题**而非自增计数器：异步回调不知道自己属于哪一次导航，
但它清楚自己在画哪个页面。「出错了」那一屏没有页面标题，单独用 `navEpoch` 判断。

## 12. v1.7.0 新增子系统

### 12.1 网盘能力位矩阵（能力声明 → 前端渲染）

问题：四种存储后端能力差异极大（WebDAV 协议无搜索语义、本地目录无"保活"概念）。
若前端按 `provider` 类型硬编码按钮，则**能力矩阵被复制到两处**，新增网盘必然漂移。

```
BasePanStorage
  ├── supports_rename / supports_move / supports_search / supports_keepalive
  ├── capabilities()  ──► dict[str, bool]
  └── rename / move / copy / search / keep_alive
        └── 默认实现返回 False/空，**不抛 NotImplementedError**
                │
                ▼
services/pan_storage.overview()  ──►  每个盘附带 capabilities
                │
                ▼
GET /api/v1/pan  ──►  web/assets/app.js
                        └─ 按能力位渲染按钮；不支持的操作**根本不渲染**
```

要点（ADR-28）：

- 新增网盘时**前端零改动**；新增能力时改基类 + 具体后端 + 前端映射三处。
- 基类默认实现不抛异常，是为了让未实现新方法的第三方 Provider
  不至于在 `overview()` 里炸掉整个网盘页——降级成"不支持"可接受，白屏不可接受。
- 同一原则也用在搜索结果上：`Resource.actions` 由**链接种类**（磁力 / ed2k /
  网盘分享 / 网页视频）推导可用动作，前端 `resourceActions()` 按位渲染，
  所以网盘类资源会同时出现「转存」与「下载」。

### 12.2 封面回退链与图片代理

```
榜单条目
   │
   ├─1─ 站点自带元数据（零额外请求，与资源同源，不会配错）
   ├─2─ 豆瓣 subject_suggest（免 API Key，中文命中率最高）
   ├─3─ TMDB（需 Key，多语言更规范）
   └─4─ 占位色块（按标题哈希取色，保证 UI 不破版）

services/trending.enrich_posters()
   └─ 异步并发 8，**只补前 24 条**（补图是锦上添花，不能让榜单响应
      取决于第三方站点健康度）；`with_poster=false` 可整体关闭
```

**为什么需要后端图片代理**（ADR-30）：豆瓣图床校验 `Referer` ——
裸请求返 **418**，带 `Referer: https://movie.douban.com/` 返 200（实测 25069 字节）。
浏览器跨站请求**只会发送同源或降级后的 Referer**，页面无法伪造成 `movie.douban.com`，
所以前端加 `referrerpolicy` 在原理上就不可行，只能服务端代拉：

```
<img src="/api/v1/images?url=https://img.doubanio.com/...">
        │
        ▼
routers/images.py
   ├─ 防线①  域名白名单：host == suffix or host.endswith("." + suffix)
   │          （用 host.endswith(suffix) 会被 doubanio.com.attacker.net 绕过）
   ├─ 防线②  仅允许 http / https（挡 file:// gopher:// 等）
   ├─ 防线③  响应 content-type 必须 image/*，并有 MAX_BYTES 上限
   └─ 补 Referer 转发 ──► 豆瓣图床 200
```

代理**刻意不挂登录校验**：`<img>` 标签带不了 `Authorization` 头，
安全性由白名单而非鉴权保证。B 站 / YouTube / TMDB 图床实测可直连，**不走代理**。

   ├── BilibiliSearchProvider
   │     GET https://www.bilibili.com/        ← 预热拿 buvid3 Cookie（破 412）

## 13. v1.8.0 新增子系统

### 13.1 发现榜管道（豆瓣四分类 + Bilibili）

```
                        ┌──────────────────────────────────────┐
                        │  GET /trending/discover              │  首屏：一次并发拉全部
                        │  GET /trending/discover/{category}   │  切页签：只拉一类
                        │  GET /trending/bilibili/{partition}  │  B 站二级分区
                        │  GET /trending/discover/categories   │  页签清单（前端据此渲染）
                        └───────────────────┬──────────────────┘
                                            ▼
                              services/discover.py（编排层）
                    ┌───────────────────────┴────────────────────────┐
                    ▼                                                ▼
    providers/metadata/douban_chart.py            providers/indexer/bili_chart.py
    search_subjects?type=&tag=                    ┌── UGC：ranking/v2?rid=
    ├ movie : type=movie                          │    （全站/动画/影视/纪录片/娱乐）
    ├ tv    : type=tv & tag=国产剧                └── PGC：pgc/season/rank?season_type=
    ├ anime : type=tv & tag=日本动画                    （番剧=1 电影=2 纪录片=3
    └ show  : type=tv & tag=综艺                          国创=4 电视剧=5）
      需 Referer: movie.douban.com/explore        需先 GET 首页拿 buvid3 Cookie
      缓存 1800s / 退避 300s                       缓存 900s
                    └───────────────────────┬────────────────────────┘
                                            ▼
                              _annotate_local()：给每条榜单标注
                              「你的站点已有 N 条片源」
                              （查 resources 表，按解析后的标题匹配）
                                            ▼
                              前端 discoverBoard() / discoverTable()
                              画板（封面墙 + 角标）↔ 列表 可切
```

**为什么单独开一套端点而不改 `/trending`**：两者口径不同——`/trending`
统计的是本地资源库（有片源、有做种数、能直接下），发现榜反映的是外部热度
（可能一条片源都没有）。混在一起用户没法判断某条能不能立刻下，
而且 `/trending` 有下游依赖（榜单自动订阅规则），改它的语义等于悄悄改变
「按热度自动订阅」的行为。详见 ADR-36。

**为什么 B 站要分流两个接口**：B 站内部把内容分成 UGC（用户投稿）与 PGC
（版权番剧/影视），排行榜接口完全不同。番剧/国创属 PGC，用 `ranking/v2`
会稳定返回 `code=-400`。分流封装在 Provider 内部，服务层与前端只认
「分区」这一个概念（ADR-37）。PGC 接口的评分字段是 `"9.7分"` 字符串，需单独解析。

**降级策略**：任一分类失败只影响该分类（返回空 items + 可读 message），
不抛异常、不 500。未知分类同样返回 200 + 空列表——榜单页拿不到数据时
应当显示「暂无」而不是整页报错。

### 13.2 网盘登录管道（扫码 / Cookie 导入）

```
   POST /pan/login/qrcode {provider}
            │
            ▼
   services/pan_login.py ── PROVIDERS 能力表（后端声明 qrcode/cookie 能力位）
            │                  ├ pan115 : qrcode=True
            │                  ├ baidu  : qrcode=True
            │                  └ quark  : qrcode=False ← 前端据此不渲染扫码按钮
            ▼
   services/panlogin/{pan115,baidu,quark}.py
            │
            ├─ start()  → LoginSession（token/qr_image/qr_content/status）
            │              存入 _SESSIONS（**进程内存，不落库**，TTL 600s）
            │              二维码图走 /api/v1/images/proxy 显示
            │
            ├─ GET /pan/login/qrcode/{token} → poll()
            │      peek_session()（不回收，才能区分「过期」与「不存在」）
            │      115  : get/status/ 长轮询 status 0/1/2/-2
            │      baidu: channel/unicast 长轮询（双层 JSON）
            │      status=2/拿到票据 → _exchange() 换 Cookie
            │
            └─ POST /pan/login/complete {token}
                   status 必须为 success，否则 400
                   → apply_cookie(verify=False)  ← 扫码已证明有效，不再校验
                                                   （多一次请求更容易撞风控）
                   → 写入 SiteConfig.cookie + options.cookie
                   → drop_session()  ← Cookie 立刻从内存消失

   POST /pan/login/cookie {provider, cookie}   ← 夸克等只能走这条
            └─ apply_cookie(verify=True 恒定)
                   verify() 先校验 → 不过则**不写库**（ADR-40）
                   过则写库；无对应站点时**自动创建并启用**

   POST /pan/login/verify {provider, cookie}   ← 只校验不保存（自查用）
```

**响应体绝不含 Cookie**：`LoginSession.to_dict()` 是唯一对外序列化出口，
它不输出 `cookie` 字段。这样就不存在「某个端点不小心把凭据返回给前端」的路径，
并有专门的回归测试钉住（ADR-39）。

**为什么 Cookie 两处都写**：`SiteConfig.cookie` 列与 `options["cookie"]`。
Provider 读凭据走 `option()`，只写列会出现「填了却读不到」。

**对外接口不提供 `verify=false`**：这是本轮冒烟测试抓到的真实漏洞——
请求体带上它就能把任意字符串（实测 `x=1`）当 Cookie 写进站点记录并启用该站点，
把 ADR-40 整条绕过去。服务层保留该参数，但只给扫码流程内部调用。
