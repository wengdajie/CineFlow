## ADR-01 · 「盘搜」与「网盘存储」拆成两类 Provider

- **背景**：v1.2.0 只有 `app/providers/pan/`（pansou / pan_generic），它做的是
  「在第三方索引里找到别人分享的网盘链接」。v1.3.0 要做的是
  「把这个链接转存到我自己的网盘，并浏览我自己的网盘目录」。
  两件事都叫「网盘」，但输入输出完全不同。
- **候选方案**：
  1. 复用 `SearchProvider`，给它加 `save()` / `list_dir()` 可选方法。
  2. 新增独立抽象 `BasePanStorage`（`kind=panstorage`），与搜索器并列。
- **决定**：选 2。新增 `app/providers/panstorage/`，`ProviderKind` 增加 `PANSTORAGE`。
- **理由**：搜索器是**无状态只读**的，可以随便并发、失败就跳过；存储器是
  **有状态可写**的（会真的往盘里写文件、会删文件），生命周期、错误处理、
  权限模型都不一样。混在一个接口里会导致「搜索并发扫站时不小心触发写操作」
  这类难查的问题，也会让 `search.py` 里的打分逻辑被存储字段污染。
- **后果**：Provider 总数 18 → 21；站点表里同一个「夸克」可能出现两条记录
  （一条盘搜、一条存储），界面上用 `kind` 区分。文档需明确解释这个区别，
  见 [`06-网盘管理.md`](06-网盘管理.md) 开头。

## ADR-02 · 优先推荐 AList 网关，而不是逐个网盘直连

- **背景**：国内网盘（夸克、迅雷、115、天翼…）都没有公开 OpenAPI，
  只能抓 Web 接口 + Cookie 鉴权。每接一家就是一份易碎的逆向代码。
- **候选方案**：
  1. 逐家直连，做 5~10 个 Provider。
  2. 只接 AList（一个网关背后挂 20+ 家盘），自己不碰各家私有协议。
  3. 以 AList 为主推 + 保留 1 家直连样板（夸克）。
- **决定**：选 3。`alist` 为「推荐」，`quark` 作为直连样板，`local_dir` 作为零配置试用。
- **理由**：AList 已经在维护那些私有协议了，重复造轮子的边际收益很低，而
  维护成本（每次网盘改接口就炸）极高。但完全不做直连又无法验证抽象是否够用，
  所以保留夸克一家把 `save_share` 的完整四步流程走通，证明抽象没漏洞。
- **后果**：夸克直连**依赖 Cookie，会过期**，属于「best effort」能力，
  健康检查失败时界面提示重填 Cookie 而不是当成 bug。AList 的转存走
  `add_offline_download`，是**异步提交**，所以 `SaveResult` 的语义是
  「已提交」而非「已落盘」，文档必须写清这一点。

## ADR-03 · Webhook 入站端点不走 JWT 鉴权

- **背景**：ChatOps 需要飞书/钉钉/Telegram 主动 POST 到 CineFlow。
  这些平台**没有办法**在回调里带上我们签发的 JWT。
- **候选方案**：
  1. 要求平台带 `Authorization: Bearer <token>`（做不到，除 TG 外无法自定义头）。
  2. 在 URL 里塞一个长随机 token（`/webhook/feishu?key=xxx`）。
  3. 用各平台自己的验签机制（飞书 verification token / 钉钉 HMAC / TG secret token）。
- **决定**：选 3，`POST /api/chatops/webhook/{platform}` 明确排除在 JWT 依赖之外，
  改由 `ChatAdapter.verify()` 逐平台验签。
- **理由**：方案 2 的 token 会出现在平台后台配置、日志、浏览器历史里，
  且无法防重放。平台自带的验签机制是它们官方推荐做法，签名里含时间戳，
  能同时解决伪造与重放。
- **后果**：`app/api/deps.py` 的全局鉴权不能「一刀切」加在 router 上；
  chatops router 里只有 `/webhook/{platform}` 是匿名的，其余 7 个端点仍需登录。
  这一点在代码里有显式注释，改动时不要顺手把整个 router 包进依赖。

## ADR-04 · 未配置验签密钥时**默认拒绝**（破坏性变更）

- **背景**：适配器初版逻辑是「没配密钥 → 跳过验签 → 放行」，方便本地调试。
- **候选方案**：
  1. 保持放行（易用优先）。
  2. 默认拒绝，提供显式开关 `allow_unverified` 才放行。
- **决定**：选 2。新增 `ChatAdapter._missing_secret()`，三平台 `verify()` 统一调用它。
- **理由**：这个端点**没有 JWT 保护**（ADR-03），而它能触发**下载、删除网盘文件**。
  如果用户建了机器人却忘了填密钥，任何人扫到 `http://nas:6060/api/chatops/webhook/telegram`
  就能远程操控 NAS。「忘配 = 敞开」是不可接受的默认值；
  「忘配 = 报错」用户会立刻发现并修好。
- **后果**：**这是破坏性变更**。从更早版本升级、且未填密钥的用户会收到 401，
  响应体里给出明确原因与解决办法（填密钥，或纯内网场景显式打开
  `allow_unverified`）。已在 [`08-变更日志.md`](08-变更日志.md) 的 v1.3.0 条目标注。

## ADR-05 · 设置页做成「只读 + 指引」，而不是可编辑表单 ⚠️ 已被 ADR-18 部分取代

> **v1.5.0 更新**：本条的**结论下反了**——正确做法不是「全部只读」，
> 而是「只放开真能生效的那些」。见 [ADR-18](#adr-18--可编辑配置用白名单而不是全放开或全只读)。
> 下面的原始记录保留，因为它对**方案 2（改写 .env）**的否决理由至今仍然成立。

- **背景**：用户希望「界面上改配置」。但当前配置来自 pydantic-settings，
  读取顺序是 `环境变量 > .env > 默认值`，进程启动时快照到 `settings` 单例。
- **候选方案**：
  1. 设置页可编辑，写回 `settings` 表，运行时优先读表。
  2. 设置页可编辑，直接改写 `.env` 文件并要求重启。
  3. 设置页只读展示（分组 + 敏感项脱敏）+ 说明「在哪改、怎么生效」。
- **决定**：选 3（v1.3.0），方案 1 列入 v1.4.0 候选。
- **理由**：方案 1 要给每一个配置项引入「表值 vs 环境值」的双来源判定，
  否则会出现「界面显示 A、实际生效 B」——这比不能改更糟。
  方案 2 在 Docker 里 `.env` 常是只读挂载，且改完必须重启，体验是假的。
  当前 47 个配置项里真正需要热改的只有少数几个（调度间隔、通知开关），
  这些已经有各自的专用界面（定时任务页可改 cron、站点页可改站点）。
  与其做一个 47 项都「看起来能改」的假表单，不如老实展示 + 指路。
- **后果**：设置页有 9 个分组只读表，敏感项（含 `SECRET` / `TOKEN` / `PASSWORD`
  / `API_KEY` 字样）显示为 `******（已设置）`；页面底部有「如何修改配置」说明。
  真正可运行期修改的东西（密码、通知测试）以按钮形式放在同页账号卡。

## ADR-06 · `create_default_sites()` 改为「按 name 逐条补齐」

- **背景**：原实现是「`sites` 表非空就整体跳过 seed」。v1.3.0 新增了 3 条
  网盘存储示例站点，老库升级后**永远看不到**它们，用户只能手动照文档抄配置。
- **候选方案**：
  1. 保持不动，靠文档让用户手建。
  2. 加版本号字段做数据迁移脚本。
  3. 按 `name` 逐条 upsert：缺哪条补哪条，已存在的**绝不覆盖**。
- **决定**：选 3。
- **理由**：方案 2 对一个单文件 SQLite 的示例数据来说太重。方案 3 的关键是
  「只增不改」——用户改过的站点（改了 URL、填了 Cookie、启用了）不会被 seed 覆盖，
  因为判定条件是 name 存在即跳过。实测老库升级补入了 5 条缺失示例。
- **后果**：`DEFAULT_SITES` 从 8 条增至 11 条，全部 `enabled: False`
  （示例站点默认不启用，避免升级后突然去请求陌生站点）。
  以后新增示例站点只需往 `DEFAULT_SITES` 追加，老用户下次启动即可见。

## ADR-07 · 热度排行折叠 `unknown` 类型

- **背景**：热度榜按「资源类型」分 tab。但很多站点返回的条目
  无法可靠判定是电影还是剧集（标题里既没有 SxxExx 也没有年份线索）。
- **候选方案**：
  1. 猜一个（默认归到电影）。
  2. 单独开一个 `unknown` tab 展示。
  3. 不给 `unknown` 单开 tab，把它折叠进「全部」，仅在明细里标注。
- **决定**：选 3。
- **理由**：方案 1 会污染「电影榜」的可信度——用户看到榜单里混进剧集会怀疑
  整个功能。方案 2 会出现一个用户完全不理解、且经常是最长的 tab。
  折叠进「全部」保证任何条目都不丢，同时每个类型 tab 里的东西都是可信的。
- **后果**：各 tab 计数之和可能小于「全部」的计数，这是预期行为而非 bug。

## ADR-08 · 前端坚持零依赖（无 CDN / 无构建）

- **背景**：目标运行环境是 NAS，常见于**无外网或外网很慢的内网**。
- **候选方案**：Vue/React + 构建产物；或 CDN 引入轻量库；或原生 JS + CSS。
- **决定**：原生 JS（`web/assets/app.js`）+ 原生 CSS（`style.css`），
  单页 hash 路由，14 个页面全部手写渲染函数。
- **理由**：CDN 在内网直接白屏；引入构建工具会让「clone 下来就能跑」变成
  「先装 node、再装依赖、再 build」。NAS 用户的耐心通常止于第一步。
- **后果**：`app.js` 已 3661 行，靠 `PAGES` / `ROUTES` 表 + 每页一个
  `pageXxx()` 函数保持可读。**新增页面必须同时更新 `PAGES`、`ROUTES`
  和 `scripts/ui_check.py` 的页面清单**，否则点检覆盖不到。
  UI 回归完全依赖 `ui_check.py` 的程序化断言（真浏览器 + 捕获 JS 报错）。

## ADR-09 · 转存失败不阻塞下载流程，改由队列重试

- **背景**：`download.add_download()` 遇到网盘资源时要转存。
  转存可能因 Cookie 过期、容量不足、分享失效而失败。
- **候选方案**：
  1. 转存失败 → 整个 `add_download` 返回失败。
  2. 转存失败 → 任务留在 `pending`，由 `pan_transfer` 定时任务重试。
- **决定**：选 2。新增内置任务 `cineflow.pan_transfer`
  （interval，`CF_PAN_TRANSFER_INTERVAL_MINUTES`，默认 20 分钟）。
- **理由**：订阅巡检是自动跑的，没人在旁边看返回值。失败即丢会导致
  「明明搜到了却什么都没发生」。留在队列里可以在用户重填 Cookie 后自动补救，
  界面上也能看到「待转存 N 条」这个明确信号。
- **后果**：内置定时任务从 4 个增至 5 个，顺序为
  `subscribe → radar → download → pan_transfer → library`。
  网盘管理页提供「一键全部转存」手动触发同一入口，行为与定时任务完全一致
  （同一个 `pan_storage.transfer_pending()`），不存在两套逻辑。

## ADR-10 · 依赖方向单向：`core ← providers ← services ← api`

- **背景**：服务之间存在真实的相互需要（chatops 要调 search/download/subscribe/pan，
  pan 要调 notify，download 要调 pan）。
- **决定**：分层严格单向；**services 之间的互相调用一律写在函数内部延迟 import**。
- **理由**：模块级交叉 import 在这种拓扑下必然出现循环导入，
  且报错信息极难定位（表现为「某个属性不存在」）。
  延迟 import 的代价是每次调用一次字典查找，可忽略。
- **后果**：看到函数体里出现 `from app.services import xxx` 不是笔误，
  是刻意的。新增跨服务调用时请沿用此写法，`core/` 内不得有任何 IO。

## ADR-11 · NFO 拆成 `core/nfo.py`（渲染）+ `services/scraper.py`（IO）

- **背景**：刮削 = 「取元数据」+「拼 XML」+「写盘/下图」。三件事混在一起写最省事。
- **候选方案**：
  1. 一个 `services/scraper.py` 全包（取数据、拼 XML、写盘）。
  2. 拆成 `core/nfo.py` 纯渲染 + `services/scraper.py` 负责 IO。
- **决定**：选 2。
- **理由**：NFO 的字段与格式是**最容易出错也最需要反复调**的部分
  （不同媒体服务器对标签容忍度不同）。放进 `core/` 后可以完全离线单测，
  一条断言就能验证「季号补零」「演职员顺序」这类细节，
  不必起数据库、不必 mock TMDB。这也是 ADR-10 分层铁律的直接应用。
- **后果**：`test_nfo.py` 8 例全部不触网不落库；
  `core/nfo.py` 内**禁止**出现 `httpx` 与 `async def`（`verify_docs.py` 硬校验）。

## ADR-12 · TMDB 不可用时写「最小 NFO」而不是不写

- **背景**：用户不配 TMDB API Key 是常态（申请麻烦、内网不通）。
- **候选方案**：
  1. 拿不到 TMDB 数据就不写 NFO，交给媒体服务器自己刮。
  2. 用本地 `meta` 解析结果（标题/年份/季集）写一份最小 NFO，标记 `degraded`。
- **决定**：选 2。
- **理由**：媒体服务器"自己猜"在国产剧、冷门片上错误率很高，
  一旦猜错还会把错误元数据缓存起来，用户得手工改。
  一份**不完整但正确**的 NFO（片名、年份、季集号）足以让它别猜错，
  而这些信息本地解析引擎已经有了，白扔掉可惜。
- **后果**：NFO 里带 `degraded` 标记，将来配好 TMDB 后可用
  `CF_SCRAPE_OVERWRITE=true` 跑一次补刮覆盖。

## ADR-13 · 分类判不出来就不归档；分类归档默认关闭

- **背景**：`CF_CATEGORY_ENABLED` 会在媒体库下插入一级目录
  （电影/电视剧/动漫/纪录片/综艺/儿童）。
- **候选方案**：
  1. 判不出时归到「其他」目录。
  2. 判不出时返回 `None`，原样入库不加分类目录；且整个能力默认关闭。
- **决定**：选 2。
- **理由**：归错目录的代价远大于不归档——用户要手工把文件搬回来，
  而搬动已入库文件会打断硬链、让媒体服务器重新识别。
  「其他」目录同样是错的：它会随时间变成垃圾堆。
  默认关闭同理：对已经有几 TB 媒体库的用户，中途改布局是破坏性的。
- **后果**：`categories.detect()` 明确可返回 `None`；
  `verify_docs.py` 校验 `settings.CATEGORY_ENABLED is False`。

## ADR-14 · STRM 默认写 `proxy` 302 端点，而不是网盘临时直链

- **背景**：`.strm` 文件里存一个 URL，媒体服务器播放时直接请求它。
  网盘给的直链通常几十分钟到几小时就过期。
- **候选方案**：
  1. `direct`：写网盘当次返回的临时直链。NAS 完全零参与。
  2. `proxy`：写 `/api/v1/strm/play/{id}`，播放时现取直链并 302 跳转。
  3. 真代理：CineFlow 把视频流转发给播放器。
- **决定**：默认 **2**，保留 1 作为可选项，**明确否决 3**。
- **理由**：`.strm` 一旦被媒体库扫进去，可能几个月都不会重扫，
  写一个会过期的链接等于埋雷——表现为"以前能播的剧突然点不开"。
  方案 2 的链接永不过期，且**只回 302 不代理流量**，NAS 带宽与 CPU 不参与，
  代价仅是播放时多一次 HTTP 跳转。方案 3 会让 NAS 变成流量瓶颈，
  且要处理 Range 请求、断点续播等一堆细节，收益不匹配。
- **后果**：`GET /api/v1/strm/play/{id}` **必须匿名**——播放器没法带 JWT
  （与 ADR-03 同一类问题）。风险控制上，该端点只做跳转、不列举内容、
  不返回文件本体，且 record_id 不可枚举出媒体库结构。

## ADR-15 · 洗版默认关闭，且「先入库、后删旧」

- **背景**：洗版会**删除已入库文件**，是本项目唯一有破坏性的自动动作。
- **决定**：
  1. `CF_UPGRADE_ENABLED` 默认 `false`，且仅对勾选 `best_version` 的订阅生效；
  2. 评分差需 ≥ `CF_UPGRADE_SCORE_DELTA`（15），每文件最多 `CF_UPGRADE_MAX_TIMES`（2）次；
  3. 删旧文件的时机放在**新文件确实入库成功之后**（`library.replace_library_file`）。
- **理由**：
  - 单靠"分数更高就换"会在几个同档版本（不同压制组的 1080p）之间反复横跳，
    每次横跳都是一次下载 + 一次删除，既费流量又危险，所以要阈值 + 次数上限双闸。
  - 若先删旧再下新，下载失败/中断就会在媒体库留下一个空洞，
    用户当晚就发现"这集没了"。反序则最坏情况只是磁盘上多占一份。
- **后果**：订阅页提供**洗版试算**（`upgradeReport`），只报告
  「哪个文件会被什么替换、分差多少」，不执行任何删除，供用户开启前评估。

## ADR-16 · 分享追更用「已转存文件名」做增量，而不是记时间戳

- **背景**：追更一个网盘分享链接，每轮要判断"哪些是新增的"。
- **候选方案**：
  1. 记上次巡检时间，只处理更晚的文件。
  2. 记已转存过的**文件名集合**（`saved_files`），做差集。
- **决定**：选 2。
- **理由**：分享里的文件时间戳不可靠——分享者补档、重传、改名都会让时间跳变，
  而 CineFlow 也不总能拿到可信的修改时间（`list_share` 各家字段不一）。
  文件名是唯一稳定可比的东西，且天然实现"补档不会被重复搬"。
- **后果**：
  - 网盘**不支持** `list_share`（只能整体转存）时无法做差集，
    于是写入哨兵 `__whole_share__` 表示"已整体转存过"，避免每轮重复搬整个分享。
  - 用户填的过滤正则若非法，`_compile()` 捕获 `re.error` 后按"没填"处理——
    一个人填错正则不该让整轮巡检崩掉。
  - 连续失败到 `CF_PAN_SUBSCRIBE_MAX_FAILURES` 标记 `invalid` 停手：
    死链无限重试只会刷日志和触发网盘风控。

## ADR-17 · 老库升级用 `ALTER TABLE` 补列，不引入 Alembic

- **背景**：v1.4.0 给 `library_files` 增加了 `quality_score` / `upgrade_count`。
  `Base.metadata.create_all()` **只建新表，不给已有表加列**，
  老库升级后 `/system/dashboard`、`/library/files` 与两个插件直接 500（已实测复现）。
- **候选方案**：
  1. 引入 Alembic，正式做迁移版本管理。
  2. 启动时执行一个表驱动的幂等 `ALTER TABLE ADD COLUMN` 清单。
  3. 要求用户删库重建。
- **决定**：选 2（`init_db.migrate_columns()` + `_ADDED_COLUMNS` 清单）。
- **理由**：
  - 方案 3 不可接受：媒体库索引、订阅、下载记录都会丢。
  - 方案 1 的成本不在代码而在**部署形态**：会引入 `migrations/` 目录、
    版本表与"忘记生成迁移脚本"这一类新故障，与本项目
    「一个 SQLite 文件即全部状态、Docker 起来就能用」的定位冲突。
  - SQLite 的 `ADD COLUMN` 是廉价操作，且新增列一律**可空或有默认值**，
    所以补列本身不会失败；即使失败也只 `warning` 不阻塞启动
    （宁可某个新功能不可用，也不能让整个服务起不来）。
- **后果**：**今后新增列必须同时登记进 `_ADDED_COLUMNS`**，
  且只允许"可空/带默认值"的新列；需要改列类型或删列时，
  本 ADR 失效，届时应重新评估方案 1。已补老库升级的接口用例防回归。

## ADR-18 · 可编辑配置用**白名单**，而不是全放开或全只读

- **背景**：ADR-05 把设置页做成只读，理由是「显示与生效不一致比不能改更糟」。
  这个顾虑是对的，但推出的结论错了：用户想调一个搜索超时就得 SSH 改 `.env` 再重启，
  在 NAS 上体验很差，而且 62 项里确实有一大半是**运行期每次读取**的。
- **候选方案**：
  1. 维持只读（ADR-05）。
  2. 全部可编辑，写回 `settings` 表，运行时优先读表。
  3. **白名单**：只有「运行期读取即生效」的键可编辑，其余保留只读并标「需重启」。
- **决定**：选 3。`config_store.EDITABLE` 收 51 项；`DATA_DIR` / `PORT` /
  `SECRET_KEY` / `DB_URL` / `HOST` 等**明确排除**。
- **理由**：
  - 方案 2 会造出真正的假功能：改了 `PORT` 界面显示 6061，服务还在 6060 上听。
    这正是 ADR-05 当初担心的情况——但答案是**筛掉这些键**，不是连能改的一起锁死。
  - 判定标准很清楚：**代码里是在请求/任务里读 `settings.X`，还是在启动时读一次？**
    前者可编辑，后者不可。这个标准是可机械校验的，`verify_docs.py` 里有对应断言。
  - 生效方式选 `object.__setattr__` 写回 settings 单例，而不是让每个读取点改成
    「先查表再退默认」——后者要改上百处调用，且漏一处就是一个隐蔽的不一致。
    值在 `coerce()` 里已经校验过，绕过 pydantic 校验直接赋值是安全的。
- **后果**：**今后新增配置项时要顺手判断能否进白名单**；进了白名单的键，
  其读取点必须是运行期读取。`EDITABLE` 数量变化会被 `verify_docs.py` 拦住，
  强制更新文档。不可热改项在界面上标「需重启」，用户预期明确。

## ADR-19 · 只做三档角色，不做细粒度 ACL

- **背景**：v1.4.0 只有单个管理员账号。要给家人开账号，就得共享全权限密码。
- **候选方案**：
  1. 资源级 ACL（每个端点/每个资源配读写权限）。
  2. 角色 + 权限点（RBAC，角色绑定一组 permission）。
  3. 三档固定角色：`admin` / `operator` / `viewer`，按 `rank` 比较。
- **决定**：选 3。`UserRole` 带 `rank`（viewer 1 < operator 2 < admin 3），
  依赖只做 `role_of(user).rank >= minimum.rank` 这一个比较。
- **理由**：
  - 家用 NAS 的真实需求就三种人：**管事的、能点下载的、只想看进度的**。
    方案 1/2 会引入权限管理界面、权限点命名规范与「为什么我点不了」的排查成本，
    收益却接近零。
  - `is_superuser` 布尔位**保留并由 role 推导**，而不是删掉：旧代码、旧 JWT、
    `X-API-Token` 取管理员的逻辑都还在读它，推导能保证两者永远一致。
  - 鉴权**读数据库角色而不是 JWT 里的 role 副本**：JWT 是签发时的快照，
    如果信它，改完某人角色要等他旧令牌过期才生效——降权场景下这是安全问题。
    JWT 里仍带 role，但只供前端决定隐藏哪些按钮。
  - 老库补 `role` 列默认 `'admin'`（而不是 `'viewer'`）：老库里唯一的那个用户
    就是管理员，补成 viewer 会把他锁在系统外。启动时 `sync_user_roles()`
    再按 `is_superuser` 对齐一次，纠正多用户老库的情况。
- **后果**：前端隐藏入口只是体验，**服务端每个写端点都挂了角色依赖**——
  界面隐藏不能当安全边界。两条自我保护（不能删/停自己、最后一个启用中的管理员
  不能降级或停用）必须保留，否则会出现没人能登录的死局。
  今后新增写端点必须显式选 `OperatorUser` 或 `AdminUser`，不能只用 `CurrentUser`。

## ADR-20 · 站点健康探测对搜索类站点**真搜一次**，0 结果判「降级」

- **背景**：原有 `health_check` 探站点首页。但站点最常见也最难发现的故障是
  **Cookie 过期**——首页照样 200，只有搜索结果变成 0 条。用户的体感是
  「最近怎么没更新」，完全查不到原因。
- **候选方案**：
  1. 只探首页（现状），快且轻。
  2. 探首页 + 检查响应里有没有登录态特征（如用户名、退出链接）。
  3. 对搜索类站点**真的发一次搜索**，用结果条数判定。
- **决定**：选 3。用固定关键词 `"的"`（中文站几乎必有命中），三档判定：
  `ok` 有结果 / `degraded` 能连通但 0 结果或极慢 / `down` 连不通或报错。
- **理由**：
  - 方案 1 对目标故障完全无感，等于没做。
  - 方案 2 依赖每个站点的页面特征，等于给每站写一条脆弱的正则——
    改版就失效，且对 API 型站点（torznab/JSON）不适用。
  - 方案 3 用的是**站点真正被使用的那条路径**：搜索能出结果，就是真的可用。
    代价是每次探测产生一次真实搜索请求，所以默认周期设 180 分钟（不是几分钟）。
  - **0 结果算 `degraded` 而不是 `ok`** 是本条的核心：它可能是关键词恰好没命中，
    但更可能是 Cookie 过期。标成「亚健康」让用户去看一眼，比标成正常然后
    静默不更新要好得多。
- **后果**：探测有真实成本，周期不能调太密（配置项有下限保护）。
  `degraded` 会有一定误报率（比如站点确实没有含「的」的资源），
  所以**只在连续失败达阈值时才告警**，且只在**状态翻转**时通知——不刷屏。
  用户手点「立即巡检」时 `notify=False`：他正看着屏幕，不需要再推一条。

## ADR-21 · 不健康的下载器**排到最后**，而不是从候选里剔除

- **背景**：多下载器时要避开挂掉的那个。手上有 `site_health` 的健康数据。
- **候选方案**：
  1. 把 `down` / `degraded` 的下载器从候选列表里**剔除**。
  2. 把它们**排到最后**，仍可作为兜底。
- **决定**：选 2。
- **理由**：健康数据**天生是过期的**——它来自上一次巡检（默认 180 分钟前）。
  下载器刚重启完、网络刚恢复，健康表里还写着 `down`。此时方案 1 会导致
  「明明能用却不投递」，在只有一个下载器且它被标 `down` 时更是直接**停摆**。
  方案 2 既避开了坏的（正常情况下永远轮不到它），又保留了兜底路径；
  真的投递失败还有 failover 接着换下一个，两层保护足够。
- **后果**：极端情况下会向一个确实挂掉的下载器投递一次并失败，
  这个代价可接受（一次失败 + 自动换源），远小于「无法下载」。
  健康数据取不到时（比如表还没建好）直接退回策略排序，不抛异常。

## ADR-22 · 过滤规则组用**有序分层**，而不是继续加评分权重

- **背景**：用户要「宁可 1080p 中字，也不要没字幕的 4K」。现有能力是
  `filters.score_resource` 的加权打分（4K +N、中字 +30…）。
- **候选方案**：
  1. 继续调权重：把「中字」的分值调到比「4K vs 1080p 的差值」更大。
  2. 引入**有序层级**：命中靠前层的资源整体优于靠后层，层内再按原评分排序。
- **决定**：选 2（`core/rules.py`），排序键 `(rule_level, -score)`。
- **理由**：
  - 方案 1 只能表达**单调偏好**。一旦有两条以上的交叉偏好（画质、字幕、体积、
    做种数），权重之间会互相"打架"：把中字调高到能压过 4K，就会连带压过
    「REMUX vs WEBRip」这些本不该被压过的差异。调权重是在用一维数值
    去编码多维偏好，本质上做不到。
  - 方案 2 把「哪些条件组合更重要」显式表达成顺序，用户看得懂、改得动，
    而且**层内仍然复用既有评分** → 不丢细粒度排序能力，也不推翻已有实现。
  - 层级条件全部**可留空 = 不限制**：否则用户被迫填满 10 个字段才能建一层。
- **后果**：
  - 规则组会**改变搜索结果排序**，所以内置 4 个模板**全部 `is_default=False`**：
    升级后悄悄换掉用户熟悉的排序是很糟糕的体验，让他自己去点「设为默认」。
  - `accept_unmatched=False` 时未命中资源会被**剔除**（宁可不下也不要不合规的），
    这是有意提供的严格模式，界面上必须说清楚。
  - 删除规则组时把引用它的订阅**解绑**而不是禁止删除：残留一个指向不存在组的
    `rule_group_id` 会让订阅静默失去过滤能力，比报错更糟。
  - `core/rules.py` 保持**纯函数无 IO**（同 ADR-10/ADR-11），`meta_of` 由调用方注入。

## ADR-23 · 榜单自动订阅必须有**单次上限**，并记录已处理条目

- **背景**：热度排行只能看，用户要「让高分新剧自动变成订阅」。
- **候选方案**：
  1. 每次巡检把榜单里所有符合条件的都加成订阅。
  2. 单次有上限，且记录已处理过的条目 ID。
- **决定**：选 2。`RANKING_MAX_PER_RUN` 默认 5；`handled_ids` 记录已处理
  （截断 500 条）。
- **理由**：
  - 无上限的第一次执行就能刷进上百个订阅，每个订阅又会去所有站点搜索、
    投递下载——直接把下载器和磁盘打满。这类"自动化"一旦失控，
    用户的第一反应是卸载。
  - **不记 `handled_ids` 会有更隐蔽的问题**：用户手动删掉一个不想要的订阅，
    下次巡检又给他加回来。用户会觉得"这东西有毒"。所以判重要基于
    「**我处理过它**」而不是「订阅表里还在不在」。
  - `handled_ids` 截断 500 条：无限增长会让这一行 JSON 越来越大。
    500 条足够覆盖任何榜单的翻滚窗口。
- **后果**：首次配好规则后需要跑几轮才会把榜单里的存量补齐，
  这是有意的节流。提供 `dry_run` 让用户先看会建哪些订阅再真跑。
  「重新处理某条」目前没有界面入口，需要时可删规则重建（`handled_ids` 随规则走）。

## ADR-24 · yt-dlp 只下**公开内容**，正片播放页在入口拒绝

- **背景**：用户要求「集成 B 站 / YouTube / 抖音 / TikTok 下载」，
  同时要求「适配优酷 / 腾讯 / 爱奇艺 / 芒果 TV 的资源解析」。
- **候选方案**：
  1. 全部接入，包括长视频平台的正片解析（市面上有大量"VIP 解析"接口）
  2. 只接公开内容，长视频平台正片播放页直接拒绝
  3. 完全不做网页视频下载
- **决定**：**方案 2**。用 yt-dlp 覆盖公开内容；对
  `v.qq.com/x/(cover|page)/`、`iqiyi.com/v_`、`youku.com/v_show/`、`mgtv.com/b/`
  以及 Netflix / Disney+ / Hulu / HBO / Prime Video，在 `probe()` 与 `add()`
  的**入口**就拒绝，并返回可读中文原因，建议改用平台官方客户端的离线缓存。
- **理由**：
  - 长视频平台的正片**基本都在会员墙或区域授权之后**。抓取它等于绕过付费墙，
    这不是"技术难不难"的问题，而是产品该不该做的问题。所谓"VIP 解析"接口
    本身也依赖盗取的会员票据，接进来等于把项目和灰产绑在一起。
  - 选 yt-dlp 而不是自己写各站解析：它是该领域事实标准，抽取器覆盖 1700+ 站点、
    维护活跃。自研解析器会在每次站点改版后集体失效，是长期负债。
  - **按 URL 路径特征拒绝，而不是封整个域名**：这些平台也有公开的预告、
    UP 主自制内容和官方免费片。一刀切封域名会误伤合法用途。
- **后果**：用户要下 VIP 正片会被明确拒绝。我们不把"做不到"伪装成"技术故障"，
  而是直接说明原因并给替代路径。需要登录才能看的内容，只支持用户提供**自己账号**
  的 cookie 去下载其**有权访问**的部分。

## ADR-25 · 搜索的多站公平性靠**轮转交错**，不靠砍单站配额

- **背景**：用户报「站点都启用了，结果里却只有 PanSou 的资源」。
  实测每个站点单独直连都正常（PanSou 214 条 / Mukaku 90 条），
  问题出在聚合层：`dedupe(collected)[:400]` 只做全局截断，
  返回量大的站把小站**挤出了结果窗口**；且单站失败被 `except: continue` 静默吞掉。
- **候选方案**：
  1. 给每个站点设一个小配额（如每站 40 条）后再合并
  2. 保留全局上限，但合并时按站点**轮转交错**（A1,B1,A2,B2…）
  3. 只扩大全局上限
- **决定**：**方案 2**。另加 `SEARCH_MAX_PER_SITE`（默认 300）作为**安全阀**，
  以及每站诊断结构 `SiteOutcome`（`ok|empty|timeout|error` + 原始/保留条数 + 原因 + 耗时）。
- **理由**：
  - 我第一次实现时选了方案 1（每站 40 条），结果总数从 145 掉到 80 ——
    **把"公平性"和"砍量"混为一谈了**。公平性要解决的是"谁能进结果窗口"，
    答案是改变**合并次序**，而不是丢弃数据。修正后总数 145 → 200，
    Mukaku 从 25 → 80 条。
  - `SEARCH_MAX_PER_SITE` 保留为安全阀（防单站返回几万条打爆内存），
    默认给到 300 这种"正常情况下碰不到"的值，避免它悄悄变成公平性旋钮。
  - **静默失败比失败更糟**：用户看到"只有一个站有结果"却无法得知原因。
    实测 Jackett 返回 502（本机未部署）、Nyaa 返回 0 条（只收日番，
    中文剧名搜不到）——这两条信息一旦暴露在界面上，用户立刻知道该怎么办。
- **后果**：搜索响应体增加 `sites[]` 字段。`search()` 的签名保持不变
  （老调用点零改动），需要诊断的场景改调 `search_detailed()`。

## ADR-26 · 榜单封面/评分取自**站点自带元数据**，不强依赖 TMDB

- **背景**：热榜要改成画板（封面卡片墙）。本机 `TMDB_API_KEY` 为空，
  而绝大多数自部署用户也不会去申请。
- **候选方案**：
  1. 强依赖 TMDB，没配就不显示封面（画板退化成列表）
  2. 用站点搜索接口**自带**的元数据（Mukaku 返回 `image` / `doub_score` /
     `years` / `class` / `episodes` / `performer` 等），取不到则占位
  3. 内置一个第三方图片代理服务
- **决定**：**方案 2**。在 `generic_api` 里定义 `DEFAULT_MEDIA_MAP`
  （可用站点 `options.media_map` 覆盖），把作品级元数据合并进资源 `extra`，
  经搜索落库到 `ResourceRecord.meta`（已有 JSON 列，**无需迁移**），
  再由 `trending` 聚合成榜单字段。
- **理由**：
  - 站点搜索结果里**本来就带**封面和豆瓣评分，多打一次 TMDB 请求属于重复劳动，
    还会因为片名翻译差异匹配错作品。
  - "没配 API Key 就没图"会让首屏体验直接崩掉，而这恰恰是绝大多数用户的默认状态。
  - **映射表而非硬编码字段名**：Mukaku 用 `image`/`doub_score`，别的站叫别的名字。
    做成可覆盖的映射，接新站时改配置即可，不用改代码。
  - 评分为 `0`/空/"暂无"时**不输出**该字段：把"没有数据"渲染成"0 分"
    是在制造错误信息。同理，非 `http(s)` 的封面地址直接丢弃。
- **后果**：纯盘搜类站点（PanSou）不返回元数据，其条目显示占位色块——
  这是预期行为而非缺陷。占位按标题哈希取稳定色相，同一部作品每次进页面颜色一致。
  历史入库的资源会在下次搜索命中时**回填**元数据（首版实现里
  `if key in existing: continue` 导致老记录永远拿不到封面，已修正为回填空字段）。

## ADR-27 · 异步页面渲染必须校验「这一屏属于谁」

- **背景**：UI 点检发现地址栏是 `#settings`、页面内容却是站点健康页，
  且后续所有点击都作用在这个"幽灵页面"上。
- **根因**：每个页面函数都是「先画 `loading()`，`await` 拉数据，再画真内容」。
  站点健康的「立即巡检」要真去各站点搜一次（十几秒），期间用户切走后，
  旧请求返回时仍然无条件 `replaceChildren`，覆盖了新页面。
- **候选方案**：
  1. 给每个页面函数手工加"我还是当前页吗"的判断
  2. 在 `shell()` 这个**唯一的 DOM 写入口**集中校验
  3. 引入 `AbortController` 取消在途请求
- **决定**：**方案 2**。建立 `页面标题 → 页面 key` 映射，`shell()` 写 DOM 前
  比对 `store.page`，不匹配直接 `return` 丢弃这次渲染。
- **理由**：
  - 41 处 `shell()` 调用散落在 20 个页面函数里，方案 1 需要改 41 个地方，
    且以后每加一个页面都可能漏掉——**这类约束必须由基础设施保证，不能靠自觉**。
  - 判据用**标题**而不是自增计数器：异步回调无法知道自己属于哪一次导航，
    但它清楚自己正在画哪个页面。
  - 方案 3 更彻底但改动面大得多（每个 `api()` 调用都要接 signal），
    而且拿不到"取消"能力的第三方渲染路径依然会漏。留待后续。
  - 「出错了」那一屏没有对应页面标题，单独用导航代次 `navEpoch` 判断。
- **后果**：慢请求返回后其结果被丢弃（不会渲染），用户需要切回该页重新触发。
  这比看到错乱的页面要好。已在 `scripts/ui_check.py` 加回归用例：
  **必须用应用内导航（点侧边栏）复现**，`page.goto` 会整页刷新、
  连带丢弃在途请求，测不出这个 bug —— 实测关掉守卫时点侧边栏 6.4 秒即被抢屏。

## ADR-28 · 网盘能力由后端**能力位**声明，前端按位渲染；基类默认降级不抛异常

- **背景**：用户要求「参考 T3FAP 优化网盘方案：登录 / 保活 / 文件管理」。
  四个存储后端（夸克 / AList / WebDAV / 本地目录）能力差异很大：
  WebDAV 协议根本没有搜索语义，本地目录没有"保活"概念。
- **候选方案**：
  1. 前端按 `provider` 类型硬编码显示哪些按钮
  2. 后端 `capabilities()` 下发能力位，前端按位渲染
  3. 全部按钮都显示，不支持的操作点了报错
- **决定**：**方案 2**。基类提供 `supports_rename / move / search / keepalive`
  与 `capabilities()`，`GET /api/v1/pan` 随总览一起下发；
  且 5 个新方法在**基类里都有默认实现，返回 False/空而不抛 `NotImplementedError`**。
- **理由**：
  - 方案 1 会把后端能力矩阵复制到前端，**新增一个网盘要改两处**且必然漂移。
    方案 2 下新增网盘时前端零改动。
  - 方案 3 最省事但最糟：让用户点一个注定失败的按钮，是把实现细节的代价转嫁给用户。
    **不支持的操作根本不渲染**，比渲染了再报错诚实。
  - 默认实现不抛异常，是因为第三方/自建 Provider 不该因为没实现新方法就在
    `overview()` 里炸掉整个网盘页——降级成"这个盘不支持搜索"是可接受的，白屏不是。
- **后果**：新增能力时要同时改基类能力位、具体后端、以及前端的按钮映射三处；
  作为约束，`verify_docs` 断言基类不得抛 `NotImplementedError`。
  同一原则也用在搜索结果的 `Resource.actions`（M23）上。

## ADR-29 · 封面用**多级回退链**，豆瓣排在 TMDB 之前

- **背景**：v1.6.0 的封面只取站点自带元数据（ADR-26），
  但 PanSou 这类纯盘搜站根本不返回元数据，画板里大面积是占位色块。
  用户要求「资源封面提供更优方案，可以对接豆瓣」。
- **决定**：建立回退链 **站点自带 → 豆瓣 → TMDB（需 Key）→ 占位色块**，
  逐级尝试，任一级拿到就停。
- **理由**：
  - 站点自带排第一：零额外请求，且与资源本身同源，不会配错作品。
  - **豆瓣排在 TMDB 之前**：`subject_suggest` 免 API Key
    （绝大多数自部署用户不会去申请 TMDB Key），且对中文影视命中率明显更高。
  - TMDB 保留在链上：有 Key 的用户能拿到更规范的多语言元数据。
  - 占位色块必须保留在链尾：**任何一级都可能失败，UI 不能因此破版**。
- **约束**：只补前 24 条、并发 8。补图是"锦上添花"，
  不能让榜单响应时间取决于第三方站点的健康度。
- **后果**：豆瓣有反爬 → 缓存 6h + 命中限流退避 300s；
  同名作品可能配错封面（`subject_suggest` 是标题模糊匹配），
  已列入 v1.8.0 候选（加年份/类型二次校验）。

## ADR-30 · 豆瓣图床走**后端图片代理**，并用三道防线挡 SSRF

- **背景**：豆瓣封面地址直接放进 `<img src>` 后返回 **418**。
  排查发现不是限流也不是封 IP：**裸请求 418，带
  `Referer: https://movie.douban.com/` 返 200**（实测 25069 字节）。
- **候选方案**：
  1. 前端加 `referrerpolicy` / `<meta referrer>` 让浏览器带上 Referer
  2. 后端加图片代理端点，由服务端补 Referer 后转发
  3. 把封面下载到本地磁盘再由自己提供
- **决定**：**方案 2**，新增 `app/api/routers/images.py`。
- **理由**：
  - 方案 1 **在原理上行不通**：跨站请求时浏览器只会发送同源或降级后的 Referer，
    页面无法伪造成 `movie.douban.com`。这一点值得记录，否则下次还会有人尝试。
  - 方案 3 要引入磁盘配额、清理策略与缓存失效，为"封面"这件事过重。
  - **B 站 / YouTube / TMDB 图床实测可直连**，所以代理只对需要的域名生效，
    不做全局图片中转，避免把自己变成流量瓶颈。
- **SSRF 三道防线**（代理任意 URL 是典型的 SSRF 面）：
  1. **域名白名单**，比较方式必须是 `host == suffix or host.endswith("." + suffix)`
     —— 用 `host.endswith(suffix)` 会被 `doubanio.com.attacker.net` 绕过；
  2. 只允许 `http` / `https`（挡掉 `file://`、`gopher://` 等）；
  3. 响应 `content-type` 必须是 `image/*`，并有 `MAX_BYTES` 上限。
- **刻意不挂登录校验**：`<img>` 标签带不了 `Authorization` 头。
  安全性由白名单而非鉴权保证；**往白名单加域名前必须确认它不指向内网**。

## ADR-31 · B 站搜索先**预热首页拿 Cookie** 破 412

- **背景**：`api.bilibili.com/x/web-interface/search/type` 对不带 `buvid3`
  Cookie 的请求返回 **412 Precondition Failed**（风控）。
  yt-dlp 自带的 `bilisearch:` 同样栽在这里，所以不能靠上游解决。
- **决定**：搜索前**先 GET 一次 `https://www.bilibili.com/`**，
  用同一个 session 承接下发的 Cookie，再调搜索接口。
- **理由**：412 是缺少"正常浏览器访问过首页"的证据，而不是要求登录。
  预热是最小代价的合规做法——**不伪造登录票据、不绕过任何付费墙**，
  只是让请求看起来像它实际的样子（一个浏览器在搜公开内容）。
- **后果**：每个搜索会话多一次首页请求（Cookie 在 session 内复用）。
  若 B 站将来改成必须登录，这个方案会失效，届时应当**报错而不是伪造凭据**。

## ADR-32 · 网页视频的播放量**投影到 `seeders`**，而不给榜单加特例

- **背景**：M24 把 B 站 / YouTube 结果并入聚合搜索后，
  这些资源没有做种数，但有播放量；热度排序与榜单聚合都是按 `seeders` 计算的。
- **候选方案**：
  1. 给 `Resource` 加 `views` 字段，并在排序/榜单/前端逐处加 `WEBVIDEO` 分支
  2. 把播放量归一化后写入既有 `seeders` 字段
- **决定**：**方案 2**。
- **理由**：两者语义一致——都是「有多少人正在消费这个资源」，
  也都只用于**相对排序**而非绝对展示。方案 1 会在排序、榜单聚合、
  前端渲染三处各加一个 `if`，而这类分支一旦开始加就会不断增殖。
- **后果**：UI 上网页视频的"做种数"实际是播放量量级，可能远大于 BT 资源。
  因为只参与相对排序，不影响正确性；若将来要区分展示，再引入独立字段。

## ADR-33 · 网盘凭据用**定时轻量探活**，而不是等任务失败

- **背景**：网盘 Cookie / token 会静默过期。原先的表现是**半夜的转存任务失败了才发现**，
  且失败原因混在日志里难以归因。
- **决定**：新增「网盘凭据保活」定时任务（`JOB_PAN_KEEPALIVE`，默认 **6 小时**，
  `PAN_KEEPALIVE_INTERVAL_MINUTES` 可在线改），逐个存储调一次轻量接口。
- **理由**：
  - 一次轻量调用同时达成两件事：**刷新登录态**（多数网盘会滑动续期）与
    **提前告警**（失效时立刻通知，而不是等到需要转存时）。
  - 6 小时是权衡：远短于常见 Cookie 有效期，又不至于频繁到被当成异常流量。
  - **不做自动重新登录**：各网盘登录流程差异极大且多带验证码/短信，
    自动化不可靠；能续期的续期，不能的**明确告警让人来处理**（同 ADR-20 立场）。
- **后果**：这是"保活 + 告警"，不是"永不掉线"。凭据彻底失效时仍需人工更新。

## ADR-34 · 不硬刚站点反爬（`hdzu` 403）

- **背景**：用户要求接入的 `hdzu.org` 返回 **403** 且响应体是
  `<script>window.location.href="/"</script>`；无 `CF-Ray` 头，
  说明是站点**自建**反爬而非 Cloudflare。
- **候选方案**：
  1. 逆向其反爬逻辑（分析 JS 挑战、伪造指纹）
  2. 引入无头浏览器过挑战
  3. 提供 Cookie 输入框，由用户登录后自行粘贴
- **决定**：**方案 3**，站点默认禁用，并在文档中写明"需手工 Cookie"。
- **理由**：
  - 方案 1 是与站点的军备竞赛：对方一改就失效，且**主动规避访问控制**在
    立场上与 ADR-24（不绕付费墙）不一致。
  - 方案 2 要引入 Playwright/Chromium 到运行时依赖（数百 MB），
    为一个站点付这个代价不合理，且同样属于对抗反爬。
  - 方案 3 把"我有权访问这个站"的举证责任交给用户本人——
    他用自己的账号登录、自己提供凭据，这是合规且稳定的。
- **后果**：`hdzu` 开箱不可用。**如实写进文档与站点适配表**，
  而不是标成"已支持"让用户自己去发现搜不到东西。

## ADR-35 · 用**通用适配器**接多站，而不是逐站写定向爬虫

- **背景**：用户要求新增 7 个资源站点。
- **决定**：只写两类代码——① `yyets` 这种有**结构化 API**
  的站单独适配（两阶段 `keyword` → `id`，`_flatten()` 拍平四层嵌套）；
  ② `wp_film` 这种**通用 WordPress 影视站适配器**
  （`/?s=kw&feed=rss2` 搜索 + 详情页抓磁力/网盘/ed2k），一份代码适配多站。
  剩下的交给既有的 `api_generic` / `html_generic` 字段映射。
- **理由**：
  - 大量中文影视站是 WordPress 站，**共享 RSS 搜索这个稳定契约**；
    RSS 结构比页面 HTML 稳定得多，改主题不会破坏它。
  - 逐站写定向爬虫的维护成本随站点数线性增长，且改版时**集体失效**。
  - 实测结果支持这个判断：7 个站里只有 2 个真正能出资源，
    如果每个都写了定向爬虫，等于为 5 份注定要删的代码付出维护成本。
- **配套**：`fetch_text(..., encoding=...)` 支持强制编码，
  以 `content.decode(encoding, errors="replace")` 处理 `dygod` 这类 GB2312 老站
  —— 老站不声明或错误声明字符集时，自动探测会得到乱码。
- **后果**：通用适配器对"长得不标准"的站点命中率有限（见 M25 的 ⚠️ 档）。
  正确的改进方向是给用户**可视化抓取调试器**（v1.8.0 候选），
  而不是我们替每个站写死选择器。
