## v1.13.0 · 2026-08-31 · 搜索名额与超时两个真缺陷 + 按资源选下载器 + 在线站索引 + 内置 AI

> 本轮输入是用户的四条：①「搜索慢，已开启多站但只返回一个站」②「不同资源要用
> 对应的下载方式，网盘要 aria2，缺下载器要提示」③「适配在线视频站 bzzdyy / cz4k」
> ④「内置可自定义模型/接口/密钥的 AI，分析站点该用哪种解析方式并自动添加」。
>
> ① 是**两个真缺陷**（都有可复现的实测数据）；③ 做了但要**如实说明能力边界**：
> 那类站 92% 是会员正片，它的「什么都能下」靠 VIP 解析网关，按 ADR-24 不接。

### 🐛 修复

**① 「已开启多个站点，却只返回一个站的内容」**
- 实测证据：各站 kept 合计 **632 条**，返回前端 **200 条**，其中
  **Nyaa(75) / Bilibili(20) / YouTube(20) 一条都没进**。
- 根因：`apply_site_quota()` 的「按站点轮转交错」只在**排序前**成立。
  `filter_and_rank()` 会按评分**全局重排**把交错打散，再 `[:200]` 一刀切，
  评分天然偏低的站就被**整站抹掉**。
- 评分低不代表结果差，而是**量纲不同**：Nyaa 是生肉站没有中字加成，
  B 站/YouTube 条目没有分辨率与做种数可打分 —— 它们在全局榜上永远垫底。
- 修复：新增 `enforce_site_share(ranked, limit)`，**排序后再做一次名额保护**
  （按站点分桶、桶内保序、轮转取出）。盘搜 `PanSou·夸克` 按 `·` 前缀归并，
  避免一个盘搜吃满名额。
- 实测修复后 5 个站都在：PanSou 54 / Mukaku 53 / Nyaa 53 / B站 20 / YouTube 20。（ADR-65）

**② 「搜索慢」：超时按关键词累加**
- `_search_one()` 对 `build_keywords()` 产出的**每个关键词**各套一次
  `SEARCH_TIMEOUT`。带季集时会产 3 个关键词，于是**一个卡死的站要花
  3 × 25s = 75s**，而 `gather` 必须等最慢的那个。
- 用户看到「转了一分多钟」，配置里却写着 25 秒 —— **配置项含义与实际行为不一致**。
- 修复：`SEARCH_TIMEOUT` 改为**单站点总预算**，每个关键词只能用剩余额度，
  不足 1s 就中止并标 timeout。保留了「站点快速返回空 → 继续降级试下一个关键词」
  这条正常路径（有专门用例钉住）。（ADR-66）

**③ 只装 yt-dlp 时，磁力会被投给 yt-dlp 并标成「正在下载」**
- 实测：投一条磁力 → `downloader=yt-dlp / status=downloading`。
  yt-dlp 根本下不了磁力，用户得等它烂在队列里才发现。反向同理：
  网页视频投给 qBittorrent 会下到一个几 KB 的 HTML。
- 根因：投递逻辑只问「有没有可用下载器」，**不问它收不收这种资源**。

**④ 网盘资源既无账号又无 aria2 时静默 pending**
- 界面上一片空白，用户不知道缺什么。现在会写明两条可行路径（加网盘账号或加 aria2）。

### ✨ 新增

**按资源类型选下载器（需求 2）**
- `BaseDownloader.supported_kinds` + `accepts(kind)` 能力位，基类默认种子/磁力：

  | 下载器 | 可收类型 |
  |---|---|
  | qBittorrent / Transmission | 种子、磁力 |
  | 迅雷 | 种子、磁力、直链 |
  | aria2 | 直链、种子、磁力 |
  | yt-dlp | 仅网页视频 |

- 新增 `app/services/download_routing.py`：`route_of` / `candidates_for` /
  `check` / `hint_of` / `describe`，统一回答「该走谁、缺什么、缺了怎么办」。
- 新增 `GET /api/v1/downloads/routing`；前端据此把下不了的按钮**置灰并写明原因**，
  点击前先拦一次。
- **提示必须可行动**：不是「没有可用下载器」，而是
  「网盘直链需要 aria2：设置 → 下载器 → 添加 aria2」。（ADR-67）

**MacCMS 在线影视站适配器（需求 3，有能力边界，请务必读）**
- 新增 `maccms` Provider + 两个默认禁用的预设（西瓜影院 bzzdyy / CZ4K）。
- **实测数据**：抓 bzzdyy 首页 30 部片、53 个播放源，平台分布
  `qq 21 / qiyi 12 / youku 10 / mgtv 6 / bilibili 3 / rrmj 1`
  → **49/53 ≈ 92% 是长视频平台的会员正片**。
- 这类站**自己不存片**，它的「什么都能下」靠 `playerconfig.js` 里所有播放源
  共用的一个 **VIP 解析网关**（依赖盗取/共享的会员票据）—— 按 ADR-24 **不接**。
- 所以本适配器只做**索引**：产出播放源指向的原始平台地址；会员正片在结果里
  **如实标注「会员」标签且不给下载按钮**（渲染一个必然失败的按钮只会让用户白点）。
- **实际能下到的是 B 站内容与官方免费片源**，数量远少于站点首页看起来的那样。
- `cz4k.com` 被 SafeLine WAF 拦（HTTP 468），**不做 WAF 对抗**。（ADR-68）

**内置 AI 站点分析（需求 4）**
- 新增 `app/services/ai_site.py` + `app/api/routers/ai.py`
  （`GET /ai/config`、`POST /ai/analyze|verify|apply`）。
- 只用 **OpenAI 兼容 `/chat/completions`**，所以 OpenAI / DeepSeek / 智谱 /
  通义 / Ollama / OneAPI 都能用。7 项配置在设置页「内置 AI」分组可改。
- **默认关闭**（`AI_ENABLED=False`）：开启意味着把站点页面正文发给第三方模型，
  必须显式同意。有用例钉住「没开就零外发流量」。
- **三步走 `analyze → verify → apply`，AI 只出建议不直接写库**：模型会编造字段，
  自动落库等于把搜不到东西的站塞进搜索链路，之后每次搜索都白等一次超时。
  界面先给「置信度 + 依据 + 试搜命中几条」，你确认才添加（默认不启用）。
- 落库时写 `_ai_generated` / `_ai_reason` 留痕。（ADR-69）

### 🔧 变更

- `Resource.paywalled`（会员正片判定，复用 `ytdlp.is_blocked`，只对网页视频生效），
  `to_dict()` 一并下发；会员正片的 `actions` 里不含 `download`。

- 前端补 `sparkles` 图标与 `.notice` / `.pre-wrap` 样式（AI 面板要用）。

### 💥 破坏性变更

## v1.12.1 · 2026-08-30 · 代码 Review 查缺补漏：失败通知从来没发出去 + 通配符语法不生效

> 本轮输入是一句「review 项目代码，进行查缺补漏」。
> **不是随机翻代码**：沿用上一轮抓到「网盘保活从不发通知」的同一模式，
> 写脚本批量扫「**声明了但没接线**」的缺口 —— 这类缺陷不会让任何测试失败、
> 界面上也看不出来，只能靠交叉比对文档承诺与代码实际行为找出来。
>
> 结果抓到 **6 个真缺陷**，全部有可复现的硬证据。最讽刺的是：
> 上一轮我把「只把失败推到手机」写成通知过滤功能的**头号用例**，
> 而**下载失败和入库失败一条通知都发不出来** —— 失败的全部下场是
> `stats["failed"] += 1`，这个计数返回给调度器后就被丢掉了。

### 🐛 修复

**① 下载失败从来不发通知**
- `sync_tasks()` 里失败的唯一处理是 `stats["failed"] += 1`。种子死了、
  磁盘满了、下载器鉴权掉线 —— 用户**完全不知情**，除非自己去翻「下载任务」页。
- 现在推 `error` 级 `download.failed`，正文带失败原因（换资源还是清磁盘，
  取决于原因，所以必须带上）。
- **只在状态翻转时发**（`downloading → failed` 那一刻）。`sync_tasks` 是
  5 分钟一轮而失败是个**稳定状态**，不去抖的话一个卡住的死种一天推 288 条，
  用户会直接关掉通知、连真正重要的告警一起丢掉（ADR-63）。
- 一轮内失败 N 个**合并成一条**，正文最多列 10 条 + 「…另有 N 个」。

**② 入库失败从来不发通知，`transfer.failed` 枚举零触发点**
- `transfer_completed_tasks()` 同样只 `stats["failed"] += 1`；
  全文 `TRANSFER_FAILED` 出现 **0 次** —— 枚举声明了却永不触发。
- **这是最容易被忽略的中间态**：「下载任务」页显示**已完成**，
  媒体库里却什么都没有 —— 一个*看起来正常*的错误状态。
  典型原因是硬链接跨盘（`Invalid cross-device link`，下载目录与媒体库
  不在同一文件系统）和目标目录权限不足，两者都不会自愈。
- 现在推 `error` 级 `transfer.failed`，正文带原因（跨盘和权限的处理方式完全不同）。

**③ 事件通配符 `*` 根本不生效**
- 实现只认**带尾点**的 `download.`，而文档从头到尾教用户写 `download.*`。
- 照文档配的后果，两个方向都是**静默失败**（无报错、无日志、界面无异常）：

  | 用户按文档写 | 实际行为 |
  |---|---|
  | `"events": ["download.*"]` | **一条通知都收不到** |
  | `"events_exclude": ["library.*"]` | **以为屏蔽了，其实照收** |

- 现在 `download.*` / `download.` / `download` **三种写法完全等价**，
  且通配以**点**为边界（`download.*` 不误伤 `downloader.speed_limit`）。
- 与 ADR-59 同一原则：通知系统的失效模式必须偏向「多发」而非「不发」（ADR-62）。

**④ 文档里的两个事件名是错的 / 不存在的**
- `site.down` **纯属笔误**，真名是 `site.unhealthy`（3 处，全在用户会
  **直接复制粘贴的 JSON 代码块**里）。
- `download.failed` 在 v1.12.0 **并不存在于 `EventType`**，是写文档时凭空编的。
  本轮随缺陷 ① 正式补上（`EventType` 现有 17 个成员）。
- 照抄配好之后那个渠道会**彻底静默且没有任何报错** —— 最难自查的一类故障。

**⑤ `download.completed` / `plugin.action` 声明了却零触发点**
- 两者都被开发指南列为「可订阅事件」，但代码里**没有任何地方触发** ——
  插件订阅后永远收不到回调，且不会报错。
- 现在都接到事件总线上。两者**只 `emit()` 不发用户通知**：
  `download.completed` 紧接着就有「入库完成」通知，两条挨着发就是刷屏；
  `plugin.action` 点一下按钮就弹推送太吵。

**⑥ 文档里 38 处 API 路径漏了 `/v1` 前缀**
- `docs/05-ChatOps-机器人.md`（15 处）与 `docs/06-网盘管理.md`（20 处）
  整章写成 `/api/pan/...`、`/api/chatops/...`，而真实路径是 `/api/v1/...`。
  同一份文档的**另一些段落却是对的** —— 典型的抄改遗留。
- **危害最大的是 ChatOps 回调地址**：那三行是要**复制粘贴进飞书 / 钉钉 /
  Telegram 后台**的。填错的表现是「机器人死活没反应」，平台侧只回一个 404，
  用户根本不会想到是文档抄错了前缀。
- 新增 `tests/test_doc_endpoints.py`（5 个用例）：以 `app.openapi()` 为
  权威来源，断言文档里每个路径都真实存在，**并直接提示正确路径**。
  同时覆盖两种写法 —— 行内 `METHOD /path`，以及**端点表格**里方法与路径
  分列两格的 `| POST | /api/v1/... |`。后者一开始漏了，
  负向验证时发现「把回调地址那行改坏，测试居然还是绿的」才补上 ——
  而那正是全文最要紧的一行。
- 相对简写（`POST /downloads`）也一并锁住：必须能用 `/api/v1` 补全到真实端点，
  否则端点改名后这些行会静默变错。第三方接口（夸克 `/share/sharepage/*`、
  AList `/api/fs/*`、ldysg `/api.php`）与 `/api/health`

**③ 下载器限速时段（M40）——白天限速、夜里跑满**
- 新增 `app/services/speed_limit.py`、3 个端点、设置页「下载器限速时段」卡片、
  第 14 个定时任务 `speed_limit`（默认每 10 分钟幂等下发）。
- **跨午夜时段是这类功能的经典 bug**：`23:00-07:00` 用朴素 `start<=now<=end`
  **恒为假**，整个"夜间限速"会静默失效（用户以为配好了，其实从未生效）。
  已显式分支处理，边界全部测到；`start==end` 视为全天。
- **三个下载器三种单位，全部实测确认**：
  - **qB 的接口是 B/s** → 必须 ×1024。不换算的话用户设 10MB/s 实际得到 10KB/s，
    看起来像"限速反而让下载更慢了"。
  - **TR 本来就是 KB/s**（别顺手乘 1024），但**必须同时下发 `speed-limit-down-enabled`** ——
    只设数值不开开关，TR 会把数值存下来却**继续满速跑**，是最难自查的一种失效。
    传 0 要**关开关**而不是限到 0（限 0 会彻底断流）。
  - **aria2 的值必须是字符串**（`"5120K"`），传整数会被 JSON-RPC 拒绝。
- 基类新增能力位 `supports_speed_limit`，迅雷 CGI 与 yt-dlp 保持 `False` ——
  **不假装支持**，下发结果如实标「跳过」（沿用 ADR-28 思路）。
- 刻意**不做 per-torrent 限速**：那属 PT 保种精调，应在下载器自己界面做。

**⑥ 豆瓣同名不同年会配错封面（真缺陷）**

  2002 年的电影《无间道》会被配上 2019 剧版的封面。

  若只扣 40，该组合得 65 分**仍能过门槛，等于没拦住**。

## v1.10.1 · 2026-08-30 · 修「升级后界面还是旧版」：静态资源禁止启发式缓存

> 本轮输入是用户的一句反馈：「我在 docker 中更新了项目，但不是最新版本。
> 检查 GitHub 上是否已经完成更新。」
>
> **先说结论：GitHub 端当时已经完全更新到位**，逐层核验过——
> `origin/main` = `9ea71f4`、Actions `build-image` success、
> GHCR `latest` 与 `sha-9ea71f4` 同指 `sha256:df6d1c76`、
> 镜像 label 的 `revision` 正是该 commit。为避免「标签对但内容旧」的缓存陷阱，
> 还**解包了镜像层**验证：里面的 `version.py` 确实是 `1.10.0`、
> `app.js` 6555 行且已不含 `trendingSearchPanel`、含 `videoDownloadButton`/
> `downloaderForm`/`cols-settings`。**镜像内容无误。**
>
> 所以问题不在发布侧。顺着「为什么用户会觉得不是最新版」往下查，
> 找到两个**真实缺陷**，都在这一版修掉。

### 🐛 修复

**① 静态资源缺 `Cache-Control`，浏览器可能根本不回源 → 界面比后端慢一个版本**

- Starlette 的 `StaticFiles` 默认**只给 `ETag`/`Last-Modified`，不给 `Cache-Control`**。
  缺了它，浏览器可按 RFC 7234 **自行推算新鲜期**（常见实现是「距上次修改时间的 10%」）
  直接用本地副本、**根本不来问服务器**。
- 后果非常具有误导性：`/api/health` 已经返回 `1.10.0`，
  但界面加载的还是旧 `app.js` —— 看起来就像「镜像没更新成功」，
  实际后端早就是新的。这正是本轮用户症状的最可能成因。
- 修法：新增 `_NoCacheStatic`，给 `/assets/*` 与 `/`（index.html）统一加
  `Cache-Control: no-cache`。注意 `no-cache` 的语义**不是"不缓存"**，
  而是"每次必须回源校验"——配合已有 ETag，未变更时仍返回 **304**（几百字节），
  几乎不增加流量，但保证升级后**必然拿到新代码**。
- index.html 也必须加：它引用的是**不带版本指纹**的 `/assets/app.js`，
  一旦入口文档被缓存住，后续资源会跟着停留在旧版本。

**② 运维手册里的 `docker compose build` 命令在 ADR-47 之后已经失效**

- v1.9.2（ADR-47）把 `build` 从部署用 compose 里**彻底移除**了，
  但 `docs/07-运维手册.md` 的日常运维命令仍写着
  `docker compose build --no-cache && docker compose up -d` ——
  用户照着执行会直接报错（服务没有 build 配置）。**文档漂移**。
- 已改为 override 写法：
  `docker compose -f docker-compose.yml -f docker-compose.build.yml build --no-cache`。

### 📖 文档

- `docs/07-运维手册.md` 新增 **§⑨-1「升级后『还是旧版本』怎么查」**：
  从外到内四步定位（`/api/health` 权威版本 → 比对容器 Image 与 latest 的 Id →
  `docker exec cat version.py` 直接看镜像内代码 → 读镜像 label 的构建时间与 commit），
  并给出四种现象各自的处置（含 `pull` 显示 up to date 但 digest 是旧的这种情况）。
- `docs/11-飞牛NAS部署指南.md` §5.1 升级步骤补上 **`--force-recreate`** ——
  `pull` 只更新镜像，**不会自动重建已在跑的容器**，这是最常见的「升级了没变化」原因；
  另补充如何用 `CINEFLOW_IMAGE=…:sha-<commit>` **锁定版本或回滚**。

## v1.9.1 · 2026-08-30 · YAML 与部署文件审计：修 3 个真缺陷 + 新增 verify_yaml 门禁

> 本轮输入是用户的一条要求：「检查 yml 语法」。
> 4 个 YAML 的**语法本来就全合法**，但语法过 ≠ 能跑 ——
> 深挖语义层后发现 3 个真缺陷，其中 1 个会让功能静默失效。

### 🐛 修复

**① 配置模板被 bind mount 遮蔽 → 首次生成配置的逻辑永远不触发**
- 原先 Dockerfile 把模板 `COPY` 到 `/app/config/config.yaml.example`，
  而两个 compose 都把宿主 `./config` 挂到 `/app/config`。
  **bind mount 是整体替换目录内容**，镜像里那份模板直接被遮蔽 →
  entrypoint 的 `[ -f /app/config/config.yaml.example ]` **恒为假** → 永不复制。
- 症状很隐蔽：服务能正常启动（`_yaml_source()` 里 `if not path.exists(): return {}`，
  配置文件是可选的，全靠环境变量），**但用户在 NAS 上打开 config 目录发现是空的**，
  没有可编辑的模板 —— 而 README 与 `docs/13` 都在讲「可以改 config.yaml」。
- 修法：模板改放 **`/app/config.yaml.example`**（挂载点之外），
  entrypoint 用 `CF_TEMPLATE` 变量指向它；顺带**把模板副本也复制进挂载目录**，
  用户可对照默认值，改坏了能照抄回来。已有 `config.yaml` 一律不覆盖。

**② entrypoint 里 `cp` 早于 `mkdir` → `set -e` 下可能直接杀死容器**
- 脚本开头是 `set -e`，而配置复制那段原本排在 `mkdir -p /app/config` **之前**。
  `docker run` 不挂载 config 卷时该目录可能不存在，`cp` 失败会终止启动。
- 修法：调整顺序为**先建目录、再复制配置**。

**③ workflow 的 `on:` 被 YAML 解析成布尔键 `True`**
- YAML 1.1 把裸 `on` / `off` / `yes` / `no` 当布尔字面量，
  所以 `build-image.yml` 的顶层键实际是 `True` 而不是字符串 `"on"`。
- **GitHub Actions 自身对此有特殊处理，构建一直是成功的**，所以不是运行期 bug。
  但 `yq` / `actionlint` / 自写脚本读 `data["on"]` 会 `KeyError`。
- 修法：写成 `"on":`。改后 `yaml.safe_load` 能正常取到 `push` 与 `workflow_dispatch`。

### 🔧 变更
- `build-image.yml` 行尾统一为 LF（原本 51 行 LF + 末行 CRLF 混合，
  是之前用 PowerShell 追加内容留下的痕迹）。
- `docker-compose.yml` 里「改用源码编译」的注释改为**显式警告必须先注释掉上面那行 `image`**
  —— 两个 `image` 键同时存在时 YAML 不报错、**静默取后一个**，
  用户会以为在用自己编译的镜像，其实拉的是官方的（或反之），极难排查。

### 🆕 新增

**`scripts/verify_yaml.py`（101 项，无需启动服务）**
单独立一个门禁而不塞进 `verify_docs.py`，因为它验的是**部署契约**而非文档事实。
覆盖两层：

| 层 | 检查项 |

### 🐛 修复

**两个真 bug，都是本轮自测抓到的（不是重构顺手改的）**

1. **`int(x or -1)` 把成功值 `0` 吃掉**（`panlogin/baidu.py`）。
   百度的 `status` 与 `errno` 成功值都是 `0`，而 `0` 在 Python 里是假值，
   `or` 会直接替换成 `-1`，于是「成功」永远判不出来——扫码成功也识别不了、
   有效 Cookie 也判成无效。同一个坑在两处各踩一次，已抽成 `_as_int()` 复用
   并写明为什么不能用 `or`。
2. **对外接口的 `verify=false` 是个后门**（`schemas/models.py` + `routers/pan.py`）。
   这是**冒烟测试打真实 HTTP 抓到的**：`POST /pan/login/cookie` 请求体带上
   `verify=false`，就能把任意字符串（实测 `x=1`）当 Cookie 写进站点记录
   **并启用该站点**，等于把 ADR-40「校验不过不写库」整条绕过去。
   已从 `PanCookieImportRequest` 移除该字段、路由写死 `verify=True`，
   并加两条回归测试（schema 无该字段 / 路由源码不读 `payload.verify`）。
   服务层仍保留该参数，但只给扫码流程内部用——扫码本身已证明凭据有效，
   再校验一次反而更容易撞风控。

3. **发现榜的本地片源统计静默失效**（`services/discover.py`）。
   首版照抄猜测的列名（`site_name`、`parsed_title`），而 `ResourceRecord`
   的真实列名是 `site` 且**没有** `parsed_title`（`parse` 来自
   `app.core.meta`，不是 `app.utils.media`）。表现是不报错、
   角标永远显示 0。已修并留回归用例。

4. **约 1/4 的榜单封面裂图**（`routers/images.py` + `metadata/douban_chart.py`）。
   这是 **`ui_check` 抓到的**：36 个 JS 报错全是 `/images/proxy` 返回 415。
   起初以为是「豆瓣图址过期」这类环境噪声、准备加进忽略白名单，实测后否掉：
   同一张图在 `img1/img2/img3` 都返回 `image/jpeg`，只有 **`img9.doubanio.com`
   返回 200 + `text/html`**（反爬脚本页）——它是个长期损坏的镜像，而豆瓣会把
   封面随机分发到这四个镜像（20 条里 img9 占 5 条）。
   修法是两层：**入库前把 img9 改写成 img3** + **代理侧按 `img3→img1→img2`
   轮换重试**。刻意**没有**放宽 `content_type` 校验（那是 SSRF 三道防线之一），
   也**没有**把 415 加进 ui_check 白名单——那属于用忽略掩盖用户真实可见的缺陷。
   见 [ADR-41](04-决策记录.md)、[docs/07 §8.4](07-运维手册.md)。

### 🔒 安全

- **扫码会话只存进程内存**，不落库、不写日志、不进缓存文件，TTL 600s，
  进程重启即清空。理由：凭据的有效生命周期只有几十秒（从扫码到写入站点），
  为此付出永久持久化的风险（进备份、进 SQLite WAL）不值得。见 [ADR-39](04-决策记录.md)。
- **响应体绝不含 Cookie**：`LoginSession.to_dict()` 是唯一对外序列化出口，
  它不输出 `cookie` 字段，因此不存在「某个端点不小心把凭据返回给前端」的路径。
  有专门的回归测试 `test_session_dict_never_leaks_cookie` 钉住。
- **登录成功后立即销毁会话**；过期会话报一次过期提示后也立即销毁。
- **校验不通过一律不写库**（[ADR-40](04-决策记录.md)）。存无效凭据的唯一效果
  是让半夜的定时任务静默失败——把错误推迟到最难排查的时刻。
- 登录写入类端点需 **operator 及以上**权限；`/login/providers` 仅需登录。

### ⚠️ 破坏性变更

- `POST /api/v1/pan/login/cookie` 的请求体**不再接受 `verify` 字段**
  （多余字段会被忽略，校验照常执行）。该端点是 v1.8.0 本轮新增的，
  不存在依赖它的旧客户端，故不提供兼容开关。

   会把**进程当前目录**当成网盘根目录。改为返回 `None` 并给出明确提示，
