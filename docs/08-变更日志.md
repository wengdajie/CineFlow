## v1.10.0 · 2026-08-30 · 榜单改「当前最热」并加 YouTube + 下载器搬进设置页 + 设置页多列布局

> 本轮用户提了三组需求：①榜单改造（当前最热口径 / 去掉页内搜索卡片 / 加 YouTube /

### ✨ 新增

**① 榜单第六个分类：YouTube 地区热榜**
- 新增 `app/providers/indexer/yt_chart.py` + `GET /trending/youtube/{region}`，
  支持 US / JP / KR / HK / TW / GB（实测均 200，各约 15 条）。
- 数据源绕了两条弯路才落地：YouTube 官方 `/feed/trending` **已下线**（yt-dlp 报
  `channel/playlist does not exist`）；社区流传的 "Popular Right Now" playlist
  能抓到但里面是 **2024 年陈旧数据**（假数据，比报错更危险）；Data API v3 要用户
  自申请 Key 与配额，与其余榜单开箱即用不符。最终选**免 Key 的 Piped 开源实例**。
- 公开实例极不稳定：**实测 8 个候选只有 1 个可用**（其余 DNS 失败/502/403），
  所以核心设计是**多实例故障转移** + 记住成功实例优先复用 + 30 分钟缓存 +
  失败退避 300 秒。封面从 videoId 重建 `i.ytimg.com` 直链（实测 200 image/jpeg），
  不用 Piped 自家代理地址。详见 [ADR-49](04-决策记录.md)。
- ⚠️ **已知局限**：该分类依赖第三方公开实例且需能访问外网，可能间歇不可用。

**② 下载器独立管理接口（设置页专用）**
- 新增 `app/services/downloader_specs.py` 显式登记每个下载器的可配字段
  （type / 范围 / choices / hint / target），以及
  `GET /downloaders/schema`、`GET/POST /downloaders`、
  `PATCH/DELETE /downloaders/{id}`、`POST /downloaders/{id}/test`。
- 实测可配字段数：qBittorrent **8** / Transmission **6** / aria2 **6** / yt-dlp **16**。
  再也不用手写 `options` JSON。
- 存储**仍复用 `SiteConfig` 表（kind=downloader）**，已有配置**零迁移**，
  `site_service.downloaders()` 完全不动。

## v1.9.2 · 2026-08-30 · 修部署事故：镜像来源结构性隔离 + 飞牛文档去过时

> 本轮输入是用户在飞牛上部署时的两条真实报错。
> 上一版（v1.9.1）**已经预判到这个坑并加了注释警告，但用户照样踩进去了** ——
> 说明靠文档提醒兜底设计缺陷不可靠，这一版改成结构上配不错。

### 🐛 修复

**① 「注释掉一行、取消注释另一行」的操作设计导致双重报错**

用户现场：
```
Get "https://registry-1.docker.io/v2/": context deadline exceeded
failed to solve: failed to read dockerfile: open Dockerfile: no such file or directory
```

根因是用户取消注释了 `# image: cineflow:latest` 与 `# build: .`，
但**漏掉「先注释掉上面那行 ghcr image」**。两个 `image` 键并存时
**YAML 与 compose 都不报错**、静默取后者裸名 → 去 Docker Hub 拉不存在的镜像超时；
同时 `build: .` 生效却在只有 compose 文件的目录里找不到 Dockerfile
（日志 `transferring dockerfile: 2B` 即证据）。

修法是结构性的，不再依赖用户正确执行两步：
- `docker-compose.yml` / `docker-compose.fnos.yml`：**只保留一个 `image` 键，彻底移除 `build`**，
  并改为 `${CINEFLOW_IMAGE:-ghcr.io/wengdajie/cineflow:latest}`（可用变量换版本/换仓库，
  默认值保证**不会退化成裸名**）。
- **新增 `docker-compose.build.yml`** 作为编译 override：
  `docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build`。
  两种模式在不同文件里，无法互相污染。详见 [ADR-47](04-决策记录.md)。

**② `docs/11-飞牛NAS部署指南.md` 有 7 处过时内容（文档漂移）**

v1.8.0 起就已改用预构建镜像，但飞牛指南仍在说
「CineFlow 目前是**源码构建**（compose 里 `build: .`）」、
「图形界面**仍需要代码在** `/vol1/docker/cineflow`」、
「升级用 `up -d --build`」—— **用户照着做必然踩坑**。
已全部改为 `pull` 路线，新增 §5.3「从源码自行编译」，
并把本次两条报错的**症状与处置**写进 §4.1 排障（含「怎么判断它去的是 Docker Hub 而不是 ghcr.io」）。

## v1.9.1 · 2026-08-30 · YAML 与部署文件审计：修 3 个真缺陷 + 新增 verify_yaml 门禁

> 本轮输入是用户的一条要求：「检查 yml 语法」。
> 4 个 YAML 的**语法本来就全合法**，但语法过 ≠ 能跑 ——
> 深挖语义层后发现 3 个真缺陷，其中 1 个会让功能静默失效。

### 🐛 修复

**① 配置模板被 bind mount 遮蔽 → 首次生成配置的逻辑永远不触发**
- 原先 Dockerfile 把模板 `COPY` 到 `/app/config/config.yaml.example`，
  而两个 compose 都把宿主 `./config` 挂到 `/app/config`。
  **bind mount 是整体替换目录内容**，镜像里那份模板直接被遮蔽 →
  entrypoint 的 `[ -f /app/config/config.yaml.example ]` **恒为假** → 永不复制。
- 症状很隐蔽：服务能正常启动（`_yaml_source()` 里 `if not path.exists(): return {}`，
  配置文件是可选的，全靠环境变量），**但用户在 NAS 上打开 config 目录发现是空的**，
  没有可编辑的模板 —— 而 README 与 `docs/13` 都在讲「可以改 config.yaml」。
- 修法：模板改放 **`/app/config.yaml.example`**（挂载点之外），
  entrypoint 用 `CF_TEMPLATE` 变量指向它；顺带**把模板副本也复制进挂载目录**，
  用户可对照默认值，改坏了能照抄回来。已有 `config.yaml` 一律不覆盖。

**② entrypoint 里 `cp` 早于 `mkdir` → `set -e` 下可能直接杀死容器**
- 脚本开头是 `set -e`，而配置复制那段原本排在 `mkdir -p /app/config` **之前**。
  `docker run` 不挂载 config 卷时该目录可能不存在，`cp` 失败会终止启动。
- 修法：调整顺序为**先建目录、再复制配置**。

**③ workflow 的 `on:` 被 YAML 解析成布尔键 `True`**
- YAML 1.1 把裸 `on` / `off` / `yes` / `no` 当布尔字面量，
  所以 `build-image.yml` 的顶层键实际是 `True` 而不是字符串 `"on"`。
- **GitHub Actions 自身对此有特殊处理，构建一直是成功的**，所以不是运行期 bug。
  但 `yq` / `actionlint` / 自写脚本读 `data["on"]` 会 `KeyError`。
- 修法：写成 `"on":`。改后 `yaml.safe_load` 能正常取到 `push` 与 `workflow_dispatch`。

### 🔧 变更
- `build-image.yml` 行尾统一为 LF（原本 51 行 LF + 末行 CRLF 混合，
  是之前用 PowerShell 追加内容留下的痕迹）。
- `docker-compose.yml` 里「改用源码编译」的注释改为**显式警告必须先注释掉上面那行 `image`**
  —— 两个 `image` 键同时存在时 YAML 不报错、**静默取后一个**，
  用户会以为在用自己编译的镜像，其实拉的是官方的（或反之），极难排查。

### 🆕 新增

**`scripts/verify_yaml.py`（101 项，无需启动服务）**
单独立一个门禁而不塞进 `verify_docs.py`，因为它验的是**部署契约**而非文档事实。
覆盖两层：

| 层 | 检查项 |
|---|---|
| 语法 | 4 个 YAML 的解析合法性、**重复键**（PyYAML 默认静默取后者，自定义 Loader 显式报错）、Tab 缩进、BOM、孤立 CR |
| 语义 | 容器端口与 Dockerfile `EXPOSE`/`HEALTHCHECK` **三方一致**；healthcheck 依赖的 `curl` 真装在镜像里；`CF_*` 变量都被 `Settings` 认识（`extra="ignore"` 会静默丢弃拼错的）；`PUID/PGID/TZ` 真被 entrypoint 消费；Dockerfile 声明的数据目录都被挂载；**模板不落在会被遮蔽的目录**；entrypoint 先建目录再复制；`config.yaml.example` 全部键有效且类型能过 Pydantic |
| 用户操作模拟 | **精确剥掉注释启用可选服务**，验证仍是合法 YAML、每个服务都是完整映射且有镜像来源、宿主端口不冲突、**各服务 `/downloads` 指向同一宿主路径**（硬链接铁律） |
| 端到端 | 生成的 `config.yaml` **真能被 `Settings` 读取**（改成 77 验证读到 77），且**环境变量仍能覆盖它**（设 99 验证得 99），与文档承诺的优先级一致 |

**负向验证**：故意引入 4 种回归（模板放回被遮蔽目录 / `on` 退回裸写法 /
容器端口与 EXPOSE 不一致 / 环境变量名拼错），**全部被抓到并退出非 0**，
确认这 101 项不是空跑。

  **`message` 只在 `offset == 0` 时给**——翻到最后一页拿到空结果是正常到底，
  不该再报「豆瓣限流」这种误导性提示。

  `/trending/bilibili/{partition}` 的 `limit` 默认 **24 → 30**，

### 🐛 修复

**两个真 bug，都是本轮自测抓到的（不是重构顺手改的）**

1. **`int(x or -1)` 把成功值 `0` 吃掉**（`panlogin/baidu.py`）。
   百度的 `status` 与 `errno` 成功值都是 `0`，而 `0` 在 Python 里是假值，
   `or` 会直接替换成 `-1`，于是「成功」永远判不出来——扫码成功也识别不了、
   有效 Cookie 也判成无效。同一个坑在两处各踩一次，已抽成 `_as_int()` 复用
   并写明为什么不能用 `or`。
2. **对外接口的 `verify=false` 是个后门**（`schemas/models.py` + `routers/pan.py`）。
   这是**冒烟测试打真实 HTTP 抓到的**：`POST /pan/login/cookie` 请求体带上
   `verify=false`，就能把任意字符串（实测 `x=1`）当 Cookie 写进站点记录
   **并启用该站点**，等于把 ADR-40「校验不过不写库」整条绕过去。
   已从 `PanCookieImportRequest` 移除该字段、路由写死 `verify=True`，
   并加两条回归测试（schema 无该字段 / 路由源码不读 `payload.verify`）。
   服务层仍保留该参数，但只给扫码流程内部用——扫码本身已证明凭据有效，
   再校验一次反而更容易撞风控。

3. **发现榜的本地片源统计静默失效**（`services/discover.py`）。
   首版照抄猜测的列名（`site_name`、`parsed_title`），而 `ResourceRecord`
   的真实列名是 `site` 且**没有** `parsed_title`（`parse` 来自
   `app.core.meta`，不是 `app.utils.media`）。表现是不报错、
   角标永远显示 0。已修并留回归用例。

4. **约 1/4 的榜单封面裂图**（`routers/images.py` + `metadata/douban_chart.py`）。
   这是 **`ui_check` 抓到的**：36 个 JS 报错全是 `/images/proxy` 返回 415。
   起初以为是「豆瓣图址过期」这类环境噪声、准备加进忽略白名单，实测后否掉：
   同一张图在 `img1/img2/img3` 都返回 `image/jpeg`，只有 **`img9.doubanio.com`
   返回 200 + `text/html`**（反爬脚本页）——它是个长期损坏的镜像，而豆瓣会把
   封面随机分发到这四个镜像（20 条里 img9 占 5 条）。
   修法是两层：**入库前把 img9 改写成 img3** + **代理侧按 `img3→img1→img2`
   轮换重试**。刻意**没有**放宽 `content_type` 校验（那是 SSRF 三道防线之一），
   也**没有**把 415 加进 ui_check 白名单——那属于用忽略掩盖用户真实可见的缺陷。
   见 [ADR-41](04-决策记录.md)、[docs/07 §8.4](07-运维手册.md)。

### 🔒 安全

- **扫码会话只存进程内存**，不落库、不写日志、不进缓存文件，TTL 600s，
  进程重启即清空。理由：凭据的有效生命周期只有几十秒（从扫码到写入站点），
  为此付出永久持久化的风险（进备份、进 SQLite WAL）不值得。见 [ADR-39](04-决策记录.md)。
- **响应体绝不含 Cookie**：`LoginSession.to_dict()` 是唯一对外序列化出口，
  它不输出 `cookie` 字段，因此不存在「某个端点不小心把凭据返回给前端」的路径。
  有专门的回归测试 `test_session_dict_never_leaks_cookie` 钉住。
- **登录成功后立即销毁会话**；过期会话报一次过期提示后也立即销毁。
- **校验不通过一律不写库**（[ADR-40](04-决策记录.md)）。存无效凭据的唯一效果
  是让半夜的定时任务静默失败——把错误推迟到最难排查的时刻。
- 登录写入类端点需 **operator 及以上**权限；`/login/providers` 仅需登录。

- `POST /api/v1/pan/login/cookie` 的请求体**不再接受 `verify` 字段**
  （多余字段会被忽略，校验照常执行）。该端点是 v1.8.0 本轮新增的，
  不存在依赖它的旧客户端，故不提供兼容开关。

### 🐛 修复

1. `LocalDirStorage.base_dir` 未配置时返回 `Path("")`（等价于 `Path(".")`），
   会把**进程当前目录**当成网盘根目录。改为返回 `None` 并给出明确提示，
   同时支持 `file:///` 前缀写法。
2. 指令解析的 `_SEASON_RE` / `_EPISODE_RE` 用了 `\bS(\d{1,2})\b`，
   导致 `S01E09` 匹配不到季号。改为 `(?<![A-Za-z0-9])S(\d{1,2})(?!\d)`。
3. 指令解析里 `cleaned.replace(":", " ", 1)` 会把 `magnet:?xt=` 和 `https://`
   拆坏，导致「下载 magnet:…」失败。改为只替换紧跟指令词的第一个冒号。
4. `quark` / `alist` 的凭据改用 `self.option()` 读取，兼容填在 `options` 里的情况。

### ⚠️ 破坏性变更

**ChatOps Webhook 未配置验签密钥时，从放行改为默认拒绝（401）。**

原因：该端点不走 JWT 鉴权（平台无法携带），却能触发下载与删除网盘文件。
「忘配密钥 = 敞开大门」不可接受。详见 [`04-决策记录.md`](04-决策记录.md) ADR-04。

**升级动作**：给每个启用的平台补齐密钥；纯内网且明白风险者，
可在该平台配置里把 `allow_unverified` 填 `1` 恢复旧行为（会打 WARNING 日志）。
