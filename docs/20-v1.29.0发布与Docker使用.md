## 镜像与离线包

仓库：[wengdajie/CineFlow](https://github.com/wengdajie/CineFlow)。镜像：`ghcr.io/wengdajie/cineflow`，支持 `linux/amd64`、`linux/arm64`。

| 标签 | 用途 |
|---|---|
| `latest` | main 分支最近一次成功构建 |
| `v1.29.0` | 本次版本标签构建 |
| `sha-<短提交号>` | 按具体源码提交固定镜像 |

GitHub Actions 先运行两套 Python 的质量门禁，再构建 amd64 镜像，验证容器健康、版本、前端、非 root 管理员登录及重启后密钥不变，随后构建并推送双架构镜像。导出时逐一验证 amd64、arm64 容器启动和登录，全部成功后才发布版本附件。构建失败时不能把“已推送代码”视为“镜像已可用”；应以 [build-image](https://github.com/wengdajie/CineFlow/actions/workflows/build-image.yml) 运行成功和镜像摘要为准。

构建产物 `cineflow-docker-<完整提交号>` 包含：

- `cineflow-1.29.0-linux-amd64.tar.gz`
- `cineflow-1.29.0-linux-arm64.tar.gz`
- `SHA256SUMS`

正式版本构建成功后，离线包和校验文件会同步上传到 [GitHub Releases](https://github.com/wengdajie/CineFlow/releases)，可直接下载。Actions 临时产物保存 14 天，下载需要登录 GitHub。选择与 NAS 架构一致的包；使用 Actions 产物时先解压外层 ZIP，然后校验并导入：

```bash
sha256sum -c SHA256SUMS
docker load -i cineflow-1.29.0-linux-amd64.tar.gz
CINEFLOW_IMAGE=ghcr.io/wengdajie/cineflow:1.29.0-amd64 \
  docker compose -f docker-compose.fnos.yml up -d --pull never
```

ARM NAS 改用 `arm64` 文件和 `1.29.0-arm64` 镜像标签。离线包导入的架构标签是本地镜像名，在线拉取请使用上表中的多架构标签。`--pull never` 用于本次离线启动，避免 compose 的 `pull_policy: always` 再访问仓库。上述命令在 compose 文件所在目录运行。

## 在线更新

先备份数据、配置与 STRM，保留原 compose 文件及挂载路径，不用下载的新模板覆盖自己的配置。

```bash
# 通用部署
docker compose pull cineflow
docker compose up -d cineflow

# 飞牛部署
docker compose -f docker-compose.fnos.yml pull cineflow
docker compose -f docker-compose.fnos.yml up -d cineflow
```

固定到本次版本：在相同 shell 中先执行 `export CINEFLOW_IMAGE=ghcr.io/wengdajie/cineflow:v1.29.0`，再执行对应更新命令。更新后访问 `/api/health`，确认版本为 `1.29.0`；查看容器日志与健康状态，验证原订阅、下载器路径及媒体库挂载。

## 升级变化与回滚

- 使用公开默认 JWT 密钥的实例将自动生成 `data/jwt-secret.txt`，旧登录会话失效，需要重新登录。现有密码不自动修改，自定义密钥保留。
- 备份必须包含整个数据目录和新密钥文件。自定义调用方修改密码时，使用 `POST /api/v1/auth/password` 的 JSON 请求体 `{old_password, new_password}`。
- 外部 HTTP 默认校验证书，自签名服务应配置受信任 CA；确需关闭时由对应驱动 options 显式配置 `verify_ssl: false`。
- 历史无凭据 STRM 链接的迁移步骤见 [精简优化与升级说明](16-精简优化与升级说明.md)。
- 回滚时先停止应用，恢复升级前的镜像标签、数据和配置备份，再启动。不要仅降级镜像后继续共用未经核对的新数据库。

外部网盘暂无有效测试账号，本次不宣称这些平台实盘下载验证成功；站点可用性也会随网络和站点变动。Windows 本机没有 Docker 引擎，实际容器构建和运行验证由 GitHub Actions 执行。

构建方式参考 [Docker 官方先测试再推送流程](https://docs.docker.com/build/ci/github-actions/test-before-push/)，产物下载参考 [GitHub Actions 文档](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)。
