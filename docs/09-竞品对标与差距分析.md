### 明确不做的项及原因

- **PT 刷流 / 站点签到**：属于「薅站点资源」而非「看片」，且极易违反站点规则
  导致封号。CineFlow 定位是观影追剧，不做此类。
- **网盘签到领空间 / 跨盘秒传**：各家私有接口，维护成本极高而收益是几十 GB 空间，
  与 ADR-02（不逐家逆向）一致。
- **Web SSH**：与影视自动化无关，且给一个家用服务开 shell 是纯粹的安全负担。
- **逆向网盘客户端签名（夸克扫码登录）**：v1.8.0 实测夸克登录接口要求
  `x-pan-client-id` / `x-pan-tm` / `x-pan-token` 三个**签名过的客户端公参**。
  拿到扫码能力必须逆向签名算法——这与绕反爬（ADR-34）、绕付费墙（ADR-24）
  是同一件事：主动规避访问控制。而且签名一改就全线失效，
  等于给自己安排一个永久的军备竞赛。**明确不做**，并在界面与文档里
  如实标注「夸克不支持扫码」而不是写成已支持（ADR-38）。
  补偿方案是 Cookie 导入 + **即时校验**——粘完立刻知道有没有效，
  而不是先存下来等半夜任务失败。
- ~~**单站视频下载器**（如 bilibili-video-downloader ★1930）~~
  **→ v1.6.0 部分推翻**：原判断是「接单站下载器会让定位漂移，且每站接口都要单独维护」。
  维护成本这个顾虑是对的，但结论下错了——正确做法不是不做，而是**不自己写单站解析**。
  v1.6.0 接入 [yt-dlp](https://github.com/yt-dlp/yt-dlp)（该领域事实标准，
  抽取器覆盖 1700+ 站点、维护活跃），一次接入覆盖 B 站/YouTube/抖音/TikTok 等，
  维护成本转移给上游。定位漂移的风险则由**合规边界**约束：只下公开内容，
  长视频平台正片播放页在入口拒绝（ADR-24）。
- **VIP / 付费内容解析**（优酷 / 腾讯 / 爱奇艺 / 芒果 TV 正片，
  以及 Netflix / Disney+ / Hulu / HBO / Prime Video）：**明确不做**。
  这类内容在会员墙或区域授权之后，抓取等于绕过付费墙；市面上的"VIP 解析"接口
  本身也依赖盗取的会员票据。这不是技术难度问题，而是产品该不该做的问题（ADR-24）。
- **为无授权站点写定向爬虫**：用户提出的 7 个站点，v1.7.0 逐站实测后**分档处理**
  （M25）：能用通用适配器覆盖的就做预设（`yyets` 两阶段 API、
  `wp_film` 一份代码适配 3 个 WordPress 站），
  被反爬/微信公众号墙/限流挡住的**如实标注为受限或不可用，不假装能用**。
  仍然**不为单站写一次性爬虫**——改版即失效，且维护成本会压垮项目。
  7 站里只有 2 站真正出资源，这个比例本身就是"别写定向爬虫"的证据。
- ~~**豆瓣/猫眼榜单**：豆瓣没有公开 API、反爬严格~~
  **→ v1.7.0 部分推翻**：原判断里「没有公开 API」这半句是**错的**。
  实测 `https://movie.douban.com/j/subject_suggest?q=` 是可用的公开接口、
  **无需 API Key**、对中文作品命中率明显高于 TMDB。
  v1.7.0 据此把豆瓣接进**封面回退链**与 `GET /trending/douban`（M22）。
  「反爬严格」这半句是对的，所以没有改成主数据源，而是：
  ① 只作为站点自带元数据之后的**第二级回退**；② 缓存 6h；
  ③ 命中限流即退避 300s；④ 失败静默退回 TMDB / 占位色块，不影响搜索与下载。
  猫眼仍未接（票房榜与"能不能下到"关联弱）。
  这条修正也说明：ADR-06 的顾虑应该约束**依赖强度**，而不是直接判定不可用。

## 3. v1.4.0 选定范围（按依赖排序）

| 序 | 特性 | 解决的差距 | 为什么现在做 |
|---|---|---|---|
| A | **NFO 刮削 + 图片下载** | #6 | 入库后 Emby/Jellyfin/Plex 识别率的决定性因素；纯本地写文件，可完全离线测试 |
| B | **WebDAV 存储 Provider** | #10 | 一个协议覆盖 AList/Nextcloud/坚果云/群晖/TeraCLOUD；标准协议，抽象已就绪 |
| C | **网盘 STRM 同步 + 302 直链** | #7 #8 #9 | 竞品共识最高的方向，也是 CineFlow 最弱的一环 |
| D | **网盘分享追更订阅** | #4 #5 | quark-auto-save 3k star 的核心；把「一次性转存」升级为「持续追更」 |
| E | **洗版** | #11 | v1.3.0 已承诺的候选项 |
| F | **媒体分类归档** | #12 | 与 A 同属 organizer，一并做掉边际成本低 |

依赖关系：`B → C`（STRM 需要存储器列目录）、`A → F`（同在 organizer/scraper）、
`D` 依赖 v1.3.0 已有的 panstorage、`E` 依赖 library + subscribe。

### 每项的验收标准

| 特性 | 必须被证明 |
|---|---|
| A | 生成的 NFO 能被 Emby 识别（XML 结构符合规范）；无 TMDB 时降级为仅本地信息；图片下载失败不阻塞入库 |
| B | 假 WebDAV 服务器上跑通 list/mkdir/delete/download_url；`PROPFIND` XML 解析正确 |
| C | 全量生成 → 增量只处理变化 → 源文件消失后 STRM 被清理 → 302 端点返回 Location |
| D | 同一分享第二次巡检**不重复转存**；正则过滤/重命名生效；失效分享被标记并跳过 |
| E | 仅当新资源评分显著更高才替换；替换后旧文件按策略处理；不会无限洗版 |
| F | 动漫/纪录片/综艺能被正确归类；未知类型不乱归 |

## 4. v1.5.0 选定范围与结果

v1.4.0 关掉了全部 P0/P1「功能性」缺口后，剩下的差距集中在**治理与运维**。

| 序 | 特性 | 解决的差距 | 结果 |
|---|---|---|---|

| M12 | 多用户与三档权限 | #18 | ✅ admin/operator/viewer，服务端逐端点校验（ADR-19） |

| M14 | 下载器负载均衡 | #27 | ✅ 三策略 + 排后不剔除 + 失败换源（ADR-21） |
| M15 | 榜单自动订阅 | #22 | ✅ 有上限 + 记 handled_ids（ADR-23） |

用户点进去会一无所获。所以 §5 / M25 的验收标准定为**拿到可下载的链接条数**，

### 继续从 T3FAP 学到什么

| T3FAP 的做法 | CineFlow 的取舍 |
|---|---|

### 这一轮的教训

**两个真 bug 都不是靠读代码发现的，是靠冒烟测试打真实 HTTP 抓到的。**

其中 `verify=false` 那个后门尤其值得记下来：单元测试全绿、
代码逻辑看起来也合理（「提供一个跳过校验的开关」听着挺正常），
只有真的发一次 HTTP 请求才暴露出——任意字符串都能被写进站点记录**并启用该站点**，
把 ADR-40 整条绕过去。

另一个是 `int(x or -1)`：百度接口的成功值是 `0`，而 `0` 在 Python 里是假值，
被 `or` 直接吃掉换成了 `-1`，于是「成功」永远判不出来。这个坑在同一个文件里
踩了两次（`status` 和 `errno` 各一次）。

结论：**smoke_test 的价值不只是防回归，它还能发现设计层面的漏洞**——
因为它是唯一一个「像真实客户端那样说话」的检查。
同时，「用 `or` 兜默认值」这个习惯在处理 `0` / `""` / `[]` 是合法值的接口时是有害的，
已抽成 `_as_int()` 并写明原因。

## 9. v1.11.0 对标结论（下载器方向）

本轮围绕「下载器为什么调不通」做了针对性对标，**结论是我们缺的不是功能而是健壮性**。

### 9.1 从 MoviePilot 学到的两件事（都已落地）

`jxxghp/MoviePilot`（★11.6k）的 `app/modules/qbittorrent/qbittorrent.py` 里有两个
我们原先没有的设计，实测证明都是必需的：

| 它的做法 | 我们原先 | 为什么必须学 |
|---|---|---|
| `is_inactive()` + `reconnect()` 显式管理连接失效 | 缓存了 client 就永远复用 | qB 的 SID 会过期、重启会作废。不重连就表现为「一开始能用、过一阵全挂」，是本轮用户报障的**主因**（ADR-53） |
| `get_torrent_id_by_tag()` 用**唯一临时标签**定位刚提交的种子 | 前后 hash 集合取差集 | 差集在并发投递时**会认错**：实测同时加 3 个磁力，三次返回同一个 hash（ADR-54） |

### 9.2 刻意没学的部分

MoviePilot 的 qB 模块还有 `set_speed_limit` / `recheck_torrents` / `update_tracker` /
`get_content_layout` 等三十多个方法。**没有全抄**，因为本项目的下载器只承担
「投递 + 跟踪 + 删除」这三件事，限速与 tracker 管理应该在 qB 自己的界面里做——
搬过来只会得到一堆没人用、却要跟着 qB API 变化维护的代码。

同理，迅雷只做了 `add/get/list/remove`：`pause`/`resume` 在迅雷本地 CGI 上
没有对应接口，基类默认返回 `False`，**不假装支持**。

### 9.3 仍然缺的（记录，未做）

| 项 | 竞品共识度 | 判断 |
|---|---|---|
| 下载器**限速时段**（夜间跑满、白天限速） | 中 | P2，值得做。当前只能在下载器侧设 |
| 种子**做种/删种策略**（保种时长、比率） | 中高 | P2。属于 PT 保种场景，与「看剧」主线稍远 |
| 迅雷**云端离线兜底死种** | 低 | **不做**，需逆向签名 + 每日 3 次限额（ADR-51） |
| 下载器**分类目录自动映射**（按剧名建子目录） | 中 | 🟡 已有 `save_path` 分流到 tv/movies/others，但不按剧名建层 |
