### 明确不做的项及原因

- **PT 刷流 / 站点签到**：属于「薅站点资源」而非「看片」，且极易违反站点规则
  导致封号。CineFlow 定位是观影追剧，不做此类。
- **网盘签到领空间 / 跨盘秒传**：各家私有接口，维护成本极高而收益是几十 GB 空间，
  与 ADR-02（不逐家逆向）一致。
- **Web SSH**：与影视自动化无关，且给一个家用服务开 shell 是纯粹的安全负担。

## 3. v1.4.0 选定范围（按依赖排序）

| 序 | 特性 | 解决的差距 | 为什么现在做 |
|---|---|---|---|
| A | **NFO 刮削 + 图片下载** | #6 | 入库后 Emby/Jellyfin/Plex 识别率的决定性因素；纯本地写文件，可完全离线测试 |
| B | **WebDAV 存储 Provider** | #10 | 一个协议覆盖 AList/Nextcloud/坚果云/群晖/TeraCLOUD；标准协议，抽象已就绪 |
| C | **网盘 STRM 同步 + 302 直链** | #7 #8 #9 | 竞品共识最高的方向，也是 CineFlow 最弱的一环 |
| D | **网盘分享追更订阅** | #4 #5 | quark-auto-save 3k star 的核心；把「一次性转存」升级为「持续追更」 |
| E | **洗版** | #11 | v1.3.0 已承诺的候选项 |
| F | **媒体分类归档** | #12 | 与 A 同属 organizer，一并做掉边际成本低 |

依赖关系：`B → C`（STRM 需要存储器列目录）、`A → F`（同在 organizer/scraper）、
`D` 依赖 v1.3.0 已有的 panstorage、`E` 依赖 library + subscribe。

### 每项的验收标准

| 特性 | 必须被证明 |
|---|---|
| A | 生成的 NFO 能被 Emby 识别（XML 结构符合规范）；无 TMDB 时降级为仅本地信息；图片下载失败不阻塞入库 |
| B | 假 WebDAV 服务器上跑通 list/mkdir/delete/download_url；`PROPFIND` XML 解析正确 |
| C | 全量生成 → 增量只处理变化 → 源文件消失后 STRM 被清理 → 302 端点返回 Location |
| D | 同一分享第二次巡检**不重复转存**；正则过滤/重命名生效；失效分享被标记并跳过 |
| E | 仅当新资源评分显著更高才替换；替换后旧文件按策略处理；不会无限洗版 |
| F | 动漫/纪录片/综艺能被正确归类；未知类型不乱归 |
