### 明确不做的项及原因

- **PT 刷流 / 站点签到**：属于「薅站点资源」而非「看片」，且极易违反站点规则
  导致封号。CineFlow 定位是观影追剧，不做此类。
- **网盘签到领空间 / 跨盘秒传**：各家私有接口，维护成本极高而收益是几十 GB 空间，
  与 ADR-02（不逐家逆向）一致。
- **Web SSH**：与影视自动化无关，且给一个家用服务开 shell 是纯粹的安全负担。
- ~~**单站视频下载器**（如 bilibili-video-downloader ★1930）~~
  **→ v1.6.0 部分推翻**：原判断是「接单站下载器会让定位漂移，且每站接口都要单独维护」。
  维护成本这个顾虑是对的，但结论下错了——正确做法不是不做，而是**不自己写单站解析**。
  v1.6.0 接入 [yt-dlp](https://github.com/yt-dlp/yt-dlp)（该领域事实标准，
  抽取器覆盖 1700+ 站点、维护活跃），一次接入覆盖 B 站/YouTube/抖音/TikTok 等，
  维护成本转移给上游。定位漂移的风险则由**合规边界**约束：只下公开内容，
  长视频平台正片播放页在入口拒绝（ADR-24）。
- **VIP / 付费内容解析**（优酷 / 腾讯 / 爱奇艺 / 芒果 TV 正片，
  以及 Netflix / Disney+ / Hulu / HBO / Prime Video）：**明确不做**。
  这类内容在会员墙或区域授权之后，抓取等于绕过付费墙；市面上的"VIP 解析"接口
  本身也依赖盗取的会员票据。这不是技术难度问题，而是产品该不该做的问题（ADR-24）。
- **为无授权站点写定向爬虫**：用户提出新增 7 个资源站点。相比逐站写爬虫
  （改版即集体失效、且未获站点许可），更合适的方向是**打磨 `html_generic` 通用适配器
  + 提供抓取调试器**，把接站能力交给用户自己。已实测各站可抓性
  （`dygod` 是 GBK 编码需转码、`hdzu` 返回 403 有反爬）。
- **豆瓣/猫眼榜单**：榜单订阅只接 TMDB 与本地热度榜。
  豆瓣没有公开 API、反爬严格，抓取方案会频繁失效——
  与 ADR-06「不依赖脆弱的第三方页面结构」同一顾虑。

## 3. v1.4.0 选定范围（按依赖排序）

| 序 | 特性 | 解决的差距 | 为什么现在做 |
|---|---|---|---|
| A | **NFO 刮削 + 图片下载** | #6 | 入库后 Emby/Jellyfin/Plex 识别率的决定性因素；纯本地写文件，可完全离线测试 |
| B | **WebDAV 存储 Provider** | #10 | 一个协议覆盖 AList/Nextcloud/坚果云/群晖/TeraCLOUD；标准协议，抽象已就绪 |
| C | **网盘 STRM 同步 + 302 直链** | #7 #8 #9 | 竞品共识最高的方向，也是 CineFlow 最弱的一环 |
| D | **网盘分享追更订阅** | #4 #5 | quark-auto-save 3k star 的核心；把「一次性转存」升级为「持续追更」 |
| E | **洗版** | #11 | v1.3.0 已承诺的候选项 |
| F | **媒体分类归档** | #12 | 与 A 同属 organizer，一并做掉边际成本低 |

依赖关系：`B → C`（STRM 需要存储器列目录）、`A → F`（同在 organizer/scraper）、
`D` 依赖 v1.3.0 已有的 panstorage、`E` 依赖 library + subscribe。

### 每项的验收标准

| 特性 | 必须被证明 |
|---|---|
| A | 生成的 NFO 能被 Emby 识别（XML 结构符合规范）；无 TMDB 时降级为仅本地信息；图片下载失败不阻塞入库 |
| B | 假 WebDAV 服务器上跑通 list/mkdir/delete/download_url；`PROPFIND` XML 解析正确 |
| C | 全量生成 → 增量只处理变化 → 源文件消失后 STRM 被清理 → 302 端点返回 Location |
| D | 同一分享第二次巡检**不重复转存**；正则过滤/重命名生效；失效分享被标记并跳过 |
| E | 仅当新资源评分显著更高才替换；替换后旧文件按策略处理；不会无限洗版 |
| F | 动漫/纪录片/综艺能被正确归类；未知类型不乱归 |

## 4. v1.5.0 选定范围与结果

v1.4.0 关掉了全部 P0/P1「功能性」缺口后，剩下的差距集中在**治理与运维**。
v1.5.0 据此选了 6 项：

| 序 | 特性 | 解决的差距 | 结果 |
|---|---|---|---|
| M11 | 可编辑运行期配置 | #28 | ✅ 51 项白名单，先全校验再落库（ADR-18 修正 ADR-05） |
| M12 | 多用户与三档权限 | #18 | ✅ admin/operator/viewer，服务端逐端点校验（ADR-19） |
| M13 | 站点健康巡检 | #26 | ✅ 真搜一次抓 Cookie 静默失效（ADR-20） |
| M14 | 下载器负载均衡 | #27 | ✅ 三策略 + 排后不剔除 + 失败换源（ADR-21） |
| M15 | 榜单自动订阅 | #22 | ✅ 有上限 + 记 handled_ids（ADR-23） |
| M16 | 自定义过滤规则组 | #25 | ✅ 有序分层而非调权重（ADR-22） |

其中 #26 / #27 做完后**反超了对标样本**：多数项目的站点检查只探首页
（对 Cookie 过期无感），且没有下载器级别的调度策略。

## 5. v1.6.0 选定范围与结果

本轮输入不是差距矩阵，而是**用户实际使用后的 5 条反馈**。
其中一条是真 bug，两条是体验缺口，两条被拒绝：

| 序 | 用户诉求 | 结果 |
|---|---|---|
| M17 | 「站点都启用了却只有 PanSou 的资源」 | ✅ **真 bug**：聚合层只做全局截断，小站被挤出窗口 + 失败静默。改轮转交错合并 + 每站诊断（ADR-25） |
| M18 | 「热榜改画板、要封面、要真实站点资源」 | ✅ 封面/评分取自站点自带元数据，**不依赖 TMDB**（ADR-26） |
| M19 | 「集成 bilibili/YouTube/抖音/TikTok 下载」 | ✅ 接 yt-dlp，**推翻了 §2 原先"不做单站下载器"的判断**（见上） |
| — | 「适配优酷/腾讯/爱奇艺/芒果 TV 解析」 | ❌ 绕过会员付费墙，明确不做（ADR-24） |
| — | 「新增 7 个资源站点」 | ⏸ 建议走通用化路线（`html_generic` + 抓取调试器），待用户确认 |

额外修掉一个 UI 点检发现的真 bug：慢请求返回后覆盖已切走的页面（ADR-27）。

**这一轮的教训**：M17 那条反馈用户说的是「只有 panso 的资源」，
听起来像"其他站点没配好"，实际是**我们自己的聚合逻辑缺陷**。
用户报的现象和根因往往不在同一层，必须逐站实测直连才能定位——
这也是为什么本轮把每站诊断做成**用户可见**的，而不是只写进日志。
