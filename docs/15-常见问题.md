# 15 · 常见问题 FAQ

> README 里的常见问题合集。
> 部署类问题请转 [07-运维手册.md](07-运维手册.md) 与 [11-飞牛NAS部署指南.md](11-飞牛NAS部署指南.md)。

## ❓ 常见问题

<details>
<summary><b>下载完成了但没有入库？</b></summary>

99% 是**路径不一致**。CineFlow 需要能直接访问下载器落盘的文件。
请确认 CineFlow 容器的 `/downloads` 与下载器容器的 `/downloads` 指向宿主机同一目录。
可在「运行日志」页搜 `未找到下载文件` 确认。
</details>

<details>
<summary><b>硬链接失败 / 提示已降级为复制？</b></summary>

硬链接要求源和目标在**同一文件系统**。请把 `downloads` 与 `library` 放在同一个卷
（如群晖同一个 `/volume1`）。做不到就设 `CF_TRANSFER_MODE=copy`。
</details>

<details>
<summary><b>没有 TMDB API Key 能用吗？</b></summary>

能。解析引擎是纯本地的，搜索、过滤、下载、命名、入库全部正常，
只是没有海报、简介，且「总集数」需要你在订阅时手填。
</details>

<details>
<summary><b>搜索结果为空？</b></summary>

依次检查：① 站点管理里有没有**启用**的索引器/盘搜（示例站点默认全禁用）；
② 点「测试」看连通性；③ 看「运行日志」页；④ 是否被 `EXCLUDE_KEYWORDS` 或 `MIN_SEEDERS` 过滤光了。
</details>

<details>
<summary><b>网盘资源怎么下载？</b></summary>

网盘分享链接无法交给 BT 下载器。CineFlow 会登记为待处理任务并保留提取码，
你可以在「下载任务」页点按钮手动转存；或启用 `pan_transfer` 插件，
配置一个转存 Webhook（如自建 alist / cloud-saver 服务）实现全自动。
</details>

<details>
<summary><b>忘记密码了？</b></summary>

删掉 `data/cineflow.db` 里的 users 表记录，或直接删库重启（会丢历史数据）；
也可以设 `CF_SUPERUSER` 为一个新用户名后重启，会自动创建新管理员。
</details>

<details>
<summary><b>群晖 / 威联通文件权限报错？</b></summary>

在 compose 里把 `PUID` / `PGID` 改成你的实际用户（SSH 执行 `id` 查看），
并确保该用户对挂载目录有读写权限。
</details>

<details>
<summary><b>视频追更一直没有新视频？（v1.12.0）</b></summary>

按这个顺序查：

1. **先用「预览」**：它不落库，直接告诉你能不能解析、拿到几条。
2. **首次检查故意不下载**：勾了「跳过已有」时首检只登记 ID，**第二轮**才开始下新的。
3. **B 站拿不到标题**：yt-dlp 扁平提取对 B 站只返 ID，所以**标题过滤规则在 B 站上等于不生效**
   （设计上放行）。靠标题控量的话，B 站请改用 `max_per_run`。YouTube 正常。
4. **可能被自动暂停了**：连续 5 次失败自动 `paused`，修好后点「重置失败计数」。
5. **失败的视频不会自动重试**（否则会堵死队列），要重试请手动下载那一条。

详见 [07-运维手册.md](07-运维手册.md) §9.2。
</details>

<details>
<summary><b>配了限速时段却没生效？（v1.12.0）</b></summary>

常见三种情况：

- **等下一轮**：`cineflow.speed_limit` 是 10 分钟一轮，不想等就点卡片上的「立即应用」。
- **下载器不支持**：迅雷与 yt-dlp 没有全局限速接口，结果里会如实显示 `skipped`，不是故障。
- **版本太老**：`23:00-07:00` 这种**跨午夜**区间在 v1.12.0 之前恒不生效（朴素比较的经典 bug），升级即可。

反过来，如果你想在下载器里手动管限速，请把 `CF_SPEED_LIMIT_INTERVAL_MINUTES`
设为 `0` 关掉这个任务——否则你手动调的值会在 10 分钟内被时段值盖掉（幂等下发）。
</details>

<details>
<summary><b>新番日历是空的 / 封面全白？（v1.12.0）</b></summary>

- **整个空**：`api.bgm.tv` 不通。`curl https://api.bgm.tv/calendar` 验证；不通则该页签不可用，不影响其他页签。
- **有条目但封面全白**：你走 HTTPS 访问，而封面原始地址是 `http://`（实测 113/113 都是）。
  v1.12.0 已统一改写为 `https://`；仍白就检查 `bgm.tv` 是否在图片代理白名单里。
- **显示日文名**：该番 Bangumi 上没有中文名（约 10%），回退日文原名是正常行为。
</details>

<details>
<summary><b>升级后封面比以前少了？（v1.12.0）</b></summary>

是刻意的。豆瓣匹配加了 **60 分门槛 + 年份校验**，匹配不确定时**返回空而不是硬给一张**。
错封面会让人下错片子，空白封面一眼就知道是缺数据。

想看某条为什么没匹配上，接口会返回 `match_score` / `match_confidence`：

```bash
curl -H "X-API-Token: your-token" \
  "http://127.0.0.1:6060/api/v1/trending/douban?title=片名&year=2024"
```
</details>

<details>
<summary><b>通知太吵，能只收失败吗？（v1.12.0）</b></summary>

能。在渠道的 options 里加 `events` / `events_exclude` / `min_level`：

```json
{"events": ["download.failed", "site.unhealthy"], "min_level": "warning"}
```

支持前缀通配，`download.*` / `download.` / `download` 三种写法等价
（v1.12.1 起；此前只认带尾点的 `download.`，按 `download.*` 配会一条都收不到）。
**三个都不填 = 全收**（老配置行为完全不变）。
同一条告警的重复间隔由 `CF_NOTIFY_ALERT_COOLDOWN_MINUTES`（默认 360 分钟）控制。
事件名写错不会报错，只会静默收不到 —— 合法名见
[开发指南 → 可订阅事件](14-开发指南.md#可订阅事件)。
</details>

<details>
<summary><b>Docker 更新了镜像，界面里的版本号还是旧的？（v1.15.0 修复）</b></summary>

**根因不是构建失败，而是 compose 的默认行为。** `:latest` 是**可变 tag**，
`docker compose up -d` 只要本地存在同名镜像就直接复用，
**不会**去比对远端 digest —— 表现就是「GitHub 已经是新版，容器里还是旧版本号」。

v1.15.0 起 `docker-compose.yml` 与 `docker-compose.fnos.yml` 都加了
`pull_policy: always`，每次 `up` 都会比对 digest（没更新时只有几十 KB 的
manifest 请求，不会重复下载层）。用的是旧 compose 文件的话，手动拉一次即可：

```bash
docker compose pull && docker compose up -d
# 确认容器里的版本
curl -s http://127.0.0.1:6060/api/health
```

想**锁定**某个版本别用 `latest`：把 tag 换成 `sha-xxxxxxx`（Actions 每次构建都会打），
并把 `pull_policy` 改成 `missing`。
`docker-compose.build.yml`（源码自建）刻意**没有**这一行 —— 那里应当用本地构建产物。
</details>

<details>
<summary><b>搜索很慢，还提示某个站「已暂时跳过」？（v1.15.0）</b></summary>

这是**熔断**在保护你。聚合搜索要等最慢的站返回，所以一个连不通的站会
决定所有人的等待时间（实测 YouTube 连不上时吃满 25s 预算却返回 0 条，
而其余站 5s 内就全回来了）。

一个站连续 3 次「吃满超时预算且零结果」就会被冷却 10 分钟，冷却期内直接跳过，
搜索立刻回到「最慢的健康站」的速度。**慢但有结果的站不会被熔断**
（盘搜要 19s 但能给几千条，它是最有价值的站之一）。

- 看谁在冷却：`GET /api/v1/search/breaker`
- 刚改完站点地址/代理不想等：`POST /api/v1/search/breaker/reset?site=站点名`
- 三个开关：`CF_SEARCH_BREAKER_ENABLED` / `CF_SEARCH_BREAKER_THRESHOLD` /
  `CF_SEARCH_BREAKER_COOLDOWN_MINUTES`（设 `0` = 只计数不熔断），设置页可直接改。

熔断状态只在内存里，**重启即清空**（重启后重新给每个站一次机会）。
</details>

<details>
<summary><b>点了下载弹「已加入下载队列」，但任务是红色失败？（v1.15.0 修复）</b></summary>

这是 v1.15.0 之前的一个**假成功**：接口无条件返回 `success: true`，
所以哪怕下载器把任务拒了，界面也弹绿色提示 —— 真因（下载器连不上）
从来没出现在你眼前。

现在 `success` 反映**投递的真实结局**：下载器拒绝会弹**红色**并直接写出
下载器名与原因；网盘资源缺账号/aria2 时是 `pending`，会弹**黄色**提示下一步做什么。

想在**点击之前**就知道哪类资源现在下不了，看 `GET /api/v1/downloads/routing`：
它会列出每类资源该走哪个下载器、现在缺什么，以及**哪些下载器巡检显示连不上**
（这一条会提示你去「站点健康」页重新巡检）。
</details>

<details>
<summary><b>新番日历的封面偶尔是灰色占位块（随机裂图）？（v1.15.0 修复）</b></summary>

v1.15.0 之前，日历卡片用的是 Bangumi 的 **`images.large`（未压缩原图）**：
实测单张 **300 KB ~ 3 MB、最慢 21 秒**。一屏 30 张原图并发时，会有一部分
打爆图片代理的 15s 上游超时 → 后端返回 502 → 前端退占位色块，
表现就是**随机几张裂图，刷新一下换成另外几张裂**。

而榜单卡片封面显示宽度只有 **~120px**，原图的像素根本用不上。
同一张封面的 `common` 尺寸只有 **11 KB / 230 ms**：

| 尺寸 | 体积 | 耗时 |
|---|---|---|
| `large`（原图） | 937 KB | 13216 ms |
| `common`（现用） | **11 KB** | **600 ms** |

现在按 `COVER_SIZE_PRIORITY` 优先取 `common`，一屏封面的总传输量从
约 20 MB 降到约 0.3 MB。

**还有第二个原因**：`lain.bgm.tv` 的 TLS 连接实测会被**间歇性掐断**
（同一 URL 三连的结果是 `EXC / EXC / 200`，报错 `SSL: UNEXPECTED_EOF_WHILE_READING`
—— 重试就成功，说明是链路干扰不是图床挂了）。图片代理原本对非豆瓣图床
**零重试**，一次抖动就 502。现在每个地址会重试 3 次（只针对连接失败，
403/404 不重试）。两处修完后，实测 ui_check 的失败请求数 **24 → 0**。

如果你所在网络对 `bgm.tv` 干扰严重，可给 CineFlow 配 `CF_HTTP_PROXY`。
</details>

<details>
<summary><b>换页时内容区空着好几秒才出来，但后端日志显示很快？（v1.15.0 修复）</b></summary>

这是**浏览器连接池被封面图占满**，不是后端慢（详见 ADR-73）。

走后端代理的封面（豆瓣 / Bangumi）和 API 是**同源**的，而浏览器对同一域名
只开约 **6 条**并发连接。逛完热度排行的几个分类，就能攒下几十个还在飞的
图片请求 —— 于是下一页要用的 `/api/v1/...` **只能排在这些图片后面**。

实测：逛完 7 个分类再进「定时任务」，正文长度 `+2s..+8s` 一直是 169，
`+10s` 才变 2031，而后端接口本身只用 **8ms**；切页瞬间仍在飞的 **29 个**
请求**全部**是 `/api/v1/images/proxy`。

现在整屏重绘后会主动中止**已经不在页面上**的封面请求，连接立刻还给 API。
如果你在 v1.15.0 之前遇到过「某一页打不开、刷新就好」，基本都是这个。
</details>

<details>
<summary><b>切了一次页面后，新页面看得见但点不动（像卡死了）？（v1.15.0 修复）</b></summary>

弹窗遮罩挂在 `#modal-root`，而换页只重绘页面容器，**遮罩会原地留下**并
覆盖全屏 —— 于是新页面看得见却点不动，而刷新一下就好，
几乎不可能联想到「上一页有个没关的弹窗」。

复现路径（v1.15.0 之前）：订阅页打开「新增订阅」→ 不关弹窗，点侧边栏去设置页
→ 设置页任何按钮都点不到。

现在每次换页都会统一关掉遗留弹窗。
</details>

<details>
<summary><b>qBittorrent 提示「用户名或密码错误」，但密码明明是对的？（v1.16.0 修复）</b></summary>

**先别改密码 —— 大概率是 qBittorrent 根本没启动。**

v1.16.0 之前的代码把**任何**非 200 响应都归成「用户名或密码错误」。
实测：本机 8080 端口**没有任何进程监听**时，中间的代理/端口转发仍会回
**HTTP 502**（而不是干脆的连接被拒），于是界面催你去查密码，
真相却是服务没起来。这类「把 A 故障报成 B 故障」的提示比不报更糟 ——
它会让整个排查方向跑偏。

现在按状态码分档，消息里会明确写出来：

| 现象 | 提示 | 该怎么做 |
|---|---|---|
| 服务没启动 / 地址端口填错 | 「qBittorrent 无响应（HTTP 502）：服务可能没启动，或地址/端口填错了（当前 …）。**这不是密码问题**」 | 启动 qB；核对 WebUI 端口 |
| 密码真的错 | 「用户名或密码错误（HTTP 200）」 | 改账号密码 |
| 正常 | 「连接正常，版本 v4.6.5」 | — |

自查：浏览器直接打开你填的那个地址，能不能看到 qB 的 WebUI 登录页。
打不开就是服务/地址问题，与密码无关。
</details>

<details>
<summary><b>扫码登录百度网盘提示「登录成功」，但网盘管理里看不到它？（v1.16.0 修复）</b></summary>

v1.16.0 之前这是一个**真的 bug**，不是你操作错了。

百度的扫码登录很早就实现了，但缺少对应的「存储 Provider」，
于是登录成功后建出来的是一条**僵尸站点**：站点列表里有、状态写着「登录成功」、
`enabled` 也是 true，但网盘总览里查不到它，转存 / 浏览目录 / 保活巡检
全部**静默跳过**——你唯一能得到的信号就是那句「登录成功」。

v1.16.0 补上了 `baidu` 存储 Provider（列目录/容量/改名/移动/复制/删除/
盘内搜索/直链/保活/转存），并加了门禁：**每个网盘预设都必须能造出实例**，
防止再出现同类问题。

如果你在旧版本上已经扫过码，升级后那条站点会自动可用，不需要重新登录
（Cookie 早就写进去了）。若提示 Cookie 过期，重新扫一次即可。
</details>

<details>
<summary><b>115 网盘里改名/移动明明提示「已重命名」，刷新后却没变？（v1.16.0 修复）</b></summary>

也是**真 bug**。115 的实现返回的是 `(是否成功, 原因)` 这样的元组，
而服务层按布尔值判断 —— **非空元组在 Python 里恒为真**，
于是 `(False, '115 拒绝了改名请求')` 被判成成功，界面弹绿色「已重命名」。

v1.16.0 起统一解包，并且**把 115 给出的真实原因直接显示出来**
（比如「目标目录不存在」「115 拒绝了改名请求」），
比原来那句笼统的「失败（检查权限）」有用得多。
</details>

<details>
<summary><b>升级后站点列表里还留着一堆搜不出东西的站（v1.16.1 修复）</b></summary>

v1.16.0 把内置示例站点从 27 条瘦身到 20 条（删掉的都是实测「详情页取不到真链接」的站），
但当时**只有全新安装的用户能拿到干净清单**：写库逻辑按站点名「缺了就补」，
从来不删，所以升级用户库里那 10 条老站点原地不动，其中一部分还是启用状态，
表现就是「搜索很慢，而且这些站永远 0 条」。

v1.16.1 起启动时会自动清理一次，日志里能看到：

```
已清理 8 个下线的示例站点：人人影视 YYeTs（搜索页不含关键词…）；…
```

**只清理「你没碰过」的记录。** 如果你改过某站的地址（比如换成了能用的镜像域名），
或者给它填过 Cookie / 账号 / API Key，程序**不会**删它 —— 那是你的配置，
删掉属于丢数据。这种情况会在启动日志里以 WARNING 列出来：

```
WARNING 以下示例站点已被下线（实测取不到可用链接），但检测到你改过配置，
        因此保留，请自行确认是否还需要：聚合BD、HDZU 高清组
```

看到这条就自己判断：镜像域名真能搜到东西就留着，搜不到就在站点管理里手工删掉。

清理只做一次并会记录在案，所以你之后**手工重建同名站点不会被再删一遍**。
</details>

<details>
<summary><b>某个资源站搜什么都有结果，连乱码都有？（站点配置问题）</b></summary>

说明搜索**根本没生效**，你抓到的其实是**首页**。常见两个原因：

1. **该站的搜索只认 POST**（EmpireCMS 一类的国内老站居多）。
   用 `GET /?s=关键词` 会静默返回首页：HTTP 200、页面看着完全正常。
   改用 `search_method: "POST"` + `search_data`，见
   [docs/10-站点接入指南.md](10-站点接入指南.md) 的「POST 表单搜索」。
2. **该站的搜索参数不参与过滤**（比如某些站的 `?keyword=` 只是回填到筛选框）。
   这种站无论怎么配都拿不到「和关键词相关」的结果，建议直接不要启用。

**一分钟自查法**：用两个完全不同的关键词各搜一次，
**如果返回页面的字节数一模一样，就说明抓的是首页**。
或者干脆搜一串乱码 —— 正常的站应该返回 0 条。
</details>
<details>
<summary><b>为什么搜索结果是一点一点出现的？（v1.17.0）</b></summary>

这是**刻意改成这样的**。以前要等所有站点都返回才渲染一次，
整页等待时间等于**最慢那个站**的耗时（本地 9 个站实测 3.5s），
哪怕最快的站 300ms 就出货了你也得干等；开的站越多越容易碰上一个慢站。

现在改成**每个站一返回就立刻显示它的结果**（实测 1.7s 就能看到第一批）。
所以你会看到：

- 标题旁的「搜索中 3/9 站」是**进度**，不是出错；
- 结果条数会往上跳，排序也可能随之变化（后来的站可能有更高分的资源）；
- 列表暂时空着时文案是「正在搜索，结果会陆续出现…」，
  只有全部搜完仍然为空才会说「没有匹配的资源」。

**如果你部署在 Nginx 一类反向代理后面，却发现结果仍然是一次性出现的**，
是代理把响应缓冲了。CineFlow 已经在响应里带了 `X-Accel-Buffering: no`，
若仍无效，请在你的 Nginx location 里补上：

```nginx
proxy_buffering off;
proxy_cache off;
chunked_transfer_encoding on;
```
</details>

<details>
<summary><b>从 Jackett 导入的站点搜不到东西？（v1.17.0）</b></summary>

按顺序查（大多数情况根本不是 CineFlow 的问题）：

1. **先在 Jackett 界面里自己搜一次**。Jackett 搜不到的 CineFlow 一定搜不到，
   去 Jackett 里看那个 indexer 是不是要登录/已失效。
2. **私有站的用户名密码/Cookie 要填在 Jackett 里**，不在 CineFlow 里填。
3. **看搜索页的「站点情况」**：会写明每个站是空结果、超时还是报错。
4. **别手工给地址结尾加 `/api`**。导入的地址应形如
   `.../indexers/<id>/results/torznab`，CineFlow 会自己补 `/api`；
   手动加了就变成 `/api/api` → 404，症状是「这个站永远 0 条但不报错」。
   改坏了删掉重新导入即可。
5. **地址填了 `127.0.0.1` 却用 Docker 部署**：容器里的 `127.0.0.1` 是容器自己。
   同一 compose 内写 `http://jackett:9117`，否则写宿主机 IP。
</details>

<details>
<summary><b>加了 RSS 源却一直没反应？（v1.18.0）</b></summary>

按顺序查，前两条能解释绝大多数情况：

1. **首次拉取是刻意不下载的**。默认勾选了「首次拉取只记账不补历史」，
   第一轮只把流里现有条目记成"已处理"，从**下一轮起**才下新增。
   界面上那条源的最近巡检会写明「首次拉取已记录 N 条历史条目」。
   想立刻补历史：编辑该源勾「清空已处理记录」并取消「首次拉取只记账」。
2. **聚合流只下命中订阅的**。蜜柑「我的番组」/ dmhy 分类流里混着几十部作品，
   聚合模式下会逐条识别标题再匹配你的订阅 —— 你没订阅的番不会下。
   点该源的「试运行」，`skipped` 里会逐条写明「未命中任何活跃订阅」。
   如果你就是想整条流全下，把「这是聚合流」关掉（⚠️ 会把整站新番拖回来）。
3. **地址不是 RSS**。点「预览」，解析不出条目会直接告诉你。
   需要登录的源（PT 个人订阅地址）要填 Cookie。
4. **定时任务被关了**。页面上的「巡检节奏」卡片会显示「已关闭 / 未注册」，
   在那里改周期或点「立即执行」。
5. **该订阅已经没有缺集了**。试运行的 `skipped` 会写「该订阅已无缺集」。
6. **连续失败 5 次会自动停用**，列表里会显示「已停用」+ 失败次数。
   修好原因后编辑并勾「清除失败计数」，它会**一并恢复启用**。
</details>

<details>
<summary><b>RSS 里的资源体积和做种数都是 0 / 结果被全部过滤掉？（v1.18.0）</b></summary>

**多数番剧 RSS 本身就不提供做种数**（蜜柑、动漫花园都不给），
体积也可能只写在正文里。点页面上的「字段差异说明」能看到逐站对照表。

所以 RSS 追新在匹配订阅时会**主动把最小做种数放宽为 0**，
其余过滤条件（分辨率、字幕、排除词）照常生效 ——
否则你在设置里配的 `CF_MIN_SEEDERS` 会把整条番剧流滤光，
而界面上只会显示"0 条"，看不出原因。

想要**带做种数**的源就用 Nyaa（`nyaa:seeders`）。
另外：v1.18.0 修了一个静默缺陷 —— 此前 Nyaa 系 RSS 的体积与做种数**恒为 0**，
因为它把这些字段放在 `nyaa:` 命名空间里、而 `<enclosure>` 是空的。
如果你之前加过 Nyaa 的 RSS 站点却觉得"这个站的资源永远排最后"，就是这个原因。
</details>

<details>
<summary><b>检查更新说「版本号相同，但上游主干有新提交」是什么意思？（v1.18.0）</b></summary>

意思是：你的版本号和主干一样，但主干上又提交了新内容、**还没有发新版本号**。

本仓库目前**没有发布任何 Release**，所以更新检测走的是"读主干"这条路
（弹窗里的**判定依据**会写 `branch`）。这样做是为了避免一个更糟的结果：
只按 Release 比对的实现，在没有 Release 的仓库上会**永远回答"已是最新版本"** ——
一个不报错、却永远给出错误结论的假功能。

要不要更新看你：这类提交通常是修复或文档。想拿到就按下面那条 FAQ 更新。
</details>

<details>
<summary><b>Docker 部署怎么更新？为什么没有「一键更新」按钮？（v1.18.0）</b></summary>

容器里跑的程序**无法替换自己的镜像**，所以检查更新弹窗会显示
`can_apply=false` 并给出可直接复制的命令：

```bash
cd /vol1/docker/cineflow          # 你的 compose 目录
docker compose pull
docker compose up -d
# 飞牛：docker compose -f docker-compose.fnos.yml pull && up -d
```

数据都在挂载的 `data/` 目录里，升级不会丢配置与数据库。

**为什么不做"容器内一键更新"**：那需要把宿主机的 `/var/run/docker.sock`
挂进容器，等于把**宿主机的完整控制权**交给本进程 ——
一个追剧工具不该要这种权限（它还会执行你配的站点规则、调 AI 分析外部页面）。
我们选择如实说"我换不了自己的镜像"，而不是用一个高危挂载换取便利。

**源码部署**（目录里有 `.git`）则可以点「执行更新」，它只跑
`git pull --ff-only`：**不 merge、不 `reset --hard`**。
本地有未提交改动时会如实中止并列出改了哪些文件 ——
自动 merge 会产生你看不懂的冲突，`reset --hard` 直接丢掉你的修改。
更新完需要重启服务生效。
</details>
