# 15 · 常见问题 FAQ

> README 里的常见问题合集。
> 部署类问题请转 [07-运维手册.md](07-运维手册.md) 与 [11-飞牛NAS部署指南.md](11-飞牛NAS部署指南.md)。

## ❓ 常见问题

<details>
<summary><b>下载完成了但没有入库？</b></summary>

99% 是**路径不一致**。CineFlow 需要能直接访问下载器落盘的文件。
请确认 CineFlow 容器的 `/downloads` 与下载器容器的 `/downloads` 指向宿主机同一目录。
可在「运行日志」页搜 `未找到下载文件` 确认。
</details>

<details>
<summary><b>硬链接失败 / 提示已降级为复制？</b></summary>

硬链接要求源和目标在**同一文件系统**。请把 `downloads` 与 `library` 放在同一个卷
（如群晖同一个 `/volume1`）。做不到就设 `CF_TRANSFER_MODE=copy`。
</details>

<details>
<summary><b>没有 TMDB API Key 能用吗？</b></summary>

能。解析引擎是纯本地的，搜索、过滤、下载、命名、入库全部正常，
只是没有海报、简介，且「总集数」需要你在订阅时手填。
</details>

<details>
<summary><b>搜索结果为空？</b></summary>

依次检查：① 站点管理里有没有**启用**的索引器/盘搜（示例站点默认全禁用）；
② 点「测试」看连通性；③ 看「运行日志」页；④ 是否被 `EXCLUDE_KEYWORDS` 或 `MIN_SEEDERS` 过滤光了。
</details>

<details>
<summary><b>网盘资源怎么下载？</b></summary>

网盘分享链接无法交给 BT 下载器。CineFlow 会登记为待处理任务并保留提取码，
你可以在「下载任务」页点按钮手动转存；或启用 `pan_transfer` 插件，
配置一个转存 Webhook（如自建 alist / cloud-saver 服务）实现全自动。
</details>

<details>
<summary><b>忘记密码了？</b></summary>

删掉 `data/cineflow.db` 里的 users 表记录，或直接删库重启（会丢历史数据）；
也可以设 `CF_SUPERUSER` 为一个新用户名后重启，会自动创建新管理员。
</details>

<details>
<summary><b>群晖 / 威联通文件权限报错？</b></summary>

在 compose 里把 `PUID` / `PGID` 改成你的实际用户（SSH 执行 `id` 查看），
并确保该用户对挂载目录有读写权限。
</details>

<details>
<summary><b>视频追更一直没有新视频？（v1.12.0）</b></summary>

按这个顺序查：

1. **先用「预览」**：它不落库，直接告诉你能不能解析、拿到几条。
2. **首次检查故意不下载**：勾了「跳过已有」时首检只登记 ID，**第二轮**才开始下新的。
3. **B 站拿不到标题**：yt-dlp 扁平提取对 B 站只返 ID，所以**标题过滤规则在 B 站上等于不生效**
   （设计上放行）。靠标题控量的话，B 站请改用 `max_per_run`。YouTube 正常。
4. **可能被自动暂停了**：连续 5 次失败自动 `paused`，修好后点「重置失败计数」。
5. **失败的视频不会自动重试**（否则会堵死队列），要重试请手动下载那一条。

详见 [07-运维手册.md](07-运维手册.md) §9.2。
</details>

<details>
<summary><b>配了限速时段却没生效？（v1.12.0）</b></summary>

常见三种情况：

- **等下一轮**：`cineflow.speed_limit` 是 10 分钟一轮，不想等就点卡片上的「立即应用」。
- **下载器不支持**：迅雷与 yt-dlp 没有全局限速接口，结果里会如实显示 `skipped`，不是故障。
- **版本太老**：`23:00-07:00` 这种**跨午夜**区间在 v1.12.0 之前恒不生效（朴素比较的经典 bug），升级即可。

反过来，如果你想在下载器里手动管限速，请把 `CF_SPEED_LIMIT_INTERVAL_MINUTES`
设为 `0` 关掉这个任务——否则你手动调的值会在 10 分钟内被时段值盖掉（幂等下发）。
</details>

<details>
<summary><b>新番日历是空的 / 封面全白？（v1.12.0）</b></summary>

- **整个空**：`api.bgm.tv` 不通。`curl https://api.bgm.tv/calendar` 验证；不通则该页签不可用，不影响其他页签。
- **有条目但封面全白**：你走 HTTPS 访问，而封面原始地址是 `http://`（实测 113/113 都是）。
  v1.12.0 已统一改写为 `https://`；仍白就检查 `bgm.tv` 是否在图片代理白名单里。
- **显示日文名**：该番 Bangumi 上没有中文名（约 10%），回退日文原名是正常行为。
</details>

<details>
<summary><b>升级后封面比以前少了？（v1.12.0）</b></summary>

是刻意的。豆瓣匹配加了 **60 分门槛 + 年份校验**，匹配不确定时**返回空而不是硬给一张**。
错封面会让人下错片子，空白封面一眼就知道是缺数据。

想看某条为什么没匹配上，接口会返回 `match_score` / `match_confidence`：

```bash
curl -H "X-API-Token: your-token" \
  "http://127.0.0.1:6060/api/v1/trending/douban?title=片名&year=2024"
```
</details>

<details>
<summary><b>通知太吵，能只收失败吗？（v1.12.0）</b></summary>

能。在渠道的 options 里加 `events` / `events_exclude` / `min_level`：

```json
{"events": ["download.failed", "site.unhealthy"], "min_level": "warning"}
```

支持前缀通配，`download.*` / `download.` / `download` 三种写法等价
（v1.12.1 起；此前只认带尾点的 `download.`，按 `download.*` 配会一条都收不到）。
**三个都不填 = 全收**（老配置行为完全不变）。
同一条告警的重复间隔由 `CF_NOTIFY_ALERT_COOLDOWN_MINUTES`（默认 360 分钟）控制。
事件名写错不会报错，只会静默收不到 —— 合法名见
[开发指南 → 可订阅事件](14-开发指南.md#可订阅事件)。
</details>

<details>
<summary><b>Docker 更新了镜像，界面里的版本号还是旧的？（v1.15.0 修复）</b></summary>

**根因不是构建失败，而是 compose 的默认行为。** `:latest` 是**可变 tag**，
`docker compose up -d` 只要本地存在同名镜像就直接复用，
**不会**去比对远端 digest —— 表现就是「GitHub 已经是新版，容器里还是旧版本号」。

v1.15.0 起 `docker-compose.yml` 与 `docker-compose.fnos.yml` 都加了
`pull_policy: always`，每次 `up` 都会比对 digest（没更新时只有几十 KB 的
manifest 请求，不会重复下载层）。用的是旧 compose 文件的话，手动拉一次即可：

```bash
docker compose pull && docker compose up -d
# 确认容器里的版本
curl -s http://127.0.0.1:6060/api/health
```

想**锁定**某个版本别用 `latest`：把 tag 换成 `sha-xxxxxxx`（Actions 每次构建都会打），
并把 `pull_policy` 改成 `missing`。
`docker-compose.build.yml`（源码自建）刻意**没有**这一行 —— 那里应当用本地构建产物。
</details>

<details>
<summary><b>搜索很慢，还提示某个站「已暂时跳过」？（v1.15.0）</b></summary>

这是**熔断**在保护你。聚合搜索要等最慢的站返回，所以一个连不通的站会
决定所有人的等待时间（实测 YouTube 连不上时吃满 25s 预算却返回 0 条，
而其余站 5s 内就全回来了）。

一个站连续 3 次「吃满超时预算且零结果」就会被冷却 10 分钟，冷却期内直接跳过，
搜索立刻回到「最慢的健康站」的速度。**慢但有结果的站不会被熔断**
（盘搜要 19s 但能给几千条，它是最有价值的站之一）。

- 看谁在冷却：`GET /api/v1/search/breaker`
- 刚改完站点地址/代理不想等：`POST /api/v1/search/breaker/reset?site=站点名`
- 三个开关：`CF_SEARCH_BREAKER_ENABLED` / `CF_SEARCH_BREAKER_THRESHOLD` /
  `CF_SEARCH_BREAKER_COOLDOWN_MINUTES`（设 `0` = 只计数不熔断），设置页可直接改。

熔断状态只在内存里，**重启即清空**（重启后重新给每个站一次机会）。
</details>

<details>
<summary><b>点了下载弹「已加入下载队列」，但任务是红色失败？（v1.15.0 修复）</b></summary>

这是 v1.15.0 之前的一个**假成功**：接口无条件返回 `success: true`，
所以哪怕下载器把任务拒了，界面也弹绿色提示 —— 真因（下载器连不上）
从来没出现在你眼前。

现在 `success` 反映**投递的真实结局**：下载器拒绝会弹**红色**并直接写出
下载器名与原因；网盘资源缺账号/aria2 时是 `pending`，会弹**黄色**提示下一步做什么。

想在**点击之前**就知道哪类资源现在下不了，看 `GET /api/v1/downloads/routing`：
它会列出每类资源该走哪个下载器、现在缺什么，以及**哪些下载器巡检显示连不上**
（这一条会提示你去「站点健康」页重新巡检）。
</details>

<details>
<summary><b>新番日历的封面偶尔是灰色占位块（随机裂图）？（v1.15.0 修复）</b></summary>

v1.15.0 之前，日历卡片用的是 Bangumi 的 **`images.large`（未压缩原图）**：
实测单张 **300 KB ~ 3 MB、最慢 21 秒**。一屏 30 张原图并发时，会有一部分
打爆图片代理的 15s 上游超时 → 后端返回 502 → 前端退占位色块，
表现就是**随机几张裂图，刷新一下换成另外几张裂**。

而榜单卡片封面显示宽度只有 **~120px**，原图的像素根本用不上。
同一张封面的 `common` 尺寸只有 **11 KB / 230 ms**：

| 尺寸 | 体积 | 耗时 |
|---|---|---|
| `large`（原图） | 937 KB | 13216 ms |
| `common`（现用） | **11 KB** | **600 ms** |

现在按 `COVER_SIZE_PRIORITY` 优先取 `common`，一屏封面的总传输量从
约 20 MB 降到约 0.3 MB。

**还有第二个原因**：`lain.bgm.tv` 的 TLS 连接实测会被**间歇性掐断**
（同一 URL 三连的结果是 `EXC / EXC / 200`，报错 `SSL: UNEXPECTED_EOF_WHILE_READING`
—— 重试就成功，说明是链路干扰不是图床挂了）。图片代理原本对非豆瓣图床
**零重试**，一次抖动就 502。现在每个地址会重试 3 次（只针对连接失败，
403/404 不重试）。两处修完后，实测 ui_check 的失败请求数 **24 → 0**。

如果你所在网络对 `bgm.tv` 干扰严重，可给 CineFlow 配 `CF_HTTP_PROXY`。
</details>

<details>
<summary><b>换页时内容区空着好几秒才出来，但后端日志显示很快？（v1.15.0 修复）</b></summary>

这是**浏览器连接池被封面图占满**，不是后端慢（详见 ADR-73）。

走后端代理的封面（豆瓣 / Bangumi）和 API 是**同源**的，而浏览器对同一域名
只开约 **6 条**并发连接。逛完热度排行的几个分类，就能攒下几十个还在飞的
图片请求 —— 于是下一页要用的 `/api/v1/...` **只能排在这些图片后面**。

实测：逛完 7 个分类再进「定时任务」，正文长度 `+2s..+8s` 一直是 169，
`+10s` 才变 2031，而后端接口本身只用 **8ms**；切页瞬间仍在飞的 **29 个**
请求**全部**是 `/api/v1/images/proxy`。

现在整屏重绘后会主动中止**已经不在页面上**的封面请求，连接立刻还给 API。
如果你在 v1.15.0 之前遇到过「某一页打不开、刷新就好」，基本都是这个。
</details>

<details>
<summary><b>切了一次页面后，新页面看得见但点不动（像卡死了）？（v1.15.0 修复）</b></summary>

弹窗遮罩挂在 `#modal-root`，而换页只重绘页面容器，**遮罩会原地留下**并
覆盖全屏 —— 于是新页面看得见却点不动，而刷新一下就好，
几乎不可能联想到「上一页有个没关的弹窗」。

复现路径（v1.15.0 之前）：订阅页打开「新增订阅」→ 不关弹窗，点侧边栏去设置页
→ 设置页任何按钮都点不到。

现在每次换页都会统一关掉遗留弹窗。
</details>
