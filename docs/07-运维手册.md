# 07 · 运维手册

> 部署、备份、验证、排障。端口统一 **6060**，默认账号 **admin / cineflow**（登录后立即改密）。

---

## 1. 部署

### 1.1 Docker Compose（推荐）

```bash
git clone <repo> cineflow && cd cineflow
cp .env.example .env      # 至少改 CF_SECRET_KEY 与 CF_SUPERUSER_PASSWORD
# 编辑 docker-compose.yml：把 /volume1/downloads 与 /volume1/media 改成你的实际路径
docker compose up -d
```

浏览器打开 `http://<NAS_IP>:6060`。

⚠️ **最容易出错的一点**：`downloads` 目录在 CineFlow 容器里的路径必须与
下载器容器里的路径**完全一致**，否则 CineFlow 找不到下载完成的文件，
硬链接也会失败。`library` 与 `downloads` 建议放在**同一个文件系统**上，
否则 `CF_TRANSFER_MODE=link`（硬链接）无法工作，只能退回 copy（占双份空间）。

compose 里已附带可选配套服务（注释状态，按需开启）：
Jackett（Torznab 聚合）、qBittorrent、PanSou（盘搜）、Emby。

健康检查已内置：`curl -fsS http://127.0.0.1:6060/api/health`。

### 1.2 源码运行（开发/调试）

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-dev.txt
.\.venv\Scripts\python.exe -m app.main          # 监听 0.0.0.0:6060
```

> `app/main.py` 只有模块级 `app` 对象，**没有 `create_app()` 工厂**，
> 用 uvicorn 时写 `uvicorn app.main:app --port 6060`。

### 1.3 配置优先级

```
环境变量（CF_ 前缀）  >  .env  >  config/config.yaml  >  代码默认值
```

列表型配置用英文逗号分隔（如 `CF_CHATOPS_ALLOW_USERS=ou_a,ou_b`）。
配置在**进程启动时快照**，改完必须重启。界面「设置」页只读展示（见 ADR-05），
页面底部有「如何修改配置」指引。

## 2. 备份与迁移

**必须备份的只有两样**：

| 路径 | 内容 |
|---|---|
| `data/cineflow.db` | 全部业务数据：站点、订阅、任务、入库记录、审计、转存记录 |
| `config/` | `config.yaml`（若使用）|

外加根目录 `.env`（含密钥与账号）。

SQLite 开了 **WAL**，热备份请用：

```bash
sqlite3 data/cineflow.db ".backup data/backup-$(date +%F).db"
```

直接 `cp` 正在运行的库有可能拿到不一致快照（`-wal` / `-shm` 未合并）。
最稳的做法是 `docker compose stop` 后再复制整个 `data/`。

**迁移**：新机器上放好 `data/` + `config/` + `.env`，`docker compose up -d` 即可，
无需任何迁移脚本（表结构由启动时的 `init_db` 保证；新增的示例站点会
按名字**补齐而不覆盖**你改过的配置，见 ADR-06）。

**老库升级**：新版本可能给已有表加列（如 v1.4.0 给 `library_files` 加了
`quality_score` / `upgrade_count`）。`create_all()` 不会补列，
所以启动时会执行 `init_db.migrate_columns()` 做幂等 `ALTER TABLE ADD COLUMN`
（ADR-17）。它失败只打 `warning` 不阻塞启动——**如果升级后某个页面报 500，
先看启动日志有没有补列告警**。升级前照上面备份一次数据库最稳。

## 3. 六个验证脚本

全部在 `scripts/` 下，**服务需先跑起来**（除 `demo_pipeline.py` / `research_refs.py`）。
期望输出数字如下，对不上就是有回归：

| 脚本 | 作用 | 期望结果 |
|---|---|---|
| `pytest -q` | 单元/集成测试（28 个测试文件） | **618 passed** |
| `ruff check app tests scripts` | 静态检查 | 全绿，无输出 |
| `python scripts/smoke_test.py` | 端到端打真实 HTTP，覆盖全部 API | **210/210 通过** |
| `python scripts/ui_check.py` | Playwright 真浏览器逐页点检 | **20 页 0 JS 报错 / 0 失败请求** |
| `python scripts/verify_docs.py` | 校验 README 与 docs 声明的数字与代码一致 | **625/625 通过** |

> ⚠️ `smoke_test.py` 会创建临时账号（`cf_smoke_viewer` / `cf_smoke_operator`）
> 与临时规则组/榜单规则，**结尾会全部删掉**。如果脚本中途被打断，
> 下次跑会因用户名重复而 FAIL——到「用户权限」页手动删掉这两个账号即可。

另有三个辅助脚本：

- `scripts/demo_pipeline.py`：跑一遍「搜索 → 择优 → 下载 → 入库」的演示流程。
- `scripts/live_check.py`：探测真实外部站点连通性（依赖外网，结果会波动，**不作为门禁**）。
- `scripts/research_refs.py`：抓同类开源项目能力清单做差集，规划版本时用（联网，非门禁）。

### 门禁数字的来源

`verify_docs.py` 会实际 import 代码去数：API 端点 **118**、router **20**、
数据库表 **19**、Provider **22**、前端页面 **20**、示例站点 **12**、
内置定时任务 **11**、设置页 **15 组**、可编辑配置 **51 项**、
用户角色 **3 档**、内置规则组模板 **4 个**、榜单来源 **4 个**。
**改代码后如果这些数变了，README 与 docs 必须同步改，否则脚本会 FAIL。**
这是刻意的设计：让文档过期变成一个会失败的检查，而不是靠人记得。

新增前端页面时记得同时更新 `web/assets/app.js` 的 `PAGES`/`ROUTES`
和 `scripts/ui_check.py` 的页面清单（ADR-08）。

| 2 | `cineflow.radar` | interval | `CF_RADAR_INTERVAL_MINUTES` |
| 3 | `cineflow.download` | interval | `CF_DOWNLOAD_CHECK_INTERVAL_MINUTES` |
| 4 | `cineflow.pan_transfer` | interval | `CF_PAN_TRANSFER_INTERVAL_MINUTES`（默认 20） |
| 5 | `cineflow.pan_subscribe` | interval | `CF_PAN_SUBSCRIBE_INTERVAL_MINUTES`（默认 60） |
| 6 | `cineflow.strm_sync` | interval | `CF_STRM_SYNC_INTERVAL_MINUTES`（默认 `0` = 关闭） |
| 7 | `cineflow.site_health` | interval | `CF_SITE_HEALTH_INTERVAL_MINUTES`（默认 180） |
| 8 | `cineflow.ranking` | interval | `CF_RANKING_INTERVAL_MINUTES`（默认 720） |
| 9 | `cineflow.scrape` | cron | `CF_SCRAPE_CRON`（默认 `30 4 * * *`） |
| 10 | `cineflow.upgrade` | interval | 随 `CF_UPGRADE_ENABLED`，默认关闭 |
| 11 | `cineflow.library` | cron | `CF_LIBRARY_SCAN_CRON` |

> 间隔配置为 `0`（或对应开关为 `false`）的任务**不会注册**，
> 启动日志里会打印实际注册了哪几个，可据此确认配置生效。

界面「定时任务」页可**改周期、立即运行、暂停/恢复**，改动即时生效（写回调度器）。
总开关 `CF_SCHEDULER_ENABLED=false` 可关闭全部自动任务（排障时很有用）。

## 5. 常见故障

### 5.1 下载完成了但没入库

按顺序查：

1. 路径一致性——CineFlow 容器里的 `/downloads` 和下载器容器里的是否**同一个宿主目录**。
2. `CF_MIN_FILE_SIZE_MB`（默认 100）是否把文件过滤掉了。
3. 「入库」页看 `transfer_records` 的失败原因。
4. 硬链接失败 → `downloads` 与 `library` 跨文件系统了，改 `CF_TRANSFER_MODE=copy`
   或把两者放到同一卷。

### 5.2 站点搜不到东西 / Cookie 过期

**先看「站点健康」页**（v1.5.0 起）：它对搜索类站点会真搜一次，
状态为 **亚健康（degraded）** 的基本就是 Cookie 过期——
这类站点首页照样能打开，只有搜索结果是 0 条，光点「测试」看不出来。

**再看搜索结果里的「站点诊断」**（v1.6.0 起）：搜索响应会逐站给出
`ok / empty / timeout / error` 与失败原因，直接回答"这个站为什么没出货"：

| 状态 | 通常原因与处理 |
|---|---|
| `error` 502 | 该站点服务没起来（例：配了 Jackett 但本机没部署）→ 部署或禁用该站 |
| `empty` | 连通但没匹配（例：Nyaa 只收日番，中文剧名搜不到）→ 换关键词或禁用该站 |
| `timeout` | 网络慢或站点卡 → 调大 `SEARCH_TIMEOUT` |
| `ok` 但 kept 远小于 raw | 被去重或过滤规则组筛掉了 → 检查默认规则组 |

> v1.6.0 之前小站的结果会被返回量大的站**挤出结果窗口**，表现就是"只有某一个站有资源"。
> 现已改为轮转交错合并（ADR-25）。如果你还在旧版本上看到这个现象，升级即可。

- 站点管理页对每个站点点「测试」，看具体报错。
- PT 站点普遍需要 Cookie 或 passkey，过期后表现为「0 结果」而非报错。
- 站点被墙 → 配 `CF_HTTP_PROXY`。
- 自定义站点字段映射错 → 用 `api_generic` / `html_generic` 的测试按钮逐字段调。

### 5.3 网盘转存失败

见 [`06-网盘管理.md`](06-网盘管理.md) §8。最快路径：看**转存记录表**的
`message` 字段原文，能立刻区分「没触发」与「被网盘拒绝」。
夸克 Cookie 过期是最常见原因。

### 5.4 机器人回调 401

从 v1.3.0 起**未配验签密钥默认拒绝**（ADR-04），这是破坏性变更。

1. 确认平台密钥已填（飞书 Verification Token / 钉钉 AppSecret / TG Secret Token）。
2. 钉钉还要检查**服务器时间**，签名含时间戳，时钟偏移过大会被判为重放。
3. 纯内网且明白风险 → 在该平台配置里把 `allow_unverified` 填 `1`。
4. 绕开平台自测：机器人页「指令试跑」→ 能跑通说明问题在平台侧配置。

### 5.5 STRM 能扫到但点开报错

1. `CF_STRM_LINK_MODE=direct` 时链接会过期 → 改成 `proxy`（默认）后重新同步（ADR-14）。
2. `proxy` 模式下 `CF_STRM_BASE_URL` 必须是**媒体服务器容器能访问到**的地址，
   填 `127.0.0.1` 时若 Emby 在另一个容器里就连不上。
3. 「STRM 同步」页点「测直链」，能直接判断是网盘取链失败还是地址不通。
4. 剧集点开报错但文件在网盘已删 → 开 `CF_STRM_CLEAN_INVALID` 让同步顺带清理。

### 5.6 Emby 识别错片名 / 没有海报

1. 确认 `CF_SCRAPE_ENABLED=true`；媒体库页对该文件点「补刮 NFO」看返回。
2. 没配 `CF_TMDB_API_KEY` 时只会写最小 NFO（标 `degraded`，见 ADR-12），
   配好后用 `CF_SCRAPE_OVERWRITE=true` 跑一次补刮覆盖。
3. NFO 已存在且是你手工改的 → 默认**不会**被覆盖，这是刻意行为。
4. 媒体服务器侧要允许「优先使用本地 NFO」，否则它仍用自己刮的结果。

### 5.7 界面白屏 / 某页报错

前端是零依赖原生 JS，没有 CDN 依赖，白屏基本是 JS 异常。
跑 `python scripts/ui_check.py`，它会逐页捕获 JS 报错与失败请求，
并把截图存到 `data/ui_shots/`。

### 5.8 服务起不来

- 端口占用：`6060` 被别的容器占了，改 compose 的端口映射。
- 数据库锁：上次非正常退出留下 `-wal`/`-shm`，正常情况下会自动恢复；
  确实损坏则从备份恢复 `data/cineflow.db`。
- 看日志：`data/logs/` 或 `docker compose logs -f cineflow`。

## 7. v1.5.0 新增运维项

### 7.1 在线改配置改坏了怎么办

设置页「全部恢复默认」会清空 `settings` 表里的 `runtime_config`，
所有配置回到 `.env` / `config.yaml` 的值。如果连界面都进不去：

```bash
# 直接删掉运行期覆盖（服务需停止）
sqlite3 data/cineflow.db "DELETE FROM settings WHERE key='runtime_config';"
```

配置改动**先全部校验再落库**，所以不会出现「改了一半」的状态；
非法值在保存时就被拒绝，不可能写进库。

### 7.2 把自己锁在外面了怎么办

系统本身有两道保护（不能删/停用自己、最后一个启用中的管理员不能降级或停用），
正常操作不会锁死。万一发生（比如直接改了数据库）：

```bash
sqlite3 data/cineflow.db "UPDATE users SET role='admin', is_superuser=1, is_active=1 WHERE username='admin';"
```

重启后 `sync_user_roles()` 会把 `role` 与 `is_superuser` 对齐。

### 7.3 老库升级到 v1.5.0 后请复核用户角色

`users` 表补 `role` 列时默认值是 `'admin'`（保证唯一的老管理员不被锁在外面），
启动时 `sync_user_roles()` 再按 `is_superuser` 对齐——
**原本 `is_superuser=false` 的账号会变成 `operator`**（不是 viewer，
避免突然失去已有的操作能力）。多用户老库升级后请到「用户权限」页复核一遍。

### 7.4 榜单订阅刷进来太多订阅

- 调小 `CF_RANKING_MAX_PER_RUN`（默认 5），或把规则的 `enabled` 关掉。
- 先用规则的「试算」看会建哪些，确认了再启用。
- 手动删掉的订阅**不会**被下次巡检加回来（规则记了 `handled_ids`）。

### 7.5 搜索结果顺序变了

检查「过滤规则组」页是否有组被设为**默认组**——默认组会改变全局搜索排序。
内置的 4 个模板出厂都不是默认组，所以升级本身不会改变你熟悉的顺序；
如果顺序变了，是有人点了「设为默认」。取消即可恢复。

### 7.6 下载任务总是投到同一个下载器

`CF_DOWNLOADER_STRATEGY` 默认是 `priority`（按优先级，与老版本一致）。
要摊开压力改成 `least_tasks` 或 `round_robin`，可在设置页直接改、立即生效。
注意「站点健康」页里状态为 down/degraded 的下载器会被**排到最后**
（但不会被剔除，以防健康数据过期导致完全不可投递）。

### 7.7 热榜封面显示成彩色色块

**这是预期行为，不是 bug。** 封面按**回退链**逐级尝试
（v1.7.0，ADR-29）：

```
站点自带元数据  →  豆瓣 subject_suggest  →  TMDB（需 Key）  →  占位色块
```

每一级都可能拿不到，全都失败才显示按标题哈希取色的占位块。

想让封面变多：启用带元数据的站点（如 Mukaku 类影视站）；
或确认服务端能访问豆瓣（回退链第二级，**无需 API Key**）。
已入库的老资源会在**下次搜索命中时回填**元数据，不需要清库。

如果是**真图裂了**（不是占位块），检查：
- **豆瓣封面走后端代理**（`/api/v1/images`）。豆瓣图床校验 `Referer`，
  裸请求返 **418**；浏览器跨站会剥离 Referer，所以前端加 `referrerpolicy` 治不了，
  必须由服务端补 Referer 转发（ADR-30）。若豆瓣图裂了，
  先确认**服务端**能出网，而不是检查浏览器。
- B 站 / YouTube / TMDB 图床实测可**直连**，这些不走代理，
  裂图说明是**浏览器**不能出网。
- 其他站点图床有防盗链 → 前端已带 `referrerpolicy="no-referrer"`，仍失败自动退占位
- NAS 不能直连外网 → 配 `CF_HTTP_PROXY`

### 7.9 豆瓣封面全都没有 / 日志出现豆瓣限流

**先看是不是限流自保**。豆瓣有反爬，所以内置了：缓存 6 小时、
一旦命中限流就**退避 300 秒**不再请求。退避期间封面会自动退回 TMDB 或占位色块，
**不影响搜索与下载**——这是设计好的降级，不用处理，等几分钟自愈。

| 现象 | 处理 |
|---|---|
| 偶发没有豆瓣封面 | 正常。榜单只给**前 24 条**补图（并发 8），避免补图拖慢响应 |
| 完全没有豆瓣封面 | 服务端不能访问 `movie.douban.com` → 配 `CF_HTTP_PROXY` |
| 封面配错了作品 | `subject_suggest` 是**按标题模糊匹配**，同名作品会配错。已知限制，v1.8.0 计划加年份/类型二次校验 |
| 想彻底关掉补图 | 榜单接口传 `with_poster=false` |

### 7.10 B 站 / YouTube 搜不到东西

| 现象 | 原因与处理 |
|---|---|
| B 站返回 412 | 该接口对不带 `buvid3` Cookie 的请求做风控。程序会**先 GET 一次 B 站首页拿 Cookie**（ADR-31），若仍 412 说明服务端出网被拦，检查代理 |
| 两个站都没结果 | 站点**默认禁用**。去「站点管理」启用 `bilibili` / `youtube` |
| YouTube 无结果 | 复用 yt-dlp 的 `ytsearch`，先确认 `pip install -r requirements.txt` 装了 yt-dlp，且服务端能访问 YouTube |
| 做种数大得离谱 | **预期**：网页视频没有做种数，把**播放量投影到 `seeders`** 以复用既有排序（ADR-32），只用于相对排序 |

### 7.11 新增的资源站点搜不到资源

v1.7.0 加了 9 条示例站点，**全部默认禁用**。启用后仍搜不到，
先对照下表——**其中 5 个站本身就有限制，不是配置问题**：

| 站点 | 状况 |
|---|---|
| `yyets` | ✅ 应该能用（实测 22 条）。不行则站点本身在波动 |
| `bdflixs` | ✅ 应该能用（实测 12 条磁力） |
| `juhebd` | ⚠️ 能搜到条目但**下载链接被微信公众号关注墙挡住**，只能当"有没有这部片"的探针 |
| `ldysg` | ⚠️ 只返回元数据（封面/年份/导演），**没有直链**。另注意域名实际是 `.top` 而非 `.win` |

### 7.8 网页视频（yt-dlp）下载报错

| 现象 | 原因与处理 |
|---|---|
| 提示「长视频平台的正片播放页…」 | 有意拒绝：腾讯/爱奇艺/优酷/芒果正片与 Netflix 等需会员，本工具不做（ADR-24）。请用平台官方客户端的离线缓存 |
| 提示「站点限流（HTTP 412/429）」 | B 站等站点的频率风控。等几秒再试；同一链接的成功结果会缓存 5 分钟 |
| 提示「未安装 yt-dlp」 | `pip install -r requirements.txt` |
| 下到一半失败 / 只有视频没声音 | 缺 ffmpeg。装上即可合并分离流；未装时系统会自动退回单文件流（画质低一档） |
| 需要登录才能看的内容 | 在站点 `options.cookie_file` 填**你自己账号**导出的 cookie 文件路径；只支持下载你有权访问的内容 |
| 想限速 | 站点 `options.rate_limit`（单位 KB/s） |
