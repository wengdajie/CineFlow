## 1. 部署

### 1.1 Docker 完整安装（推荐路径）

本节从「机器上还没有 Docker」讲到「浏览器能打开」，按你的平台挑一节读第 ① 步，
之后的 ②~⑦ 步所有平台通用。

> 🐮 **飞牛 fnOS 用户请直接看 [11-飞牛NAS部署指南.md](11-飞牛NAS部署指南.md)**。
> 飞牛的存储路径是 `/vol1/...` 而非群晖的 `/volume1/...`，另有硬链接同盘校验、
> 与 fnOS「影视」App 联动等差异，照本节的群晖示例抄会挂载到空目录。

#### ① 装好 Docker

**群晖 DSM 7.x**

1. 套件中心 → 搜索 **Container Manager**（DSM 6.x 叫 **Docker**）→ 安装。
2. File Station 里建好三个共享文件夹/目录：`docker`（放配置）、`downloads`、`media`。
3. 控制面板 → 终端机和 SNMP → 勾选 **启动 SSH 功能**，之后用 SSH 登录执行命令。
   DSM 7.2+ 的 Container Manager 自带「项目（Project）」功能，也可以直接在
   图形界面粘贴 `docker-compose.yml`，不用 SSH。

**威联通 QTS**

1. App Center → 安装 **Container Station**。
2. Container Station 里有 **应用程式（Applications）** 功能，可直接粘贴 compose 内容。
3. 需要命令行时：控制台 → Telnet/SSH → 启用 SSH。QNAP 上 compose 命令通常是
   `docker-compose`（带横线），不是 `docker compose`。

**Linux（Debian / Ubuntu / CentOS）**

```bash
# 官方一键脚本，会同时装上 docker 与 compose 插件
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
# 让当前用户免 sudo（需重新登录生效）
sudo usermod -aG docker "$USER"
docker compose version    # 验证：应输出 v2.x
```

**Windows 10/11**

1. 先启用 WSL2：管理员 PowerShell 执行 `wsl --install`，重启。
2. 安装 **Docker Desktop**（<https://www.docker.com/products/docker-desktop/>），
   安装时勾选 *Use WSL 2 based engine*。
3. Settings → Resources → File Sharing 里把要挂载的盘（如 `D:`）加进去，
   否则挂载卷会是空目录。
4. Windows 上路径写法用正斜杠，例如 `D:/nas/downloads:/downloads`。

**macOS**：装 Docker Desktop 即可，路径写法同 Linux。

#### ② 拿到代码并生成配置

```bash
git clone <repo> cineflow && cd cineflow
cp .env.example .env
```

**`.env` 里至少改两项**（不改就等于把大门敞开）：

| 变量 | 为什么必须改 |
|---|---|
| `CF_SECRET_KEY` | 用来签发登录 Token。用默认值等于任何人都能伪造管理员 Token |
| `CF_SUPERUSER_PASSWORD` | 默认 `cineflow` 是公开的 |

生成一个随机密钥：

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
# 或者
openssl rand -base64 48
```

#### ③ 查出 PUID / PGID（决定文件属于谁）

容器默认以 root 跑，会把下载/入库的文件建成 root 所有，
之后你在 NAS 的文件管理器里**删不掉、改不了**；Emby 之类的容器也可能读不了。
所以要告诉容器「用哪个用户身份跑」。

在 NAS 上 SSH 执行（用你平时登录 NAS 的那个账号）：

```bash
id -u          # 输出 UID，例如 1026 → 填给 PUID
id -g          # 输出 GID，例如 100  → 填给 PGID
# 一次看全：
id
```

* 群晖普通用户通常是 `uid=1026`、`gid=100(users)`。
* 威联通 admin 通常是 `uid=1000`、`gid=100`。
* Linux 首个普通用户通常是 `1000:1000`。
* 想确认某个目录该用什么值，直接看它的归属：`ls -ln /volume1/downloads`。

把查到的值写进 `docker-compose.yml` 的 `environment`：

```yaml
      PUID: 1026
      PGID: 100
```

> 实现细节：`docker/entrypoint.sh` 会在 `PUID != 0` 时 `chown` 运行期目录
> 并用 `setpriv` 降权执行。填 `0` 就是以 root 跑（不推荐，但某些挂载场景下省事）。

#### ④ 改挂载路径（**最容易出错的一步**）

`docker-compose.yml` 里这两行是示例值，**必须改成你的实际路径**：

```yaml
      - /volume1/downloads:/downloads # ← 改成你的下载目录
      - /volume1/media:/library       # ← 改成你的媒体库目录
```

各平台的宿主机路径长这样：

| 平台 | 典型路径 |
|---|---|
| 群晖 | `/volume1/downloads`、`/volume1/media`（多个存储空间时可能是 `/volume2/...`） |
| 威联通 | `/share/Download`、`/share/Multimedia`（或 `/share/CACHEDEV1_DATA/...`） |
| Linux | 你自己建的目录，如 `/srv/downloads` |
| Windows | `D:/nas/downloads`、`D:/nas/media` |

⚠️ **两条铁律，违反了会静默出问题：**

1. **`downloads` 在 CineFlow 容器里的路径，必须与下载器容器里的路径完全一致。**
   即两个容器的 compose 里都写 `- /volume1/downloads:/downloads`。
   qBittorrent 汇报的完成路径是**它自己容器里**的路径，CineFlow 拿到这个路径去找文件；
   两边不一致时 CineFlow 就是找不到文件，表现为「下载完成了但没入库」，
   而且日志里只有一句找不到路径，很难联想到是挂载问题。
2. **`library` 与 `downloads` 要在同一个文件系统（同一个卷）上。**
   `CF_TRANSFER_MODE=link`（硬链接）跨文件系统无法工作。跨了会自动退回复制，
   于是每部剧占双份空间，而且做种会因为源文件被移动而中断。
   在 NAS 上就是：两个目录都放在 `/volume1` 下，不要一个 `/volume1` 一个 `/volume2`。

#### ⑤ 启动

```bash
docker compose up -d          # QNAP 上用 docker-compose up -d
docker compose logs -f        # 看启动日志，Ctrl+C 退出（不会停容器）
```

首次启动会做这些事（日志里能看到）：初始化 SQLite、写入 22 条示例站点（默认全部禁用）、
创建管理员账号、启动调度器。约 10~20 秒。

#### ⑥ 验证

```bash
curl -fsS http://127.0.0.1:6060/api/health
# {"status":"ok","version":"1.8.0","scheduler":true}
docker compose ps             # STATUS 应为 Up (healthy)
```

`healthy` 来自镜像内置的 HEALTHCHECK（每 30s 打一次 `/api/health`，
启动宽限 20s）。浏览器打开 `http://<NAS_IP>:6060`，用 `.env` 里设的账号登录。

**登录后第一件事**：右上角改密码；然后去「站点管理」按
[`docs/10-站点接入指南.md`](10-站点接入指南.md) 接入至少一个搜索站点
（不接站点搜索页会是空的，这是预期的——预置站点一律默认禁用）。

#### ⑦ 按需开启配套服务

`docker-compose.yml` 里已备好四个可选服务，去掉注释即可：

| 服务 | 端口 | 作用 | 接入方式 |
|---|---|---|---|
| `jackett` | 9117 | Torznab 聚合，一个入口接几百个 BT 站 | 见 `docs/10` §1 |
| `qbittorrent` | 8080 | BT 下载器 | 站点管理加 `qbittorrent` 站点，地址 `http://qbittorrent:8080` |
| `pansou` | 8888 | 网盘资源搜索（盘搜） | 启用预置的「PanSou 盘搜」站点，地址改 `http://pansou:8888` |
| `emby` | 8096 | 媒体服务器 | 站点管理加 `emby` 站点 + API Key |

```bash
docker compose up -d jackett qbittorrent
```

> 🔴 **容器之间互访必须用服务名，不能用 `127.0.0.1`。**
> 在 CineFlow 容器里 `127.0.0.1` 指的是它自己，不是 NAS 主机。
> 所以地址要写 `http://jackett:9117/...`、`http://qbittorrent:8080`、`http://pansou:8888`。
> 预置示例站点里写的 `127.0.0.1` 是给「源码直跑」场景准备的，用 Docker 时记得改。
> 这一条是新手最高频的失败原因，表现是站点诊断里的 `error` + 连接被拒。

#### ⑧ 端口 6060 被占用怎么办

端口统一为 **6060**。如果宿主机上这个端口已被占用，**只改左边**：

```yaml
    ports:
      - "6061:6060"     # 宿主机 6061 → 容器内仍是 6060
```

不要去改 `CF_PORT`——容器内的健康检查、compose 的 healthcheck 都写死了 6060，
改了容器内端口会让健康检查失败、容器一直显示 unhealthy 并被反复重启。

查谁占用了端口：

```bash
# Linux / NAS
sudo lsof -i :6060       ||  sudo netstat -tulnp | grep 6060
```

```powershell
# Windows
netstat -ano | findstr :6060
```

#### ⑨ 日常运维命令

```bash
docker compose ps                     # 状态与健康
docker compose logs -f --tail 200     # 跟踪日志
docker compose logs cineflow | grep -i error
docker compose restart cineflow       # 重启（改了 .env 后必须重启才生效）
docker compose down                   # 停止并删除容器（数据在挂载卷里，不丢）
docker compose pull && docker compose up -d   # 升级到新镜像（见下方「升级后没变化」）
# 从源码重新构建要用 override 文件（部署用 compose 已不含 build，ADR-47）：
docker compose -f docker-compose.yml -f docker-compose.build.yml build --no-cache
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d
docker exec -it cineflow sh           # 进容器排查
docker stats cineflow                 # 看内存/CPU
```

日志同时写在挂载出来的 `./data/logs/` 下，`docker compose down` 之后也还在。

#### ⑨-1 升级后「还是旧版本」怎么查

按**从外到内**四步定位，每步都有明确判据，不要靠猜：

```bash
# 1) 后端到底是哪个版本？这是唯一权威来源
curl -s http://127.0.0.1:6060/api/health
#    {"status":"ok","version":"1.10.0",...}  ← version 对不对？

# 2) 容器用的镜像是不是新的？比对 digest
docker inspect --format '{{.Image}}' cineflow
docker image inspect ghcr.io/wengdajie/cineflow:latest --format '{{.Id}}'
#    两者不一致 = 容器还在跑旧镜像，pull 完没重建 → docker compose up -d --force-recreate

# 3) 镜像里的代码版本（不依赖标签，直接看文件）
docker exec cineflow cat /app/app/core/version.py

# 4) 镜像是什么时候构建的、对应哪个 commit
docker image inspect ghcr.io/wengdajie/cineflow:latest \
    --format '{{.Created}} {{index .Config.Labels "org.opencontainers.image.revision"}}'
```

对应的处置：

| 现象 | 原因 | 处置 |
|---|---|---|
| `/api/health` 版本号**已经是新的**，但**界面还是旧的** | 浏览器缓存了 `app.js` | v1.10.1 起服务端已强制 `Cache-Control: no-cache`（见下）。**仍在旧版本上**的话按 Ctrl+F5 强刷，或换隐私窗口验证 |
| `docker inspect` 的 Image 与 `latest` 的 Id 不一致 | `pull` 拿到了新镜像但容器没重建 | `docker compose up -d --force-recreate` |
| `pull` 显示 `Image is up to date` 但 digest 是旧的 | 本地缓存的 `latest` 标签过期 | `docker compose pull --policy always`，或 `docker rmi` 后重拉 |
| 版本号仍是旧的，且 pull 时报网络超时 | 没拉到 ghcr.io | 见 §4.1 的镜像来源排查；也可直接锁定版本 `CINEFLOW_IMAGE=ghcr.io/wengdajie/cineflow:sha-<短 commit>` |

> **为什么界面会比后端"慢一个版本"**：Starlette 的静态文件默认只给
> `ETag`/`Last-Modified`，**不给 `Cache-Control`**。缺了它，浏览器可以按
> RFC 7234 自行推算新鲜期（常见实现是「距上次修改时间的 10%」）
> **直接用本地副本而不回源**。于是后端已经是新版、`app.js` 还是旧的。
> v1.10.1 起 `/assets/*` 与 `/` 一律带 `Cache-Control: no-cache`
> （语义是"每次必须回源校验"，配合 ETag 未变更时仍返回 304，几乎不增加流量）。

#### ⑩ 不用 compose，只用 docker run

```bash
docker build -t cineflow:latest .
docker run -d --name cineflow --restart unless-stopped   -p 6060:6060   -e PUID=1026 -e PGID=100 -e TZ=Asia/Shanghai   -e CF_SECRET_KEY="$(openssl rand -base64 48)"   -e CF_SUPERUSER=admin -e CF_SUPERUSER_PASSWORD='改成你的密码'   -v "$PWD/data:/app/data"   -v "$PWD/config:/app/config"   -v "$PWD/plugins:/app/plugins"   -v /volume1/downloads:/downloads   -v /volume1/media:/library   -v "$PWD/strm:/strm"   cineflow:latest
```

单容器跑时容器之间没有 DNS，配置下载器/Jackett 地址要用
**NAS 的局域网 IP**（如 `http://192.168.1.10:9117`），或给它们连同一个
`docker network create` 出来的自定义网络。

#### ⑪ 安装后自检清单

| 检查 | 命令 / 位置 | 期望 |
|---|---|---|
| 服务活着 | `curl -fsS http://127.0.0.1:6060/api/health` | `status: ok`，`scheduler: true` |
| 容器健康 | `docker compose ps` | `Up (healthy)` |
| 密钥已改 | 看 `.env` | 不是 `please-change-...` |

| 至少一个站点可用 | 「站点健康」页 | 有一个 **健康 healthy** |

## 2. 备份与迁移

**必须备份的只有两样**：

| 路径 | 内容 |
|---|---|
| `data/cineflow.db` | 全部业务数据：站点、订阅、任务、入库记录、审计、转存记录 |
| `config/` | `config.yaml`（若使用）|

外加根目录 `.env`（含密钥与账号）。

SQLite 开了 **WAL**，热备份请用：

```bash
sqlite3 data/cineflow.db ".backup data/backup-$(date +%F).db"
```

直接 `cp` 正在运行的库有可能拿到不一致快照（`-wal` / `-shm` 未合并）。
最稳的做法是 `docker compose stop` 后再复制整个 `data/`。

**迁移**：新机器上放好 `data/` + `config/` + `.env`，`docker compose up -d` 即可，
无需任何迁移脚本（表结构由启动时的 `init_db` 保证；新增的示例站点会
按名字**补齐而不覆盖**你改过的配置，见 ADR-06）。

**老库升级**：新版本可能给已有表加列（如 v1.4.0 给 `library_files` 加了
`quality_score` / `upgrade_count`）。`create_all()` 不会补列，
所以启动时会执行 `init_db.migrate_columns()` 做幂等 `ALTER TABLE ADD COLUMN`
（ADR-17）。它失败只打 `warning` 不阻塞启动——**如果升级后某个页面报 500，
先看启动日志有没有补列告警**。升级前照上面备份一次数据库最稳。

## 3. 七个验证脚本

全部在 `scripts/` 下，**服务需先跑起来**（除 `demo_pipeline.py` / `research_refs.py`）。
期望输出数字如下，对不上就是有回归：

| 脚本 | 作用 | 期望结果 |
|---|---|---|
| `pytest -q` | 单元/集成测试（44 个测试文件） | **1014 passed** |
| `ruff check app tests scripts` | 静态检查 | 全绿，无输出 |
| `python scripts/smoke_test.py` | 端到端打真实 HTTP，覆盖全部 API | **275/275 通过** |
| `python scripts/ui_check.py` | Playwright 真浏览器逐页点检 | **22 页 0 JS 报错 / 0 失败请求** |
| `python scripts/verify_docs.py` | 校验 README 与 docs 声明的数字与代码一致 | **886/886 通过** |
| `python scripts/verify_yaml.py` | 校验 `docker-compose*.yml` / Dockerfile 等部署文件 | **120/120 通过** |

> ⚠️ `smoke_test.py` 会创建临时账号（`cf_smoke_viewer` / `cf_smoke_operator`）
> 与临时规则组/榜单规则，**结尾会全部删掉**。如果脚本中途被打断，
> 下次跑会因用户名重复而 FAIL——到「用户权限」页手动删掉这两个账号即可。

另有三个辅助脚本：

- `scripts/demo_pipeline.py`：跑一遍「搜索 → 择优 → 下载 → 入库」的演示流程。
- `scripts/live_check.py`：探测真实外部站点连通性（依赖外网，结果会波动，**不作为门禁**）。
- `scripts/research_refs.py`：抓同类开源项目能力清单做差集，规划版本时用（联网，非门禁）。

### 门禁数字的来源

`verify_docs.py` 会实际 import 代码去数：API 端点 **155**、router **23**、
数据库表 **20**、Provider **29**、前端页面 **22**、示例站点 **22**、
内置定时任务 **14**、设置页 **15 组**、可编辑配置 **52 项**、
用户角色 **3 档**、内置规则组模板 **4 个**、榜单来源 **4 个**。
**改代码后如果这些数变了，README 与 docs 必须同步改，否则脚本会 FAIL。**
这是刻意的设计：让文档过期变成一个会失败的检查，而不是靠人记得。

新增前端页面时记得同时更新 `web/assets/app.js` 的 `PAGES`/`ROUTES`
和 `scripts/ui_check.py` 的页面清单（ADR-08）。

| 11 | `cineflow.library` | cron | `CF_LIBRARY_SCAN_CRON` |
| 12 | `cineflow.pan_keepalive` | interval | `PAN_KEEPALIVE_INTERVAL_MINUTES`（默认 360 = 6 小时） |
| 13 | `cineflow.video_subscribe` | interval | `CF_VIDEO_SUBSCRIBE_INTERVAL_MINUTES`（默认 120 = 2 小时） |
| 14 | `cineflow.speed_limit` | interval | `CF_SPEED_LIMIT_INTERVAL_MINUTES`（默认 10） |

> 间隔配置为 `0`（或对应开关为 `false`）的任务**不会注册**，
> 启动日志里会打印实际注册了哪几个，可据此确认配置生效。

界面「定时任务」页可**改周期、立即运行、暂停/恢复**，改动即时生效（写回调度器）。
总开关 `CF_SCHEDULER_ENABLED=false` 可关闭全部自动任务（排障时很有用）。

## 5. 常见故障

### 5.1 下载完成了但没入库

按顺序查：

1. 路径一致性——CineFlow 容器里的 `/downloads` 和下载器容器里的是否**同一个宿主目录**。
2. `CF_MIN_FILE_SIZE_MB`（默认 100）是否把文件过滤掉了。
3. 「入库」页看 `transfer_records` 的失败原因。
4. 硬链接失败 → `downloads` 与 `library` 跨文件系统了，改 `CF_TRANSFER_MODE=copy`
   或把两者放到同一卷。

### 5.2 站点搜不到东西 / Cookie 过期

**先看「站点健康」页**（v1.5.0 起）：它对搜索类站点会真搜一次，
状态为 **亚健康（degraded）** 的基本就是 Cookie 过期——
这类站点首页照样能打开，只有搜索结果是 0 条，光点「测试」看不出来。

**再看搜索结果里的「站点诊断」**（v1.6.0 起）：搜索响应会逐站给出
`ok / empty / timeout / error` 与失败原因，直接回答"这个站为什么没出货"：

| 状态 | 通常原因与处理 |
|---|---|
| `error` 502 | 该站点服务没起来（例：配了 Jackett 但本机没部署）→ 部署或禁用该站 |
| `empty` | 连通但没匹配（例：Nyaa 只收日番，中文剧名搜不到）→ 换关键词或禁用该站 |
| `timeout` | 网络慢或站点卡 → 调大 `SEARCH_TIMEOUT` |
| `ok` 但 kept 远小于 raw | 被去重或过滤规则组筛掉了 → 检查默认规则组 |

> v1.6.0 之前小站的结果会被返回量大的站**挤出结果窗口**，表现就是"只有某一个站有资源"。
> 现已改为轮转交错合并（ADR-25）。如果你还在旧版本上看到这个现象，升级即可。

- 站点管理页对每个站点点「测试」，看具体报错。
- PT 站点普遍需要 Cookie 或 passkey，过期后表现为「0 结果」而非报错。
- 站点被墙 → 配 `CF_HTTP_PROXY`。
- 自定义站点字段映射错 → 用 `api_generic` / `html_generic` 的测试按钮逐字段调。

### 5.3 网盘转存失败

见 [`06-网盘管理.md`](06-网盘管理.md) §8。最快路径：看**转存记录表**的
`message` 字段原文，能立刻区分「没触发」与「被网盘拒绝」。
夸克 Cookie 过期是最常见原因。

### 5.4 机器人回调 401

从 v1.3.0 起**未配验签密钥默认拒绝**（ADR-04），这是破坏性变更。

1. 确认平台密钥已填（飞书 Verification Token / 钉钉 AppSecret / TG Secret Token）。
2. 钉钉还要检查**服务器时间**，签名含时间戳，时钟偏移过大会被判为重放。
3. 纯内网且明白风险 → 在该平台配置里把 `allow_unverified` 填 `1`。
4. 绕开平台自测：机器人页「指令试跑」→ 能跑通说明问题在平台侧配置。

### 5.5 STRM 能扫到但点开报错

1. `CF_STRM_LINK_MODE=direct` 时链接会过期 → 改成 `proxy`（默认）后重新同步（ADR-14）。
2. `proxy` 模式下 `CF_STRM_BASE_URL` 必须是**媒体服务器容器能访问到**的地址，
   填 `127.0.0.1` 时若 Emby 在另一个容器里就连不上。
3. 「STRM 同步」页点「测直链」，能直接判断是网盘取链失败还是地址不通。
4. 剧集点开报错但文件在网盘已删 → 开 `CF_STRM_CLEAN_INVALID` 让同步顺带清理。

### 5.6 Emby 识别错片名 / 没有海报

1. 确认 `CF_SCRAPE_ENABLED=true`；媒体库页对该文件点「补刮 NFO」看返回。
2. 没配 `CF_TMDB_API_KEY` 时只会写最小 NFO（标 `degraded`，见 ADR-12），
   配好后用 `CF_SCRAPE_OVERWRITE=true` 跑一次补刮覆盖。
3. NFO 已存在且是你手工改的 → 默认**不会**被覆盖，这是刻意行为。
4. 媒体服务器侧要允许「优先使用本地 NFO」，否则它仍用自己刮的结果。

### 5.7 界面白屏 / 某页报错

前端是零依赖原生 JS，没有 CDN 依赖，白屏基本是 JS 异常。
跑 `python scripts/ui_check.py`，它会逐页捕获 JS 报错与失败请求，
并把截图存到 `data/ui_shots/`。

### 5.8 服务起不来

- 端口占用：`6060` 被别的容器占了，改 compose 的端口映射。
- 数据库锁：上次非正常退出留下 `-wal`/`-shm`，正常情况下会自动恢复；
  确实损坏则从备份恢复 `data/cineflow.db`。
- 看日志：`data/logs/` 或 `docker compose logs -f cineflow`。

## 7. v1.5.0 新增运维项

### 7.1 在线改配置改坏了怎么办

设置页「全部恢复默认」会清空 `settings` 表里的 `runtime_config`，
所有配置回到 `.env` / `config.yaml` 的值。如果连界面都进不去：

```bash
# 直接删掉运行期覆盖（服务需停止）
sqlite3 data/cineflow.db "DELETE FROM settings WHERE key='runtime_config';"
```

配置改动**先全部校验再落库**，所以不会出现「改了一半」的状态；
非法值在保存时就被拒绝，不可能写进库。

### 7.2 把自己锁在外面了怎么办

系统本身有两道保护（不能删/停用自己、最后一个启用中的管理员不能降级或停用），
正常操作不会锁死。万一发生（比如直接改了数据库）：

```bash
sqlite3 data/cineflow.db "UPDATE users SET role='admin', is_superuser=1, is_active=1 WHERE username='admin';"
```

重启后 `sync_user_roles()` 会把 `role` 与 `is_superuser` 对齐。

### 7.3 老库升级到 v1.5.0 后请复核用户角色

`users` 表补 `role` 列时默认值是 `'admin'`（保证唯一的老管理员不被锁在外面），
启动时 `sync_user_roles()` 再按 `is_superuser` 对齐——
**原本 `is_superuser=false` 的账号会变成 `operator`**（不是 viewer，
避免突然失去已有的操作能力）。多用户老库升级后请到「用户权限」页复核一遍。

### 7.4 榜单订阅刷进来太多订阅

- 调小 `CF_RANKING_MAX_PER_RUN`（默认 5），或把规则的 `enabled` 关掉。
- 先用规则的「试算」看会建哪些，确认了再启用。
- 手动删掉的订阅**不会**被下次巡检加回来（规则记了 `handled_ids`）。

### 7.5 搜索结果顺序变了

检查「过滤规则组」页是否有组被设为**默认组**——默认组会改变全局搜索排序。
内置的 4 个模板出厂都不是默认组，所以升级本身不会改变你熟悉的顺序；
如果顺序变了，是有人点了「设为默认」。取消即可恢复。

### 7.6 下载任务总是投到同一个下载器

`CF_DOWNLOADER_STRATEGY` 默认是 `priority`（按优先级，与老版本一致）。
要摊开压力改成 `least_tasks` 或 `round_robin`，可在设置页直接改、立即生效。
注意「站点健康」页里状态为 down/degraded 的下载器会被**排到最后**
（但不会被剔除，以防健康数据过期导致完全不可投递）。

### 7.7 热榜封面显示成彩色色块

**这是预期行为，不是 bug。** 封面按**回退链**逐级尝试
（v1.7.0，ADR-29）：

```
站点自带元数据  →  豆瓣 subject_suggest  →  TMDB（需 Key）  →  占位色块
```

每一级都可能拿不到，全都失败才显示按标题哈希取色的占位块。

想让封面变多：启用带元数据的站点（如 Mukaku 类影视站）；
或确认服务端能访问豆瓣（回退链第二级，**无需 API Key**）。
已入库的老资源会在**下次搜索命中时回填**元数据，不需要清库。

如果是**真图裂了**（不是占位块），检查：
- **豆瓣封面走后端代理**（`/api/v1/images`）。豆瓣图床校验 `Referer`，
  裸请求返 **418**；浏览器跨站会剥离 Referer，所以前端加 `referrerpolicy` 治不了，
  必须由服务端补 Referer 转发（ADR-30）。若豆瓣图裂了，
  先确认**服务端**能出网，而不是检查浏览器。
- B 站 / YouTube / TMDB 图床实测可**直连**，这些不走代理，
  裂图说明是**浏览器**不能出网。
- 其他站点图床有防盗链 → 前端已带 `referrerpolicy="no-referrer"`，仍失败自动退占位
- NAS 不能直连外网 → 配 `CF_HTTP_PROXY`

### 7.9 豆瓣封面全都没有 / 日志出现豆瓣限流

**先看是不是限流自保**。豆瓣有反爬，所以内置了：缓存 6 小时、
一旦命中限流就**退避 300 秒**不再请求。退避期间封面会自动退回 TMDB 或占位色块，
**不影响搜索与下载**——这是设计好的降级，不用处理，等几分钟自愈。

| 现象 | 处理 |
|---|---|
| 偶发没有豆瓣封面 | 正常。榜单只给**前 24 条**补图（并发 8），避免补图拖慢响应 |
| 完全没有豆瓣封面 | 服务端不能访问 `movie.douban.com` → 配 `CF_HTTP_PROXY` |
| 封面配错了作品 | `subject_suggest` 是**按标题模糊匹配**，同名作品会配错。已知限制，v1.8.0 计划加年份/类型二次校验 |
| 想彻底关掉补图 | 榜单接口传 `with_poster=false` |

### 7.10 B 站 / YouTube 搜不到东西

| 现象 | 原因与处理 |
|---|---|
| B 站返回 412 | 该接口对不带 `buvid3` Cookie 的请求做风控。程序会**先 GET 一次 B 站首页拿 Cookie**（ADR-31），若仍 412 说明服务端出网被拦，检查代理 |
| 两个站都没结果 | 站点**默认禁用**。去「站点管理」启用 `bilibili` / `youtube` |
| YouTube 无结果 | 复用 yt-dlp 的 `ytsearch`，先确认 `pip install -r requirements.txt` 装了 yt-dlp，且服务端能访问 YouTube |
| 做种数大得离谱 | **预期**：网页视频没有做种数，把**播放量投影到 `seeders`** 以复用既有排序（ADR-32），只用于相对排序 |

### 7.11 新增的资源站点搜不到资源

v1.7.0 加了 9 条示例站点，**全部默认禁用**。启用后仍搜不到，
先对照下表——**其中 5 个站本身就有限制，不是配置问题**：

| 站点 | 状况 |
|---|---|
| `yyets` | ✅ 应该能用（实测 22 条）。不行则站点本身在波动 |
| `bdflixs` | ✅ 应该能用（实测 12 条磁力） |
| `juhebd` | ⚠️ 能搜到条目但**下载链接被微信公众号关注墙挡住**，只能当"有没有这部片"的探针 |
| `ldysg` | ⚠️ 只返回元数据（封面/年份/导演），**没有直链**。另注意域名实际是 `.top` 而非 `.win` |
| `mjf2020` | ⚠️ 疑似限流 / SSL 握手超时，多为站点侧问题 |
| `dygod` | ⚠️ GB2312 老站，搜索需 gb2312 编码；实测未命中过有效关键词 |
| `hdzu` | ❌ **403 自建反爬**，必须在站点配置里手工填**你自己登录后的 Cookie**（ADR-34）。我们刻意不逆向反爬 |

> 站点诊断（搜索响应里的 `sites[]`）会给出每站的 `ok/empty/timeout/error`
> 与失败原因，先看它再排查。

### 7.8 网页视频（yt-dlp）下载报错

| 现象 | 原因与处理 |
|---|---|
| 提示「长视频平台的正片播放页…」 | 有意拒绝：腾讯/爱奇艺/优酷/芒果正片与 Netflix 等需会员，本工具不做（ADR-24）。请用平台官方客户端的离线缓存 |
| 提示「站点限流（HTTP 412/429）」 | B 站等站点的频率风控。等几秒再试；同一链接的成功结果会缓存 5 分钟 |
| 提示「未安装 yt-dlp」 | `pip install -r requirements.txt` |
| 下到一半失败 / 只有视频没声音 | 缺 ffmpeg。装上即可合并分离流；未装时系统会自动退回单文件流（画质低一档） |
| 需要登录才能看的内容 | 在站点 `options.cookie_file` 填**你自己账号**导出的 cookie 文件路径；只支持下载你有权访问的内容 |
| 想限速 | 站点 `options.rate_limit`（单位 KB/s） |

## 8. v1.8.0 新增运维项

### 8.1 发现榜某一类空着

「发现」页有五个页签：**电影 / 电视剧 / 动漫 / 综艺**（数据来自豆瓣公开榜）
与 **Bilibili**（数据来自 B 站排行榜）。

| 现象 | 原因与处理 |
|---|---|
| 四个豆瓣类全空 | 豆瓣限流。榜单缓存 30 分钟、限流后退避 5 分钟，等一会儿自动恢复；日志会有豆瓣限流告警 |
| 只有某一类空 | 豆瓣的 `type` 只有 `movie`/`tv` 两种，动漫与综艺是靠 `tv` 的 tag 区分的。某个 tag 被豆瓣调整就会返回 0 条 —— 这类是上游变更，不影响其他页签 |
| Bilibili 页签空 | B 站排行榜对裸请求返回 `code=-352`（风控）。系统会先访问 B 站首页取 `buvid3` Cookie 再请求；若整体被风控，等几分钟或配 `CF_HTTP_PROXY` |
| B 站「番剧」「国创」空但其他分区正常 | 这两个是 PGC 内容，走的是另一个接口（`pgc/season/rank`）。若只有它们空，是该接口临时不可用 |
| 封面全是色块 | 图片代理拿不到图。见 §7.7 与 §7.9，属优雅降级不是报错 |
| 榜单条目上没有「已有 N 条片源」角标 | 说明本地资源库里还没有匹配的片源记录。先搜索/订阅几部片子，攒出记录后角标才会出现 |

> 发现榜是**只读展示**，不会自己发起下载。想追某一条，点进去用「订阅」按钮。

### 8.2 网盘扫码登录扫不出来 / 扫了没反应

「网盘管理」→「登录网盘」。三个网盘的支持程度**不一样**，这是上游决定的：

| 网盘 | 扫码 | Cookie 导入 |
|---|---|---|
| 115 | ✅ 官方接口，实测最稳 | ✅ |
| 百度 | ⚠️ 可用但风控较严 | ✅ |
| 夸克 | ❌ **不支持**（见下） | ✅ 支持导入 + 即时校验 |

| 现象 | 原因与处理 |
|---|---|
| 二维码不显示，只有一个链接 | 二维码图走图片代理拉取。代理失败时降级成可点链接，用手机打开也能登录 |
| 扫了但状态一直「等待扫码中…」 | 百度的状态查询是**长轮询**，十几秒才返回一次是正常的。多等两轮 |
| 百度提示「扫码已确认但未取到 BDUSS」 | 百度风控要求二次验证。**改用 Cookie 导入**，成功率高得多 |
| 提示「会话不存在或已过期」 | 扫码会话只存在内存里且 10 分钟过期；服务重启也会清空。重新点「登录网盘」即可 |
| 夸克没有扫码按钮 | **有意如此**。夸克登录接口要求签名过的客户端公参（`x-pan-client-id` / `x-pan-tm` / `x-pan-token`），逆向它属于对抗风控（ADR-38）。请用 Cookie 导入 |
| Cookie 导入点保存后报「未保存：…」 | 校验没通过就**不写库**（写进去只会让半夜的定时任务静默失败）。按提示重新取一份 Cookie |
| 登录成功后站点列表里多了一条 | 有意的：没有对应站点时自动创建并启用，省得你再去手工建一条还得猜 provider 填什么 |

**安全说明**（这几条是刻意设计的，不是遗漏）：

* 扫码会话**只存内存、不落库**，进程重启即清空。
* 接口返回给前端的会话数据里**绝不包含 Cookie**，只有状态和提示文案。
* 登录成功后 Cookie 立刻写入站点记录，会话随即销毁；过期会话报一次过期后也立即销毁。
* Cookie 等同账号密码。请勿把它贴到聊天群、issue 或日志里。

### 8.3 登录成功了但网盘操作还是失败

登录只保证「凭据当时有效」。之后失效有两种常见情形：

1. **Cookie 自然过期** → 「网盘管理」页看该网盘的状态；网盘保活任务
   （`cineflow.pan_keepalive`）会定时巡检并把失效的标记出来。重新登录即可。
2. **能力不支持** → 各网盘支持的操作不同（重命名/移动/搜索/保活），
   界面按后端声明的能力位渲染按钮。按钮不存在说明该网盘没有这个能力，
   不是界面出 bug。能力矩阵见 [`docs/06-网盘管理.md`](06-网盘管理.md)。


### 8.4 榜单封面部分裂图（约 1/4 显示占位色块）

**现象**：发现榜/热度排行里大部分封面正常，但零星几张始终是占位色块；
浏览器控制台报 `GET /api/v1/images/proxy?url=... 415 (Unsupported Media Type)`。

**原因**：豆瓣把封面随机分发到 `img1/img2/img3/img9.doubanio.com` 四个镜像，
其中 **`img9` 是长期损坏的节点**——即便带正确 Referer 也返回 200 + `text/html`
反爬脚本页而不是图片，被代理的图片类型校验挡下（返回 415）。详见 ADR-41。

**处置**：v1.8.0 起已自动修复（入库改写 + 代理侧镜像轮换），正常无需干预。
若仍遇到：

1. 确认版本 ≥ 1.8.0：`curl http://localhost:6060/api/health`
2. 手动验证某个镜像是否可用（把 `img9` 换成 `img3` 应返回 `image/jpeg`）：
   ```bash
   curl -sI -H "Referer: https://movie.douban.com/" \
     "https://img3.doubanio.com/view/photo/s_ratio_poster/public/p2930838026.jpg" \
     | grep -i content-type
   ```
3. 库里可能还留着旧版写入的 img9 地址，刷新榜单缓存即可（重新拉取会自动改写）
4. **注意**：不要为了消除 415 去放宽 `images.py` 里的 `content_type` 校验，
   那是 SSRF 三道防线之一（ADR-41 有说明）

## 9. v1.12.0 新增运维项

### 9.1 怎么配「白天限速、夜里跑满」

设置页 → **下载器限速时段**卡片。三个时段各自填「开始 / 结束 / 下载上限 / 上传上限」，
单位统一是 **KB/s**，填 `0` 表示该时段**不限速**。

| 字段 | 例子 | 说明 |
|---|---|---|
| 白天时段 | `08:00` ~ `23:00`，下载 `5120`、上传 `1024` | 上班时间别占满带宽 |
| 夜间时段 | `23:00` ~ `08:00`，下载 `0`、上传 `0` | 跨午夜是支持的，见下 |
| 默认（其余时间） | 留空 = 不限速 | 两个时段没覆盖到的时间用这个 |

生效方式：`cineflow.speed_limit` 任务每 **10 分钟**跑一次，
判断当前落在哪个时段，把该时段的值下发到**所有支持限速的下载器**。
不想等可以点卡片上的「立即应用」。

**几个必须知道的点**：

1. **跨午夜是支持的**：`23:00-08:00` 会被正确识别（内部拆成两段判断）。
   如果你的旧配置里写了这种区间却发现夜里没生效，那是 v1.12.0 之前的版本，升级即可。
2. **`start == end` 等于全天**，不是「零长度」。想关掉某个时段请把两个值都留空。
3. **迅雷和 yt-dlp 不支持限速**，应用结果里会如实显示 `skipped`。
   这不是故障——迅雷本地 CGI 与 yt-dlp 都没有全局限速接口。
4. **下载器侧手动改过限速会被覆盖**：任务是幂等下发，
   你在 qB 界面里手动调的值，下一轮（≤10 分钟）会被 CineFlow 的时段值盖掉。
   想手动管就把 `CF_SPEED_LIMIT_INTERVAL_MINUTES` 设为 `0` 关掉这个任务。

**排查「配了没生效」**：

```bash
# 看当前判定的时段与下发结果
curl -H "X-API-Token: your-token" http://localhost:6060/api/v1/downloaders/speed-limit
# 立即应用并看逐下载器结果
curl -X POST -H "X-API-Token: your-token" \
     http://localhost:6060/api/v1/downloaders/speed-limit/apply
```

返回里每个下载器有 `status`：`ok` / `skipped`（不支持）/ `error`（附原因）。

### 9.2 视频追更「一直没有新视频」

先分清是**没新视频**还是**判定错了**。

1. **先用「预览」**：视频追更页填完地址先点预览。它不落库，直接告诉你
   能不能解析、拿到几条、ID 是什么。解析失败在这一步就能看到原因。
2. **B 站拿不到标题是正常的**：yt-dlp 扁平提取对 B 站只返回视频 ID，
   `title` / `upload_date` 都是空。因此**标题包含/排除规则在 B 站上等于不生效**
   （设计上放行，见 ADR-58）——如果你靠标题过滤来控制下载量，B 站上会全下。
   YouTube 会给标题，规则正常生效。
3. **首次检查故意不下载**：勾了「跳过已有」时，首检只登记当前视频 ID，
   避免一订阅就灌进几百个历史视频。**第二轮**才开始下新的。
   想立刻下就取消勾选，或手动点「立即检查」两次。
4. **订阅被自动暂停了**：连续 5 次失败会自动置 `paused`（比如 UP 主注销、
   频道设为私有）。页面上状态是「已暂停」，修好原因后点「重置失败计数」恢复。
5. **失败的视频不会自动重试**：下载失败的 ID 也会记进已处理列表，
   否则每轮都卡在同一个坏链接上、新视频永远排不上队。要重试请手动下载那一条。

### 9.3 新番日历空着 / 封面全白

| 现象 | 原因 | 处置 |
|---|---|---|
| 整个日历空 | `api.bgm.tv` 不通（部分网络环境） | `curl https://api.bgm.tv/calendar` 验证；不通则该功能不可用，不影响其他页签 |
| 有条目但封面全是空白块 | 你通过 **HTTPS** 反代访问，而封面原始地址是 `http://` | v1.12.0 已统一改写为 `https://`；若仍白，检查 `bgm.tv` 是否在图片代理白名单里 |
| 条目显示日文名 | 该番 Bangumi 上没有中文名（约 10%） | 正常，回退日文原名而不是留白 |
| 某天一部都没有 | 当天确实无新番放送 | 正常，列头仍会显示日期 |

### 9.4 通知太吵 / 只想收失败

渠道配置（站点管理 → 通知类站点 → options）里加这三个字段：

```json
{
  "events": ["download.failed", "site.unhealthy"],
  "events_exclude": ["library.*"],
  "min_level": "warning"
}
```

- **三个都不填 = 全收**（老配置行为完全不变，升级不会静默失联）
- `events` 白名单与 `events_exclude` 黑名单都支持前缀通配，
  `download.*`、`download.`、`download` **三种写法完全等价**（v1.12.1 起）
- 通配以**点**为边界：`download.*` 不会误伤 `downloader.speed_limit`
- 事件名必须写对。合法名见[开发指南 → 可订阅事件](14-开发指南.md#可订阅事件)；
  写错了不会报错，只会让这个渠道**收不到对应通知**
- 白名单存在时，**没带 event 的通知仍然会发**——这是为了不吞掉老调用点的消息
- 同一条告警的重复间隔由 `CF_NOTIFY_ALERT_COOLDOWN_MINUTES`（默认 360 分钟）控制；
  恢复正常时立刻解除压制，所以「恢复通知」不会被压掉

### 9.5 封面比以前少了

v1.12.0 起豆瓣匹配加了 **60 分门槛**与年份校验：匹配不确定时**返回空**而不是硬给一张。
所以少数冷门条目会从「有封面（可能是错的）」变成「占位色块」。

这是刻意取舍：错封面会让人下错片子，空白封面一眼就知道是缺数据（ADR-61）。
想看某条为什么没匹配上：

```bash
curl -H "X-API-Token: your-token" \
  "http://localhost:6060/api/v1/trending/douban?title=片名&year=2024"
```

返回里带 `match_score` 与 `match_confidence`，低于 60 就会被判为不匹配。
